## Admin/Moderation Rework

The reviewer/staff moderation page (`admin.html`) got rebuilt from the ground up — same features, much more stable underneath, plus real bugs fixed along the way.

- **Fixed a bug where staff accounts could silently lose access.** A data-model issue meant a staff member with more than one role (e.g. both Reviewer and Trusted Editor) could get logged out of the moderation queue at random. Fixed at the database level so this can't happen again.
- **Split the 1,780-line `admin.js` into 7 focused files.** No user-facing change — this is what makes the next several bug fixes below actually findable and fixable, and makes future changes to this page far less likely to break something unrelated. (`js/admin-core.js`, `admin-queue.js`, `admin-diff.js`, `admin-preview.js`, `admin-tickets.js`, `admin-actions.js`, `admin-merge-compiler.js`, replacing the old single `js/admin.js`.)
- **New page: `owner.html`.** Site-owner-only tools (personnel/role management, media cleanup) moved out of the reviewer queue page into their own dedicated page — seed of a future "edit the site's structure without touching code" area.
- **Closed a security gap**: revision content shown to reviewers (author names, chat messages, QA notes, raw diff data) wasn't being sanitized before display — a malicious or careless submission could have run code in a reviewer's browser session. Now escaped everywhere.
- **Fixed voting on a ticket resetting your current view.** Supporting/opposing a revision used to silently snap you back to the default view even if you were looking at the live/diff comparison.
- **Fixed the OPPOSE button's state going stale** after posting a chat message on a ticket.
- **Fixed the "Revoke Access" button** in the new owner tools, which has silently failed every time it was ever used.
- **Fixed a data-corruption bug in the "merge conflicting tickets" tool** that could silently delete unrelated matchup/custom-tab/counterplay content when merging multiple pending edits to the same page. Root cause: conflicts were matched by array position instead of the item's actual identity, so a deletion in one submission could shift positions and get confused with an unrelated edit in another. Now matches by identity (same approach the delta-patch system already used correctly). Covered by a new test that reproduces the exact corruption scenario and confirms it fails against the old code, passes against the fix.

## Architecture note: no site-wide microservices rework

Considered and **rejected** (2026-08-02) — see conversation for full reasoning. Short version: the instability that motivated this idea was real, but it's oversized *client-side JavaScript files* (admin.js, editor.js), not a backend-services problem — there's no monolithic server here to split (Supabase already is a managed multi-service backend). The actual fix — splitting large files into focused modules, proven this week on admin.js — continues into editor.js and tierlist.js as those get their own passes, not a rewrite into networked microservices.

Checked actual file sizes before committing to a full "modularize everything" plan: `editor.js` (4,281 lines) was a genuine outlier, ~5x the next-biggest file — the other early scripts (`pagebuilder.js`, `description.js`, `framedata.js`, `site_meta.js`, `home_widgets.js`) showed no size-driven pain. Scope narrowed to editor.js only; the rest get a lighter structural look later, not a full split, unless a real problem turns up.

## `editor.js` Modularization (4,281 lines → 9 focused files)

The contributor CMS's core script got the same treatment as `admin.js` — split by responsibility, two real bugs fixed along the way, one long-standing "something's wrong with drafts" complaint finally root-caused and fixed.

- **Split the 4,281-line `editor.js` into 9 focused files**: `editor-core.js` (bootstrap/submit pipeline), `editor-tabs.js` (tab/move/matchup/counterplay editing + profile/playstyle), `editor-framedata.js` (the frame-data timeline builder), `editor-blocks.js` (the content block editor — add/reorder/drag text and media blocks), `editor-previews.js` (live preview rendering), `editor-sync.js` (pushes edits back into the data model + the diff comparison view), `editor-drafts.js` (local auto-save), `editor-media.js` (the media library), `editor-system.js` (system-page tab/section editing). No user-facing change on its own — this is what made the fixes below actually findable.
- **Fixed a real, long-standing draft-saving bug** — this is the "something wrong with save, I can't pinpoint it" issue. Drafts were being saved under a key scoped to whichever tab/move you were currently on, but the actual saved data was always your *entire* character's edits, not just that one section. Every time you switched between moves or tabs while editing, it silently created a brand-new, separate saved draft instead of updating the same one — old ones never got cleaned up, so the Draft Manager would slowly fill up with stale, confusing duplicate entries for the same character. Now there's exactly one draft per character, always kept up to date, and resuming it takes you back to wherever you last left off.
- **Fixed a copy-paste duplicate** in the tab editor (the same class of bug found in `admin.js` earlier) — some setup code was running twice in a row for no reason. No visible effect, just cleaned up.
- Removed one small dead function that was never actually being used anywhere.

**Process note**: this was executed in 8 small, independently-tested steps rather than one big rewrite — full test suite (102 specs) run after every single step. One real mistake happened along the way (a forgotten script-tag reference during the trickiest extraction) and the test suite caught it immediately, confirming the step-by-step approach is worth the overhead on a file this central to the CMS.

**Trivia, for the Discord/changelog if it's useful color**: the frame-data editor is internally called the "DAW" editor (Digital Audio Workstation) because the original idea was to let editors drag-and-drop frame data the way music producers arrange notes in a DAW. That's not how it actually works today, but the internal name stuck around.

## Reviewer workflow/UI redesign: kicked off, Phase 0 shipped (2026-08-02)

The reviewer/moderation page got its code stabilized earlier in v0.6 (see "Admin/Moderation Rework" above) — this is the follow-up: actually rethinking how the queue/review/diff experience looks and works, not just cleanup.

Since this system was built without reference to how real wikis handle moderation, it got a structured comparison against Wikipedia/MediaWiki's review model, GitHub-style PR review, and wiki talk-page/revert conventions. Six real gaps came out of that review, confirmed as the redesign's scope:

1. Rejecting a submission permanently deleted it — no institutional memory of disputed or bad edits.
2. No way to undo a bad edit once it's live, despite the data to do so already existing quietly in the background.
3. Reviewers can't tell how big or risky a pending edit is without opening it, and there's no way to casually browse "what's changed lately" across the whole site.
4. Frame data and move-stat changes showed up as two raw walls of text instead of a real, readable diff (prose content already gets this treatment).
5. No middle ground between approving as-is, rejecting outright, or a reviewer fully taking over and rewriting someone's submission themselves.
6. **The biggest one**: a regular contributor has zero way to see, edit, or take back their own submission once they hit Submit — the review page is staff-only, and the notification system that's supposed to tell them what happened doesn't work.

Plan: six phases, each an independently-shippable step, same discipline as the admin.js/editor.js rework. Phase 0 (foundation, no visible change on its own) is done:

- **Rejecting and withdrawing a submission are now status changes, not deletions.** The row, its discussion, and the reason it was declined all stick around instead of vanishing. Covered by a new regression test that reproduces the old delete-and-lose-everything behavior, confirmed to fail against the old code and pass against the fix.
- **Approving a submission no longer wipes its discussion history either.** The reasoning behind a decision now survives the decision.
- **Found a real, previously-unknown bug while researching this**: the table that's supposed to back a future "undo a bad edit" feature has been silently unreadable by anyone — the security rules were half-set-up and nothing was ever granted permission to actually read from it. Fixed as part of this phase since the later revert feature needs it anyway.
- **Live edits are now attributed to a real staff name** in the background version-history table, instead of a generic placeholder — needed so a future "who made this change" view actually means something.
- A new database migration ships these changes; applied to production and verified live.

**Phase 1 (the biggest gap, #6 above) is also done: contributors can now see, edit, and withdraw their own submissions.**

- **New page: `submissions.html` ("My Submissions").** Available to any logged-in account — no staff role required, unlike `admin.html`. Lists every edit you've ever submitted, in every state (still pending, in discussion, approved, declined, withdrawn), with the reason if something was declined.
- **Edit action**: reuses the exact same mechanism reviewers already use to intercept-and-edit a submission, just scoped to your own — jumps straight into the editor with your submitted content pre-loaded, and updates your original submission in place instead of creating a duplicate. Fixed one thing that would have made this confusing: that shared code always used to stamp a "Staff Note: edits applied by [reviewer]" message onto the changelog, even when you're just editing your own work — it now only does that when someone *other* than the original author is the one editing.
- **Withdraw action**: pulls a submission out of the review queue yourself, no staff involvement needed — a soft status change (see Phase 0), not a delete, so it stays visible in your own history afterward.
- **New "MY SUBMISSIONS" link** in the account dock (next to Inbox), visible to anyone logged in.
- Covered by 3 new Playwright specs (logged-out state, every status/action-visibility combination, and the withdraw action's exact database call) — full suite 107/107.
- **Not yet done manually**: a real end-to-end click-through as an actual logged-in contributor account (submit → see it appear → edit it → withdraw it) — everything below that layer (RLS policies, the page's own logic) is verified, but this specific full loop as a real user hasn't been walked through yet. Worth doing before calling Phase 1 fully closed.

**Phase 2 (queue triage signals + real diffing for structured data, gaps #3/#4) — done (2026-08-03).**

- **Review queue cards now show what actually changed, not just the category.** A pending matchup edit used to just say "[PATCH: MATCHUP]" — now it says "[PATCH: MATCHUP: vs Crow Charmer]", same for moves ("MOVE: 5H") and every other section. Ten pending move edits on the same character no longer look identical until you open every single one.
- **A rough size badge (S/M/L)** on every card, so a one-word typo fix doesn't demand the same scrutiny as a full section rewrite before you even open it.
- **Frame data and move-stat changes now show a real, readable diff** instead of two raw JSON blobs stacked on top of each other. Changed numbers are struck-through/highlighted old→new, added/removed fields are marked, and anything unchanged is left out entirely — same visual style already used for prose edits. This is the single biggest legibility fix in this pass: reviewers were previously expected to eyeball-diff two JSON dumps to catch a single changed frame number.
- Covered by 5 new Playwright specs (every change type: modified/added/removed fields, nested objects, whole-section deletions, plus the new queue badges) — full suite 112/112.

**Found but deliberately not touched this pass**: the existing prose diff engine (`diffTextLCS`, used for paragraph/list/table content) inserts submitted text into the page without escaping it first — a real gap, same class of issue fixed elsewhere on this page months ago, but a change to a shared, heavily-used function that's out of Phase 2's actual scope. Flagged for a dedicated look rather than folded in silently.

**Phase 3 (a lighter "request changes" action, gap #5) — done (2026-08-03).**

- **New REQUEST CHANGES button** for reviewers/admins, alongside the existing options. Sends a specific, written ask back to the original author instead of the only two prior choices: approve/reject outright, or take over and rewrite their submission yourself. Opens a discussion thread automatically if one isn't already going.
- **Shows up clearly for the author too** — a submission with changes requested now stands out from generic "in discussion" both in the review queue's chat log (a highlighted callout, not just another line) and on the contributor's own "My Submissions" page (a specific "CHANGES REQUESTED" status with the actual ask shown, not a vague "someone's discussing this").
- Not shown when reviewing your own submission — asking yourself for changes doesn't make sense.
- Covered by 5 new Playwright specs (button visibility per role/ownership, the request-and-open-ticket flow, cancel-does-nothing, the distinct chat styling, and the contributor-facing view). Full suite 117/117. Also re-verified the mobile action-button row (fixed earlier this pass) still wraps cleanly with the new button added to the mix.

**Another real bug found via live use (2026-08-03, reported by the owner), logged not fixed**: the diff comparison view's title, location label, and the actual diff content all render on the same row instead of stacking normally. Root cause: `admin-preview.js` builds that container by copying a class pairing from an unrelated part of the codebase (`description.js`'s system-page tab containers) that happens to include a flex-wrap layout rule never meant for this container. Purely a styling bug, nothing broken functionally, low urgency.

**Phase 4 (public sitewide "Recent Changes" feed, the other half of gap #3) — done (2026-08-03).**

- **New public page: `recent-changes.html`.** Every staff-approved edit across the entire wiki, newest first, paginated — no login required. Linked from the sidebar on the homepage, `history.html`, and the reviewer page.
- **A real, previously-unknown bug found and fixed while building this**: the site's *existing* per-page history (`history.html`) has apparently never actually worked for a genuinely logged-out visitor, despite its own header literally saying "Public history of all staff-approved revisions." Confirmed live: an anonymous visit failed silently behind a permission error that got swallowed into a misleading "No history recorded for this page yet" message. Root cause took three small, purely-additive database fixes to fully resolve (each verified live against production before moving to the next): a missing read-permission rule for approved edits, a missing table-level read grant for logged-out visitors, and a missing permission on a shared internal role-lookup function that was blocking the *first* fix from actually taking effect. All three shipped; both `history.html` and the new `recent-changes.html` now confirmed working end-to-end against live production data as an anonymous visitor.
- Covered by 4 new Playwright specs (multi-page rendering, XSS-safety, pagination, navigation.json validity). Full suite 121/121.

**Phase 5 (undo/revert for live edits, gap #2, the last phase) — done (2026-08-03). This closes out the entire reviewer-workflow redesign.**

- **New "PAGE HISTORY" view in the reviewer page**, right alongside Pending/Live/Diff. Lists every past live version of the page currently being reviewed, each showing when it was live and who made the change that superseded it.
- **"Compare to Live"** on any past version shows exactly what's different from what's live right now — reusing the same readable diff view built in Phase 2, not raw data.
- **"Restore This Version"** — one click, immediate. Reviewers/admins only (inherited from the page's existing access control). Deliberately *not* routed through the normal review queue, matching how real wikis handle rollback: restoring known-good prior content is lower-risk than a brand-new unreviewed submission, and staff could already push anything live directly via Force Approve. Restoring is itself just a normal save, so it automatically preserves whatever was live right before it as its own new history entry — a restore can always be undone the same way.
- **Verified for real, not just in tests**: actually ran the restore mechanism against production (using Boomcat, the designated test character) — restored it to an older snapshot, confirmed the history trail recorded it correctly, then restored it back to exactly where it started and confirmed the content matches byte-for-byte. Zero lasting change to real content.
- Covered by 6 new Playwright specs (listing, toggling, diff comparison, the restore action itself, and cancel-does-nothing). Full suite 127/127.

**This closes the reviewer-workflow/UI redesign.** All six gaps identified when this started (rejections destroying history, no revert, no queue triage signal, unreadable structured-data diffs, no middle ground between approve/reject, contributors locked out of their own submissions) are now addressed. Three small, low-priority styling/security bugs found along the way remain logged but unfixed (see above) - none blocking, all good candidates for whenever their respective files get touched again.

## Mobile support: closing out the rest of the site (2026-08-02)

The last three areas the v0.5 mobile pass flagged as unaudited fast-follows got the same real-device-viewport verification treatment as the rest of v0.5 — check first, only fix what's actually confirmed broken.

- **Fixed: `history.html` had no mobile navigation at all.** The v0.5 pass added a mobile hamburger menu + slide-out sidebar to every system/hub page and every character page, but `history.html` fell through the cracks of both sweeps — it's neither. Confirmed live at a 375px viewport: the sidebar sat fully off-screen with zero hamburger button, zero backdrop, nothing in the DOM to open it — a page a mobile visitor genuinely could not navigate away from except the browser back button. Fixed by adding the same `.mobile-top-bar`/`#mobile-menu-toggle`/`#mobile-backdrop` markup and wiring up the already-shared `window.initMobileNav()`. Verified end-to-end: tapping the menu opens the sidebar, tapping outside closes it.
- **Fixed: the Media Library modal was unusable on mobile.** Confirmed live: the modal's footer (upload zone, page controls, Refresh/Close buttons) was laid out with an inline 3-column grid that a `display:grid`-blind mobile CSS rule could never actually override. Result: the Close button rendered 122px past the right edge of a 375px screen, completely untappable, with no other way to dismiss the modal. Root cause was a leftover inline style duplicating (and silently beating) a CSS rule that already did the job correctly and already had a working mobile fallback — removed the inline style so the real rule takes over, and hardened the mobile override itself so this can't quietly break again. Verified live: footer now stacks in one column, every control fully on-screen, Close button confirmed clickable.
- **Fixed: buttons across the whole site were under the standard mobile touch-target size.** `.btn-sys` (used everywhere: modals, history pagination, admin/owner tools) and `.btn-manga` (tab navigation, filters, action buttons) measured ~28-33px tall on a phone — noticeably smaller than the ~44px Apple/Google guideline for a comfortable tap target. Added a mobile-only minimum height across both button families; desktop sizing is completely untouched (verified: still exactly the original size above 1024px width).
- **Confirmed fine, no changes needed:** matchup/counterplay preview cards (tested with real data plus an artificially worst-case-length opponent name + tier label — text wraps cleanly, never overflows) and the login/auth and confirm/delete modals (both already had a working `max-width: 95vw` mobile rule, verified live with no overflow).

Verified: full 102-spec Playwright suite green after all three fixes.

**Two more real bugs found via actual on-device testing, both traced back to the touch-target fix above:**
- **Fixed: the editor's header/toolbar was eating over half the screen.** The site-wide 44px button-height minimum was correct almost everywhere, but it landed badly in `edit.html`'s already-cramped mobile header: 5 toolbar buttons that already wrap across 2 rows regardless of height, plus a stacked HUB/Show Preview pair, compounded the extra height 4 times over. Confirmed live: the actual editable content dropped from starting at ~45% down the screen to ~58% down - workspace shrank to barely 45% of the viewport, exactly as reported. The editor's mobile layout already had a deliberate "compact everything, screen space is precious" design from v0.5; exempted the header's buttons back to their original size so that holds again. Verified live: header back down to its original height, workspace back to ~82% of the viewport.
- **Fixed: reviewers on mobile couldn't reach the Accept/Reject/Open Ticket buttons at all.** A pre-existing bug, surfaced by the same real-device pass - the row holding these buttons never had a mobile wrap rule, so on a narrow screen the row simply ran off the right edge of the phone with no way to scroll to what fell off. Confirmed via the worst case (4 buttons at once): fixed by letting the row wrap and buttons share the available width evenly, verified every button lands fully on-screen and tappable in every combination the queue can produce.

Verified: full 102-spec Playwright suite green after these two follow-up fixes too.

## One more real bug, reported live right after the "ready to ship" call above (2026-08-03)

**A reviewer navigating admin.html → Recent Changes → back got locked out with "Access Denied," every single time — despite being a legitimate reviewer.** A plain refresh of the admin page always fixed it. That exact pattern (100% reproducible, but a manual refresh always clears it) is the fingerprint of the browser's **back-forward cache**: modern browsers can restore a page from a frozen snapshot when you hit "back," without re-running its login check at all — so the page came back showing whatever bad/incomplete state it happened to be frozen in, instead of properly re-verifying who's logged in.

Confirmed with a live reproduction test before writing the fix. Fixed by having the reviewer page (and the owner tools page, which has the exact same login-check setup and was equally exposed) explicitly detect when they're being restored from that frozen cache and force a real reload — so returning via the back button now behaves exactly like hitting refresh, every time. 3 new tests, full suite 135/135.

**v0.6 is now fully complete and ready to ship** — admin rework, editor.js modularization, mobile support, and the full six-phase reviewer-workflow redesign, plus every bug found along the way (including this one, found via real usage right at the finish line) fixed. Nothing outstanding.

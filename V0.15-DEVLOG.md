## Scope changes to the roadmap (owner, 2026-08-15)

- **Side-by-side character comparison — REMOVED.** Cut, not deferred; it should
  not reappear in a later version's scope.
- **Tier-list edit-in-place — REPLACED** by **Create Tier List**: a tool page
  under the Tools column's Community category. Drag-and-drop characters into
  tiers, tier names and colours customisable, one button to download the result
  as a PNG. No edit button and no History — it is a tool, not a page.
- **Skill Builder ID Reader — CONFIGURATION ONLY, no code.** The page exists
  already. Restricting it to the owner is `site_pages.edit_role = 'elevated'`
  plus a `page_permissions` row with `required_role = 'admin'`. Both values are
  already in the schema and already enforced server-side.
- **Multi-tab submission — MOVED to the bug list.** It is built; it drops data.

### The rule behind the ID Reader decision

**An editable `tool` page wraps an EXTERNAL tool** — the page is description,
link and context, so it is content, and content gets edited.
**A non-editable `tool` page has its logic IN the page** — Free Submit Tier
List, Create Tier List. Nothing to submit, so no edit button and no History.

## Three findings that change the shape of this list

Recorded before building, because each one moves an item.

**Bugs 3, 5 and 6 share one axis — investigated 2026-08-16, and two are now
located exactly.**

**Bug 3 (a state's edits are dropped on submit) — CONFIRMED, `js/editor-core.js:834`.**
The character payload engine's own comment says it *"Scans EVERY tab, not just
the open one"*, and it does — that was the v0.13 fix for the tab axis. But
every scan inside it reads `window.currentEditorDescData` /
`window.currentEditorFrameData`, and `js/editor-modes.js:74` points those at
**the active state's slice** (`master.modeData[modeId]`). So the scan sweeps
every tab *within one state*, and `buildPayload` tags what it finds with
`window.editorActiveMode` as it stands at submit time.

Edit three states, press Submit once, and only the active state produces
deltas. The other two are still in `editorMasterDescData` and still ride along
in the payload's `desc_data` fallback — but the reviewer applies the *delta*,
so they never land. **It is the v0.13 bug again, one axis over:** tabs were
fixed, states were not.

The fix has the same shape as v0.13's: lift the scan into a function called
once per declared state, with `currentEditor*` re-pointed for each pass, and
let `scopeEditorDelta` wrap each state's deltas as it already does. Several
deltas from one submit already become a `multi` ticket, which admin compiles —
so the reviewer side should need nothing.

**Bug 6 ("edit this tab" on an ultimate tab opens the base Overview) —
CONFIRMED, `js/pagebuilder.js:254-261`.** Two defects in eight lines, matching
the owner's phrasing exactly:

```js
const activeTabEl = document.querySelector('nav.character-nav .btn-manga.active');
let activeTabId = 'overview';
if (activeTabEl) activeTabId = activeTabEl.id.replace('nav-', '');
window.location.href = `../../edit.html?page=${pageId}&type=${pageType}&tab=${activeTabId}`;
```

The URL carries **no `&mode=`**, while `js/editor-modes.js:376` reads exactly
that parameter to choose the state — so the editor always opens on the base
kit. And when the selector misses, `activeTabId` silently falls back to
`'overview'`. *"The overview of the base"* is those two lines, one each.

Note `js/character_modes.js:158-161` already maintains `?mode=` on the reading
page's own URL, so the value the button needs is sitting right there.

**Bugs 3 and 6 — FIXED 2026-08-16.**

Bug 3: the tab scan is now wrapped in a per-state loop. The states come from
`modeData` — the **data**, not the declared `modes` list — because dropping a
contributor's work is the bug being fixed, so a state carrying a bucket but
missing from the declaration must still be scanned. Reading the data rather
than the declaration also stops `writableView` creating empty buckets as a side
effect of scanning, and a state nobody ever opened has no bucket and therefore
nothing to find. `scopeEditorDelta` already reads `editorActiveMode`, so each
pass tags its own deltas and the nine scopes still never learn states exist.
The restore sits in a `finally` — a submit that left the editor pointed at
whichever state was scanned last would move the user somewhere they never
navigated.

Bug 6: `handleEditClick` now carries `&mode=`, preferring
`window.activeCharacterMode` over the URL parameter because the in-memory value
is correct before the first `switchCharacterMode` writes it. Base sends no
parameter rather than `?mode=base`, matching what `character_modes.js` does to
the canonical URL.

**One thing bug 6 turned out NOT to be.** The `tab=` half was already correct:
`<nav class="character-nav">` really is a `nav` element so the selector
matches, `js/character_modes.js:77` gives the Ultimate tab
`id="nav-ultimateAtk"`, and `js/editor-core.js:138` honours `?tab=`. So the
"lands on Overview" half of that report was **not** a second defect in this
path. If it still happens after this fix, it is bug 5 and needs reproducing
separately.

**Bug 5 (switching views lands on Overview) — same axis, NOT yet located.**
`window.switchCharacterMode` (`js/character_modes.js:128`) reloads the move
sections and descriptions but never touches tab selection, so the reset is
happening in the re-render underneath it — most likely `loadPageDescriptions`
rebuilding the tab container and defaulting to the first tab. **Unverified.**
Do not fix it by assumption; reproduce it first.

**Fine-tuning 1 is mostly built already.** `data/page-previews.json` is exactly
the map that item asks for — `page_id` → portrait URL, generated from
`page_data.desc_data.profile.image` and refreshed by the nightly regeneration
job. It is currently only consumed for social preview images in the generated
stubs. The tier list pages need to read it rather than query Supabase, which is
wiring rather than a feature. **One consequence to accept:** portraits refresh
nightly, not instantly — and since regeneration now targets `next-update`, a
new portrait reaches the live site at the next release rather than the next day.

**Feature 2's colour token is `--accent-blue`, not `--color-blue`.**
`js/site_meta.js:159` sets `--accent-blue` to the character's colour, and there
is no `--color-blue` anywhere in the codebase. The per-character theming the

## Settled: there is no sub-state, and there should not be one (2026-08-16)

Raised, investigated and **closed the same day**. Recorded so it is not
reopened, because the wrong answer here is expensive and superficially
reasonable.

The question was whether characters need states nested inside states. The
answer is no, and the example that settles it is Blood Manipulator: his Base
Kit is an install — he builds orbs, and the community calls the two forms
"Orbless Choso" and "Orb Choso". **With orbs, *some of his skills* change.**
Some skills, not the kit.

**The codebase already has the right mechanism, and it is not states.**

| | Mechanism | Where |
|---|---|---|
| The character effectively becomes a different character with a different kit | **A state** (`modes`) | Base Kit / Ultimate, flat, max 4 |
| A resource or condition changes *some* moves | **A move variant** (`move.variants`) | nested, already rendered by `js/framedata.js:489-537`, already edited via `daw-variant-tabs` |

This matches the convention the reference itself follows: Dustloop gives Ky's
Dragon Install its own tab because it replaces the kit, and documents
conditional moves as conditions on the row.

**The cheap answer also dodges the hard problem.** Nesting states would have
meant inheritance — a sub-state showing its parent's moves where it defines
none — and `window.resolveModeFrame` deliberately refuses that at the state
level, for a good reason its own comment gives: *"a mode with no skills written
yet shows an empty Skills tab, which is the honest answer. Falling back to the
base kit there would silently claim the ultimate has the same moves as the
base."* Inheritance would have required "unset" and "deliberately empty" to
become distinguishable in the data. At the move level none of that arises: a
move you did not change simply has no variant.

**The one real gap, and it is content rather than code.** Variants are
per-move, so nothing currently says "this character has an orb resource" in one
place — a reader infers it from four separate skill tabs. That wants a
character-mechanic note on Overview or Playstyle. Writing, not engineering.

**For the combo table this means one tab row (states) plus a condition column**
(`Orbless` / `Orb`) — not a second tab row.

Confirmed by the owner: **no character currently has a second full kit inside
the Base Kit.** If one ever does, this decision is worth revisiting with that
character as the example.

### The combo row schema, exact

127 rows, every one of them carrying:

```
combo          notation, wrapped in colour macros
position       Anywhere | Corner | Midscreen
damage         "106", "54~58", "4 (2+2)"   <- a STRING, not a number
tensionGain    "16%", "-36%"               <- its own field
worksOn        Everyone | a character list
difficulty     Very Easy | Easy | Medium | Hard | Very Hard
notes          prose
video          external link      (126 of 127)
checkedVersion "2.00"
recipePC       (5 of 127)
```

**Four corrections to what the screenshot implied:**

- **`tensionGain` is a separate field.** The screenshot showed it inside the
  Notes cell, so the *renderer* merges them — the data does not.
- **The table has no "Recipe".** `Recipe` belongs to TheoryBox. The table's
  rare `recipePC` (5 of 127) is a different thing, and what it is remains open.
- **Difficulty has FIVE levels, not four.** `Read First` states the 1–5 scale;
  the screenshot only happened to show four of them.
- **`damage` is a string**, and the column is sortable. `"54~58"` and
  `"4 (2+2)"` do not sort numerically, so sorting needs an explicit sort key.
  This is the kind of detail that looks like a bug six months later.

### Groupings and sub-tabs

Tables are grouped by **starter**, eight groups: `5P/2P/6P`, `5K/2K/6K`,
`c.S/f.S/2S`, `5H/2H/6H`, `5D/2D`, Air-to-Air, Jump-in, Special Move. Most
appear twice, once per character state.

`<tabber>` is used **throughout the page, not only for character states** —
"Normal Version / Easier Version", "Without Shock State / With Shock State",
"Preface". It is a general sub-tab primitive, which is a third possible block
type rather than a states feature.

### The colour macro is the load-bearing primitive

`{{clr|KEY|text}}` appears **1,447 times** — every input in every combo,
every difficulty label. It maps directly onto `internalstyling.js`, which
already colours terms from `FRAME_COLORS` and the character map. JJS needs its
own key vocabulary in place of Guilty Gear's P/K/S/H/D.

Three resource fields, each optional, each game-specific. **JJS needs its own
list here** — the pattern is "optional named resources rendered above the
prose", not "tension".

**`Ver` is a freshness check, not a label.** `GGST-VersionCheck` compares the
recorded version against the game's current one, which is why the screenshot
shows it in green. That is the most quietly valuable column on the page for a
wiki whose game keeps updating, and it is the same field as feature 12's Game
Version.

**THE RECIPE NAMING TRAP.** `Recipe` means two different things and both
appear on this page:

* In **TheoryBox**, `Recipe` is the *combo notation*, rendered through
  `ComboText` — the same treatment as the table's `combo` field.
* In the **table**, `Recipe` is the *controller input*, `recipePC` or
  `recipePS`, with a `(PC)`/`(PS)` subtitle.

Naming both "recipe" in our schema would guarantee a wrong-field bug. Pick two
words.

**TheoryBox** is a four-area CSS grid — Title, Difficulty, Content, VidArea —
two columns above 900px (`1fr 300px`) and stacked below. Title is a bold name
plus an italic one-liner; Difficulty is right-aligned and rendered with
`noNumber=true`, so the *same* difficulty value shows its number in the table
and not on the card. Video supports several entries, either YouTube embeds or
files with autoplay/loop/muted or a poster.

### The colour system, and what to take from it

`{{clr|KEY|text}}` is **two layers**, and the indirection is the good part:

1. A **per-game key map**: GGST is `P→1, K→2, S→3, H→4, D→5`; every other game
   maps its own buttons onto the same numbers.
2. **Eight numbered slots** rendered as CSS classes `colorful-text-1..8`.
   Anything outside 1–8 falls through to an inline `style="color: …"`.

So difficulty and buttons **share one palette** — "Very Easy" is slot 6, `5P`
is slot 1. One palette, several vocabularies pointing into it.

Their documentation gives the reason for classes over inline styles outright:
*"Colors applied with this template can be disabled or re-enabled through the
use of Monochrome mode and Colorful mode, so it is recommended to use this over
applying text colors with style attribute."* That is an accessibility
affordance we do not have and could.

**Where this lands in our code.** `js/internalstyling.js` already emits classes
for everything — `sc-b`, `sc-i`, `sc-kbd`, `sc-code` — **except its
auto-colouring**, which at line 270 emits `<span class="sc-color"
style="color: …">`. And `window.FRAME_COLORS` already reads its values from CSS
custom properties, so the palette is already themeable. The missing piece is
only the named-slot vocabulary layer, plus moving that one inline style onto a
class.

### Per-URL tabs instead of a tab strip — FEASIBLE (scan, 2026-08-16)

The owner asked whether the site could move from client-side tabs to one URL
per section, the way the reference does. **It can, and several things get
simpler rather than harder.**

**The hatch already exists.** `js/page_router.js:60` reads
`const tabs = route.tabs || DEFAULT_CHARACTER_TABS;`, and the comment above it
says why: *"The PAGE_ROUTE.tabs escape hatch is intentionally unused today. It
lets the generator start emitting per-page tab lists later without reworking
this module."* Written in v0.9 in anticipation of exactly this.

**Stubs are already fully generated** — 58 lines, carrying the whole routing
contract in one object: `window.PAGE_ROUTE = { pageId, pageType, title }`.
Emitting one per section is a generator change, not an architecture change.

**No existing link breaks.** `characters/X/index.html` stays and becomes the
Overview page. Every URL already posted to Discord keeps resolving.

**What gets better:**

| | |
|---|---|
| Discord embeds | one `og:title` per character today; per-URL gives "Boomcat — Combos" |
| Load cost | `page_boot.js` fires m1s + skills + specials + descriptions on *every* character page regardless of tab. Per-URL loads one |
| Search (a v0.15 item) | results land on the section, not the character |
| Bug 6's fragility | the editor link reads `tab` from `PAGE_ROUTE` instead of querying the DOM for `.btn-manga.active` |
| ToC | indexes the page rather than the visible tab |

**What it costs:** a tab switch becomes a page load (offset by the smaller
payload); the sitemap grows from 54 URLs to roughly 240; about 207 generated
stubs instead of 23; and `?mode=` has to be carried across links rather than
living in one page's history.

**Two unknowns, honestly flagged.** `js/description.js` is *shape-driven rather
than tab-driven* — v0.9's own comment calls unifying character tabs with
`desc_data.tabs[]` the larger data-model change — and rendering a single tab in
isolation has not been proven, only looked at. Discussion threads, the gallery
and editor draft scoping all currently assume one page per character and each
needs checking.

**Recommended sequencing, and it does not commit to the migration:**

1. **Extract the tab vocabulary** into one module. Needed either way, small,
   and it unblocks both this and the two new tabs.
2. **Prototype per-URL on one character** through the existing generator, and
   prove the two unknowns above.
3. **Then decide.** If the prototype is clean the rest is mechanical; if
   `description.js` fights back, the tab strip stays and the two new tabs land
   in it instead.

### JJS notation is NAME-FIRST, and that changes the design (2026-08-16)

The owner supplied the input vocabulary and, more usefully, real combos as
their contributors actually write them.

**The inputs.** `M1` basic attack; `1 2 3 4` the four skills per kit; `R` the
one special per kit; `F` block; `Q` dash; `Space` jump, which also enables air
variants and hold variants; `Shift` shift-lock; `A W S D` directions, which
modify some skills, some specials and every dash.

**The critical difference from the reference.** Dustloop is notation-first —
`c.S > 2H > 214S` *is* the combo, and names are looked up from it. JJS
contributors write the opposite way round: the **name is the content and the
input is an annotation**.

```
Flowing Red Scale (2)
Uppercut (Last M1 + Hold Space)
Aerial Flowing Red Scale (Air 2)
Hold Down Piercing Blood (Hold 1)
```

The owner attributes this to "site inexperience and lack of features". Treat it
instead as the thing to build for. JJS moves have names players actually say,
and a numeric notation would impose a Guilty Gear convention on a community
that does not use one — precisely what `CLAUDE.md` warns against.

**Consequences for the schema.** A combo step is `{ move, input, modifiers }`,
not a string to be parsed. Which means:

* The **name can link to the move** the way `{{MMC}}` does in the reference —
  and frame data already carries move ids, so the link target exists.
* Colour applies to **the input annotation**, not the whole cell. Far less
  fragile than colourising prose.
* `M1 x3` (repetition) and `>` (sequencing) are already in contributor usage
  and need to survive whatever the editor does.

**Proposed slots — needs the owner's sign-off:**

| Coloured | `M1`, `1`, `2`, `3`, `4`, `R`, `F`, `Q`, `Space`, `Shift` |
|---|---|
| **Plain** | `A W S D` — directions, the same call Dustloop makes for its numeric prefixes |
| **Muted prefix** | `Air`, `Hold`, `Last`, `Charged`, `Release` — a small closed modifier vocabulary |

Ten input slots plus the five difficulty levels. Slots are CSS classes, so the
count is cheap; the open question is whether `1 2 3 4` deserve four distinct
colours or share one "skill" colour.

**The Orbless/Orb example confirms an earlier decision.** The owner's two combo
lists are "Orbless Choso" and "Orb Choso" — the install case. They are two
*lists*, not two character states, which is exactly why that was recorded as a
**condition tag on the row** rather than a second tab row.

### What contributors actually write (owner screenshots, 2026-08-16)

**Contributors do NOT write key inputs.** The parentheses in the examples above
were the owner annotating for this conversation. Real live combos, from Crow
Charmer and Yuki pages:

```
MURMURATE → R↑
M1 (X3) → MURMURATE → R↑ → BIRD CONTROL(W) - OPTIONAL → DIVE BOMB
M1 (X3) → UPPERCUT (SURF) → BOUNDING → DIVE BOMB → R↑ → BOUNDING → …
IMPETUS UPDRAFT (USE TWICE) → R(W) → CIRCLING → …
M1 → M1 → M1 → UPPERCUT → GARUDA REBOUND ONCE → GARUDA REBOUND TWICE
    → GARUDA STAB OR RISING RAGE
RISING RAGE OR MASS BREAKER (PICK THE ONE YOU USED TO CD CANCEL INITIALLY)
```

**They write move NAMES, with free-form qualifiers.** Catalogued from the
screenshots, because no schema would have predicted this list:

| Form | Examples |
|---|---|
| repetition | `(X3)`, `(RX2)`, `(USE TWICE)` |
| tech / variant | `(SURF)`, `(SLOWED)` |
| direction attached to a key | `R↑`, `R↓`, `R(W)`, `BIRD CONTROL(S)` |
| alternatives | `GARUDA STAB OR RISING RAGE` |
| optionality | `- OPTIONAL` |
| open-ended | `…` at either end |
| plain instruction | `(PICK THE ONE YOU USED TO CD CANCEL INITIALLY)` |

**THE DESIGN CONCLUSION: do not over-structure the step.**

The earlier plan here — `{ move, input, modifiers }` per step — is wrong, and
the screenshots are the reason. A structured step cannot hold "GARUDA STAB OR
RISING RAGE" or "(PICK THE ONE YOU USED TO CD CANCEL INITIALLY)", and
contributors are writing both today. Forcing structure would either lose that
content or make the editor unusable for the people who actually fill the wiki.

**A step stays free text. Structure goes at the ROW level**, where the missing
fields actually are: position, damage, difficulty, works on, version, notes,
setup. That also means **no migration** — the existing `sequence` array of
strings survives as-is.

The renderer colours *recognised tokens* inside the free text and leaves
everything else alone. `internalstyling.js` already works exactly this way, and
`[noauto]` already exists for the token that must be left alone.

**Directions appear attached to keys, not standalone** — `R↑`, `R(W)`,
`BIRD CONTROL(S)`. Both arrow glyphs and WASD letters are in live use. Colour
the key, leave the direction plain.

**Skill slots get four distinct colours** (owner: "distinction between skill
slot are a thing" in JJS), so `1 2 3 4` are four slots rather than one.

### THE COMBOS TAB DESIGN, modelled on Overview & Strategy (2026-08-16)

Owner's instruction: lay the components out the way Overview & Strategy already
does. That tab is **fixed sections plus free sections keyed by title**, and the
whole design falls out of it.

**How Overview & Strategy is actually built:**

```js
desc_data.profile   = [blocks]                       // fixed
desc_data.overview  = [blocks]                       // fixed
desc_data.playstyle = [blocks]                       // fixed
desc_data.strategy  = [blocks]                       // fixed
desc_data.extras    = [{ title, content: [blocks] }] // N, keyed by title
```

Its editor is a sub-tab strip (`daw-tab-btn`) of four fixed buttons plus N
removable extras over one swapping container. Its deltas are
`<section>`/`'full'` for the fixed four and `extra`/`<title>` for the rest.

**The Combos tab, in exactly that pattern:**

```js
desc_data.comboIntro  = [blocks]                        // fixed — "Read First"
desc_data.comboGroups = [{ title, content: [blocks] }]  // N, keyed by title
desc_data.comboList   = [{ starter, rows: [...] }]      // N, keyed by starter
```

**Why the groups are author-named rather than fixed.** The reference calls them
Beginner / Core / Specialized. The owner's own live pages call them **True
Combos / Simpler Combos / Advanced Combos**. Hardcoding the reference's names
would import a vocabulary this community does not use — the exact failure
`CLAUDE.md` warns about. So a combo group is an *extra*: same shape, same
editor, same delta pattern, author picks the name.

**Every one of those three shapes already exists in this codebase**, which
means the submit, diff, merge and review paths need **no new machinery at all**:

| New field | Same shape as | Scanned by |
|---|---|---|
| `comboIntro` | `overview` / `strategy` | the fixed-section loop in `scanOverview` |
| `comboGroups` | `extras` (title-keyed) | `scanKeyedList('comboGroups', 'title', 'comboGroup')` |
| `comboList` | `matchups` (opponent-keyed) | `scanKeyedList('comboList', 'starter', 'comboTable')` |

`scanKeyedList` is already generic over `(field, keyField, scope)` and already
serves matchups and counterplay. Two more calls, no new function.

**Keying the table by starter is what keeps review readable.** The reference
has 127 rows for one character. As one `comboList`/`'full'` delta a reviewer
would face all of them at once; keyed by starter they see *"5H/2H/6H Starters
changed"*, which is the same granularity matchups get per opponent.

#### Reader-side layout, in order

```
Read First          comboIntro          prose, methodology, notation legend
<Group Title>       comboGroups[0]      TheoryBox cards, prose, inline combos
<Group Title>       comboGroups[1]      …author adds as many as they want
Combo List          comboList           one captioned sortable table per starter
```

#### Editor sub-tab strip, mirroring `overview-nav-*`

```
[ Read First ] [ Combo List ] [ True Combos × ] [ Advanced Combos × ] [ + Group ]
```

Same `daw-tab-btn` strip, same removable-extra affordance, same single swapping
container. `combos-nav-intro`, `combos-nav-list`, `combos-nav-group-<idx>`.

#### Which leaves exactly two new block types

Everything above is containers this site already has. The genuinely new work is
two entries in the block registry, both subject to the six-site checklist:

1. **TheoryBox card** — title, one-liner, difficulty, video, recipe *(notation,
   not controller input — see the naming trap)*, prose body. Lives inside a
   group.
2. **Combo table** — the sortable table. `comboList` is built from these.

Plus the **Legacy Combo Block restyle**, which is the inline form used *inside*
groups.

### The combo row schema, in our field names

Adapted from the reference rather than copied. Reference name → ours, with the
reason where they differ.

```js
{
  sequence:    ["M1 (X3)", "MURMURATE", "R↑", "DIVE BOMB"],  // free text steps
  position:    "…",              // OPEN — see below, 2D vocabulary may not fit
  damage:      "38-46",          // string. ranges are real: 38-46 is live today
  ultGain:     "12%",            // optional  ┐ owner's two resources, replacing
  evasiveGain: "-20%",           // optional  ┘ Tension / Blood / Stamina
  worksOn:     "Everyone",
  difficulty:  "Medium",         // five levels
  notes:       "…prose…",
  setup:       "…",              // optional, rendered only when present
  video:       "https://…",
  controls:    "…",              // OPEN — see below
  gameVersion: "1.4"             // shared with feature 12
}
```

**`sequence`, not `combo`.** The legacy block already stores
`sequence: [step, …]`, and the screenshots show contributors writing steps that
way. Reusing the name means both block types share one step format, one
renderer for the chips, and one mental model for whoever is typing.

**`ultGain` and `evasiveGain` replace `tensionGain`/`blood`/`stamina`** — the
owner's answer. Same mechanism as the reference: optional named fields rendered
as bold prefixes above the notes prose, not columns of their own.

**`gameVersion`, not `checkedVersion`** — because it is the same field as
feature 12's tier-list Game Version. One vocabulary, defined once, or a tier
list and a combo table will disagree about what a version string means. It
should carry the reference's freshness behaviour too: compare against the
current game version and mark stale rows, which is what makes that column worth
having on a wiki whose game keeps updating.

**The Recipe naming trap, resolved.** The reference uses `Recipe` for two
different things. We use neither:

| Reference | Ours | Why |
|---|---|---|
| TheoryBox `Recipe` (the notation) | **`sequence`** | it *is* a combo, so it shares the legacy block's field |
| Table `recipePC` / `recipePS` | **`controls`** | it is a control scheme, and the word says so |

#### Three domain questions the reference cannot answer

- **`position` — do the 2D values even apply?** The reference uses Anywhere /
  Corner / Midscreen. **JJS is a 3D arena game on Roblox**, and `CLAUDE.md`
  warns explicitly against assuming dustloop conventions map across. Nothing in
  the owner's screenshots mentions position at all, while the Choso examples
  do mention *"In the Air"* and *"Jump on top of enemy"* — which suggests the
  real axis is **ground/air**, not corner/midscreen. **Ask before building
  this field.** It may want different values, or may not exist.
- **`difficulty` — is Very Easy … Very Hard the right five?** The reference's
  scale. None of the owner's live pages show a difficulty at all, so this is
  adopted rather than confirmed.
- **`controls` — does JJS need it?** The reference splits PC and PlayStation
  recipes. JJS's inputs *are* keyboard, and Roblox also runs on console and
  mobile. If the audience is overwhelmingly PC this column is dead weight and
  should be cut rather than shipped empty.

### Answers, and two corrections to the design above (2026-08-16)

**`position` matters MORE in 3D, not less — and it is a FREE STRING.** Owner:
being near a wall opens combo routes, and some characters need distance to farm
resource safely; position "can get complicated in JJS", so it is not reducible
to an enum or a tag set. **Settled: free text.**

Two consequences, both acceptable: it sorts as text — which still groups
identical positions together, just without a meaningful order — and it cannot
be validated or colour-coded, which is the correct trade for a field whose
vocabulary the game has not finished inventing.

**`difficulty` has EIGHT levels**, owner's own scale:

```
Very Easy · Easy · Medium · Slightly Hard · Hard · Very Hard · Extremely Hard · Demon Time
```

Two consequences worth catching now:

- **It must sort by ordinal, never alphabetically.** "Demon Time" sorts *first*
  alphabetically and *last* by meaning. Same trap as any ordinal enum, and the
  sort key has to be the index in that list.
- **Difficulty and inputs are two different colour problems.** Inputs are
  *categorical* — M1 and Skill 1 have no order, so they want distinct hues.
  Difficulty is *ordinal* — it wants a **ramp** where adjacent steps look
  adjacent. Eight distinguishable categorical colours on a dark background is
  close to impossible; eight steps along a ramp is routine.

**`controls` ships, but as a conditional column.** The owner wants it for
console players even though the audience is mostly PC. The reference already
solves the empty-column problem: `Setup` renders *only if a row supplies it*
(`{{#if:{{{setup|}}}|…}}`). Apply that to `controls` too — the field exists
always, the column appears only once someone fills one in, so it costs no
horizontal space on a ten-wide table until it earns it.

#### Correction 1: the combo table is NOT a block type

Recorded earlier as one of "two new block types". Wrong. `comboList` is
`[{ starter, rows }]` — a **keyed array with its own renderer**, which is
exactly what `matchups` and `counterplay` already are. Neither of those is a
block. So the table needs a renderer and an editor panel, like matchups, and
**nothing in the block registry at all**.

#### Correction 2: TheoryBox nests, and there is already a precedent

I assumed blocks could not contain blocks. They can —
`accordion: { type, title, content: [blocks] }` is in the registry today, and
`window.activeAccordionPath` exists for *"RECURSIVE EDITOR PATH TRACKING"*.

So **TheoryBox is "accordion with more fields"**, and the recursive editor
machinery it needs already works:

```js
theorybox: {
  type: 'theorybox',
  title: 'New Combo',
  oneliner: '',
  difficulty: '',
  sequence: [],        // the route — same step format as the legacy block
  damage: '',
  video: '',
  content: [ … ],      // nested blocks, exactly like accordion
  anchor: '',          // derived from title when blank
  align: 'left',
  author: ''
}
```

Layout takes the reference's four-area grid — Title | Difficulty over
Content | Video, two columns above 900px, stacked below — with our own chrome.
Note the reference renders difficulty with `noNumber=true` on the card and with
the number in the table, so the same value reads differently in the two places.

**So the real total is one new block type, not two.**

### The combo table: sorting and mobile

**Two sort keys must be explicit, or the column lies.**

| Column | Sorts by | Why not the obvious way |
|---|---|---|
| Damage | leading integer parsed from the string | `"38-46"` and `"4 (2+2)"` are live values; lexical order puts `"4 (2+2)"` above `"38-46"` |
| Difficulty | index in the eight-level list | alphabetical puts Demon Time first and Very Easy last |

Everything else sorts as text. `Video`, `Controls` and `Ver` stay unsortable,
as in the reference.

**Mobile is the open design problem.** Ten columns will not fit. The reference
gives Combo and Notes `min-width: 250px` and lets the table scroll sideways,
which is a poor fit here — this site has had a deliberate mobile pass and
already collapses matchup cards rather than scrolling them. **Proposed: below
the breakpoint each row becomes a card** — the route on top, then the fields as
a compact definition list, notes underneath. That matches what matchups already
do on mobile and keeps the route readable, which is the only part that must be.

### The tab vocabulary module

Everything above depends on this, and it is small.

**One definition.** `window.CHARACTER_TABS` in `js/site_meta.js`, alongside
`FRAME_COLORS` and `CHARACTER_ALIASES` — an ordered list of
`{ id, label, classes }`, which is already the shape `page_router.js`'s
`DEFAULT_CHARACTER_TABS` uses. `page_router` then reads the global instead of
its own literal, and `route.tabs` stays the per-page override it was built as.

**Then replace all ~17 hardcoded lists with it**, including the four variants
that have already drifted apart over `ultimateAtk` and `gallery`.

**And a test that stops it happening again.** `scripts/page-types.js`'s own
header says the right shape: derive the expectation rather than restate the
list. Here that means a source-reading spec asserting **no file outside
`site_meta.js` contains a literal character-tab array** — the same technique
`migration-columns.spec.js` and `regenerate-workflow.spec.js` already use. A
restated list is exactly how the drift happened the first time.

### The Legacy Combo Block restyle

Three fixes, each taken from a specific thing visible in the owner's
screenshots rather than from a general sense that it is too big:

1. **Chips are oversized**, so a long route wraps across rows and loses its
   shape — the 76-damage Crow Charmer combo wraps to two lines mid-route.
   Reduce padding and font size so a typical route holds one line.
2. **Damage sits far right, detached** from the route it belongs to. Bring it
   adjacent — a trailing element of the route, not a column at the page edge.
3. **The note floats beside the damage** rather than under the combo. Put it
   below the route, full width.

Plus the original complaint: **the step text becomes monospace**, because
alignment is meaning in a combo and Finger-Paint destroys it.

### Item 14: what is still undecided, and what is merely unbuilt

The design is complete enough to build from. What remains is short and split
into things only the owner can answer and things a builder can settle.

**Needs the owner:**

- **The input colours.** Ten categorical hues, distinguishable on the dark
  theme and ideally distinct from `--accent-blue`, which already shifts per
  character.
- **The difficulty ramp.** Eight ordinal steps. A ramp, not eight categories.
- **Whether `1 2 3 4` share a family hue** (four shades of one colour, reading
  as "a skill") or are fully independent.

### Resolved: portraits are mirrored into the repo (2026-08-16)

`scripts/fetch-portraits.js` mirrors every portrait in `page-previews.json`

### The four answers

**Create Tier List delivers to the clipboard, not a download.**

That does **not** remove the blocker, and the item should not be scoped as if
it does. `navigator.clipboard.write()` needs a `Blob`, the `Blob` comes from
`canvas.toBlob()`, and a canvas tainted by a cross-origin portrait throws
`SecurityError` at exactly that call. The CORS question is unchanged: every
portrait needs `crossOrigin="anonymous"` *and* the right
`Access-Control-Allow-Origin` from Supabase Storage. **Spike that before
scoping the rest.**

Clipboard is still the better UX, but it needs a download fallback — Firefox
and Safari have lagged on image writes through `ClipboardItem`, and this site's
own bug reports come from Firefox and Edge users.

**User flair: 30 characters, emoji allowed, no special characters, no slurs or
political/sensitive content.** Three things that follow:

- Allow-list the character set (letters, digits, spaces, `\p{Extended_Pictographic}`)
  rather than block-listing punctuation. "No special characters, emoji fine" is
  not expressible as a blocklist.
- **Count grapheme clusters, not `.length`.** One ZWJ emoji is up to 11 UTF-16
  units, so a naive 30-character check rejects a single emoji. `Intl.Segmenter`.
- Word filtering must be **server-side** — a client list is bypassable by
  calling REST directly — and no wordlist is complete, so flair must also be
  reportable through the existing moderation queue. The list is a speed bump;
  the queue is the actual control.

**A private profile is visible to the owner and to holders of a new
`can_view_private_profile` capability**, which is deliberately *not*
`can_moderate`. This needs no new mechanism: it is another boolean on
`user_roles` beside `bypass_cooldown`, `can_moderate` and `can_delete_media`,
following the v0.13 pattern exactly. RLS reads: not private, OR it is your own
row, OR `get_my_role()` is `'admin'`, OR the caller holds the capability.

**Usernames are being added, and `media_uploader` keys on `user_id`.** The
owner's reasoning — a raw id is a poor thing to display — resolves into the
standard split: a unique `username` for display and addressing, a free-form
`display_name` that can change, and `user_id` as the only thing stored on other
tables. Uploader credit then resolves at read time and never goes stale.

**One migration cost to plan for:** every existing account needs a username
backfilled, with a collision strategy. That is the part of the profile system
most likely to be underestimated.

## Item 0 SHIPPED: the tab vocabulary, and two new tabs (2026-08-16)

**Character pages have two new tabs, Combos and Starter Guide.** They are empty

The point of doing this first was that adding them should be *one* change. It

### The claim in the plan was wrong, and the correction matters

The plan said the tab list was hardcoded at ~17 sites in ten files and had
**drifted into four variants**. Reading the actual sites: nothing had drifted.
Every variant was a deliberately different subset, and most carried a comment
explaining itself.

| Variant | Why it is correct |
|---|---|
| 6 tabs, `admin-*.js` | admin.html genuinely has no Ultimate button — `admin-modes.js` injects it |
| 7 with `ultimateAtk`, `editor-tabs.js` | edit.html **does** ship that button, hidden, un-hidden by `editor-modes.js` |
| 7 with `gallery`, `character_modes.js` | on the reader page Gallery is a real tab |
| `gallery` absent from every editor list | it has no editor at all |

So the real problem was never drift. It was that **the correct answer differed
per site and nothing checked it** — the failure mode is what adding two tabs by
hand would have *created*. That changed the design: a flat `{id,label,classes}`
array cannot express it, so the module carries the attributes each consumer
derives its subset from (`editable`, `frameMoves`, `modeScoped`, `injected`,

*before* `site_utils.js` and `site_meta.js` by design, so the vocabulary would
have been `undefined` at exactly the moment the tabs are built. It is a
standalone dependency-free file loaded first on all 43 pages.

That made it the **second genuinely shared module**, which falsified the
stamper's stated invariant that `site_utils.js` was the only one. Both are now
stamped with one hash covering both, so the pair can never be served
half-fresh — precisely the 2026-08-10 bug that script exists for.

1. **Seven `FRAME_MOVE_CATEGORIES || ['m1s','skills','specials']` fallbacks
   listed three categories against the real four.** Had any fired, a base-only

2. **`history.js` had no `ultimateAtk` entry**, so a base-only character's

## Item 1: the combo block, restyled — and the stored XSS underneath it
(2026-08-16)

**Combos read as one line again**, in monospace, with the damage next to the
route and the note underneath it instead of stranded at the page edge.

The restyle is the small half. Opening that renderer turned up a live stored
XSS, and the owner chose to fix it here rather than as a separate hotfix.

### The hole

`js/description.js` wrote every contributor-authored value straight into
`innerHTML`. A combo step of `<img src=x onerror=…>` executed:

- for every reader of the page once approved, **and**
- in the **reviewer's authenticated session** the moment they opened the
  preview — which needs no approval at all.

Any signed-in user could reach the second one, and a reviewer's session can
approve revisions. The diff view was safe (`diffTextLCS` escapes both inputs);
the preview was not, and the preview is what a reviewer actually reads.

Proven with a real repro before touching anything: three fields fired, three
elements injected. Not inferred from reading the source.

`js/editor-blocks.js` had the same problem in **attribute** context —
`value="${…}"` unescaped at 24 sites, reachable by a reviewer intercepting a
ticket into the editor.

### The claim that had to be disproved first

`tests/author-badge-escaping.spec.js` **asserted the opposite**, in a test
written to prevent exactly this change: *"block content is rich HTML on
purpose … escaping those would break every formatted page on the site."*

That was wrong, and it was load-bearing wrong — it left the hole in place and
guarded it. Three pieces of evidence, in order:

1. **A scan of all live content: 33 pages, 75 combo blocks, and zero `<`
   characters in any contributor string.** Nothing depended on the behaviour.
2. **The editor emits BBCode, not HTML.** `applyFormat` writes `[b]…[/b]`,
   `[color=#f00]…[/color]`, `[url=…]…[/url]`, and `internalstyling.js`
   converts them over the rendered DOM. HTML escaping does not touch square
   brackets.
3. **Verified end to end**: after the fix, `[b]` still becomes `<strong>`,
   `[color=]` still colours, `[M1]` still becomes a `<kbd>`,
   `[url=javascript:…]` is still stripped by the existing `safeUrl` — and
   `<b>literal</b>` is now shown as text.

The bold and colour visible on a live character page were never stored markup;
they are `internalstyling.js` working on the DOM. The old test's premise never
matched the editor that shipped.

### Three contexts, three rules

Escaping alone is not enough everywhere, and treating it as if it were is how
half-fixes happen:

| context | rule |
|---|---|
| text | escape |
| attribute | escape — it covers both quote characters |
| **CSS value** | **allowlist.** Escaping quotes stops an attribute breakout but leaves `100%; background: url(…)` intact, so `align` and `width` are validated |
| **tag name** | **allowlist.** `block.size` lands in the tag itself, where escaping does nothing |
| **URL** | **scheme check.** `javascript:` is not an escaping problem |

### I broke the entire editor doing it, and the test caught it

Naming the helpers `esc` and `safeUrl` collided with `js/editor-blocks.js`,
`js/dashboards.js`, `js/post-editor.js` and `js/internalstyling.js`. Every
`js/` file is a classic `<script>` sharing **one global lexical scope**, so a
duplicate top-level `const` is a SyntaxError that **aborts the whole second
file**. `initStrategyBlockBuilder` was never defined and `edit.html` died with
*"Editor failed to initialize context"* — the same symptom as the 2026-08-10
cache-skew incident, from an unrelated cause.

It was caught only because the spec drove the real `initStrategyBlockBuilder`.
**The first version of that test built its own `<input>` with `escapeHtml` and
passed while the editor was dead** — the identical mistake made on bug 6 in
v0.14, which the `writing-tests` skill already warns about.

`tests/global-scope-collisions.spec.js` now fails on any recurrence. It reads
which scripts each page loads from the HTML, so it needs no maintenance, and
its behavioural half asserts the builders are actually defined — a file that
fails to parse is invisible to every spec that mocks past boot. Falsified by
reintroducing the collision; it named a third one nobody had found by hand.

### The restyle

Three fixes, each from something visible in the owner's screenshots:

1. **Monospace steps.** A combo is notation and alignment carries meaning —
   `M1 M1 M1` should look like three of the same thing. A proportional comic
   face gave the same input a different width every time.
2. **Smaller chips**, so a route holds one line. The 76-damage Crow Charmer
   combo was wrapping mid-route.
3. **Damage beside the route, note beneath it.** Damage was pushed to the far
   page edge with `margin-left: auto` and the note sat beside it, so the note
   read as a caption on the damage rather than a condition on the combo.
   `.combo-meta-group` existed only to hold that arrangement and is gone.

Two specs pinned values that the restyle legitimately changed —
`block-styling-coverage` pinned the font name as a proxy for "styling
applied", which cannot tell a design change from a regression. It now compares
against `--text-mono`.

### Redesigned against the owner's reference (2026-08-16, PR #105 round 2)

The owner supplied the Dustloop reference *after* the first attempt and named
that as the mistake. The restyle above kept its sizing and its damage/note
placement — both were right — and changed the rest:

- **One combo is one box.** The steps were loose chips floating on the page;
  they now share a single surface, the way Dustloop's combo table does.
- **`>` between steps**, not an SVG arrow. It is the notation the community
  and Dustloop both already write by hand.
- **Our box, not theirs**: square corners and a shadow directly below, which
  is the same manga treatment `.btn-manga` uses. Adapted, not copied — the
  owner's standing constraint.
- **Hover moved from the box to the step.** It used to press the whole chip
  down. Hovering one step now fills *that step* with the character's own
  colour, because the route is what is being read.

**The contrast rule is the part with a real failure mode.** Filling with the
character colour and leaving the text white renders Register (100% lightness)
and Aspiring Mangaka (96%) white-on-white. `js/site_meta.js` now sets
`--character-ink` beside `--accent-blue`, using **the same `l < 50` test its
title engine already used** — so the two can never disagree about whether a
character reads light or dark. The default in `Common.css` is black, matching
the site's own 68%-light accent for pages that never run the character theme.

`display: inline-block` was wrong and the screenshot caught it: the box hugged
its route correctly but two combos then sat *side by side*, reading as one
long route. `display: block` with `width: fit-content` gets both.

`tests/combo-block.spec.js` covers the shape and the hover, and picks its two
subjects by sorting the real `CHARACTER_COLORS` dictionary rather than naming
characters — so the extremes follow the roster. Two assertions elsewhere had
pinned things the redesign legitimately changed: a font name, and a border
width used as a proxy for "styled at all".

## Item 2 SHIPPED: the Starter Guide tab (2026-08-16)

**Character pages have a working Starter Guide tab.** Contributors can create
topics, name them, write blocks into them and delete them; the reviewer sees
them in the diff; the reader sees them on the page.

Per the owner, the two Starter Guides are different things and both stay:
`systems/starter-guide` covers the basics, gamemodes and everything a new

### The third copy is where the registry starts

Counterplay was Matchups with the words changed, and Starter Guide would have
been a third copy across ~10 pipeline branches: the submit scan, the merge
compiler, the reviewer's diff, its label map, both renderers, the editor's
sub-nav and the sync flush.

**Missing one of those is silent** — the reviewer approves a ticket whose
Starter Guide edits are never applied, or the contributor's change summary
omits a section they wrote. That is bug 4's exact shape, which cost a release.

So a **keyed section** is now declared once, *on the tab itself*:

```js
{ id: 'counterplay', …, keyed: { keyField: 'topic', scope: 'counterplay',
                                 entryLabel: 'Counterplay', metaField: 'importance' } }
```

Not a second list beside `CHARACTER_TABS`: two lists that must agree are the
problem this module exists to remove.

**Matchups deliberately keeps its own renderer and editor.** Its card links to
the opponent's page and its picker lists the roster — that is a different
screen, not this one with different words, and folding it in would produce a
renderer full of `if (section.tab === 'matchups')`.

**Starter Guide has no `metaField` on purpose.** Matchups carry a tier and
counterplay an importance; the owner asked for Counterplay's *shape*, not for a
second meaning to be invented for that select. Adding one later is one line.

### A real bug the registry exposed

`admin-preview.js` derived the tab id by appending an `s` to the delta scope.
`matchup` → `matchups` works; **`counterplay` → `counterplays`, which is not a
tab** — so opening a counterplay ticket never landed on its own tab and the
reviewer started on Overview. Scope is now declared, never computed.

### Verified against Boomcat, at the owner's instruction

Boomcat has one counterplay topic, 20 matchups and no starter guide — which is
exactly the three states worth checking. After generalising the renderer, its
live page renders **identically**: one card, the same title, the same
`rgb(239,68,68)`, 20 matchups untouched, and the Starter Guide tab showing its
empty message.

### Two things caught by driving the real thing

**`edit.html` had the Starter Guide button and no `#tab-starterGuide` panel**,
so the editor's live preview silently rendered nothing while every other part
worked. The tab-vocabulary guard checked *buttons* for `edit.html` and only
checked *panels* for `admin.html` — its own blind spot. It now checks both.

**A NUL byte in `js/description.js`.** The `javascript:` scheme check's
character class was written with literal control bytes instead of escape
sequences. The code worked, but git treated the file as **binary**, so `grep`
refused to search it and answered "binary file matches" instead of lines. A
file you cannot search is a file whose next bug hides in it.
`tests/global-scope-collisions.spec.js` now rejects control characters in
`js/`.

### Two bugs the owner found by using it (2026-08-16)

They wrote a real Starter Guide topic on Boomcat through Live Server, which is
what turned both of these up.

**1. The tab could not be clicked.** The button was drawn, the panel existed,
the data was merged — and clicking did nothing, with no active highlight.

`js/page_boot.js` registered a **hardcoded id list** with `setupTabs`, written
as `[{ id: 'overview' }, { id: 'm1s' }, …]`. Combos and Starter Guide were not
in it, so `setupTabs` had never heard of them.

Two guards failed to catch it, and both failures are instructive:

- The restated-list scanner only understood arrays of **bare strings**. This
  list was objects, so it walked past. It now flattens `{ id: 'x' }` to `'x'`
  before matching — the same widening the scan already needed for `tests/` and
  for labels.
- The click test drove **only the last tab**, Gallery — which was in the stale
  list, so the single tab it checked was the one tab that could not fail. It
  now drives *every* tab and asserts the others hide.

**2. Every topic card was drawn inside a second card.**

`populateTextSection` wraps its output in its own `<section class="wiki-section">`,
and these previews append that INSIDE a card that is already one. The reader
has stripped the inner class since v0.13; **the editor's preview never did —
for counterplay or matchups either**. It only became visible when Starter Guide
produced an empty topic, where the inner box has no content to distract from
the extra border.

Measured rather than assumed: the editor showed `nested: 1` for all three
sections, the reader `nested: 0`. The owner remembered fixing it for matchups,
and they had — on the reader.

The class is stripped rather than the node unwrapped, because that element
carries the `contextClass` hook (`.counterplay-heading`, `.starterGuide-heading`)
that styles headings inside the card. Asserted on both surfaces now, since they
were allowed to disagree for two versions and this is what that cost.

### The silent last step (owner-reported, 2026-08-16)

The owner created a Starter Guide topic on Boomcat, merged it, got a success
modal — and nothing was written.

**`applyDeltaToData` (js/site_utils.js) had no branch for the scope.** It has
one per scope, and an unrecognised scope fell all the way through to
`return { newDesc, newFrame }` — the data unchanged, no error, no warning.
Starter Guide had a submit scan, a merge-compiler entry, a diff, a reviewer
preview, an editor and a renderer. The one branch that actually *writes* the
value did not know it existed.

**Not the missing key**, which was the natural reading: `if (!newDesc[field])
newDesc[field] = []` has always created it on first insert. There was simply no
branch to reach it. Confirmed against production — Boomcat's live `desc_data`
still had no `starterGuide` key at all.

It also explains the owner's workaround exactly. A **full** submission replaces
`desc_data` wholesale and never calls this function, so it landed; only
*deltas* were dropped. A `multi` payload would not have helped, because the
unpacker recurses into the same missing branch per edit.

**This was a hole in the guard written to prevent it.** The keyed-section scan
covered eight files and not `site_utils.js` — the file that performs the write.
Every other stage was checked; the last one was not.

Two properties now, both falsified against the old code:

1. **Every keyed section survives insert → update → delete**, driven from the
   vocabulary, starting from `desc_data` that has no such key. That first
   insert is the real case: no existing page carries the field, so every
   character's first topic is an insert into nothing.
2. **An unhandled scope is loud.** The `if/else if` chain gained a final `else`
   that logs the scope and says the edit was not applied. A delta that cannot
   be applied must never look like one that was — that property alone would
   have caught this on the first run rather than in the owner's hands.

whole of it - the section above it holds the shape.

### What the registry bought, once it was pointed at the right shape

Every one of the three parts is a shape this codebase already had:

| Field | Same shape as | Scanned by |
|---|---|---|
| `comboIntro` | `overview` / `strategy` | the fixed-section sweep |
| `comboGroups` | `extras` (title-keyed) | `scanKeyedList('comboGroups', 'title', 'comboGroup')` |
| `comboList` | `matchups` (opponent-keyed) | `scanKeyedList('comboList', 'starter', 'comboTable')` |

So submit, merge, diff and apply needed **no new machinery** - two registry
entries and one fixed-section declaration.

**Keying the list by starter is what keeps review readable.** The reference has
127 rows for one character; as a single `'full'` delta a reviewer would face all
of them at once. Keyed by starter they see *"M1 Starters changed"* - the
granularity matchups get per opponent.

**Groups are author-named.** The reference says Beginner / Core / Specialized;
the owner's live pages say True / Simpler / Advanced. Hardcoding the reference's
names would import a vocabulary this community does not use, which is the exact
failure `CLAUDE.md` warns about.

### The registry grew two concepts to fit

- **Sections that render inside a tab without being one.** `comboGroups` and
  `comboList` both live in the Combos tab. Everything downstream keys off
  `scope` and `field`, neither of which cares whether a section is a tab, so
  `tab` now names where a section *renders* - which keeps the reviewer's diff
  able to attribute a change to the Combos tab.
- **`customRenderer` and `customEditor` are separate opt-outs.** Matchups needs
  both. The combo group needs both too, but for a different reason: it is part
  of a document rather than a different screen. Counterplay and Starter Guide
  need neither. This was `tab !== 'matchups'` at five sites before the third
  section made it a list to maintain.

### The two sort keys, both wrong the obvious way

| Column | Sorts by | Why the obvious way fails |
|---|---|---|
| Damage | leading integer | `"4 (2+2)"` sorts above `"38-46"` lexically |
| Difficulty | index in the eight-level list | **"Demon Time" is first alphabetically and last by meaning** |

Both fail *quietly* - a mis-sorted column still looks sorted - so both have a
test. An unrecognised difficulty ranks **last**, not zero: a typo must not
silently become the easiest combo in the table.

`Setup` and `Controls` appear only once some row fills them in, computed across
the whole section rather than per table. Per table, one grew a Setup column and
the next grew Controls, which reads as a bug even though each table was
individually correct.

### Mobile: every row becomes a card

Ten columns cannot fit a phone. The reference scrolls sideways; this site
collapses matchup cards, so a scrolling table would be the one place that
behaves differently. Three things only the render showed:

- **`.combo-table td` outranks `.combo-cell`**, so `display: block` there beat
  the flex rule and the label ran into its value - `DAMAGE38-46`.
- **Empty fields drop out on mobile.** Ten labelled rows saying "-" bury the
  three that were filled in. They stay on desktop, where a column keeps its
  alignment.
- **The video link cannot use `var(--accent-blue)`.** On a character page that
  becomes the character's colour, and Crow Charmer (23% lightness) rendered a
  navy link on a near-black cell.

### The row editor is a modal (owner, 2026-08-16)

Built first as a panel in the editor's left pane, which shares the screen with
the live preview - a dozen fields there was mostly scroll. Fields generate from
`COMBO_COLUMNS`, so a column added to the table appears in the editor without a
second edit. Difficulty is a **select**, because a typo in an ordinal enum sorts
the row to the bottom with nothing saying why. Writes are live on every
keystroke, so closing the modal cannot lose work.

### A silent global collision, and the guard that could not see it

`editor-tabs.js` declared `function renderComboTableBody` while
`description.js` assigns `window.renderComboTableBody`. **A top-level
declaration silently overwrites a window property** - no SyntaxError, nothing in
the console. The reader then called the editor's function with the wrong
arguments and wrote a stray `rows: []` field into a contributor's combo.

`tests/global-scope-collisions.spec.js` only compared declarations against
declarations, so it saw nothing. It now also checks declarations against
`window.x =` assignments, and immediately found three pre-existing shadows:
`history.js`, `recent-changes.js` and `submissions.js` each declare their own
`escapeHtml` over `site_utils.js`'s.

Those four are byte-identical, and per-file duplication is this project's stated
preference, so they are allowlisted - **with a second test asserting they stay
identical**. Harden the canonical one and three pages that render contributor
names would otherwise silently keep the old behaviour.

## Item 4 SHIPPED: the Combo Card (TheoryBox) (2026-08-16)

**A combo group can now hold combo cards**, which is what makes it a combo
group rather than a named container. The owner put it exactly right: without
this, `comboGroup` is structurally identical to a matchup.

A card carries the route and its numbers, then a write-up that is **itself
blocks** - nested exactly like an accordion. That is the whole point: a card
holds its own clips, sub-variants and explanation, and cards nest inside cards,
so a route can carry its own variations without a second block type.

```js
theorybox: {
  type: 'theorybox', title, oneliner, difficulty, sequence: [], damage,
  video, content: [ blocks ], anchor, align, author
}
```

### Six sites, and the two that hurt

A new block type costs six sites in four files:

| File | Role |
|---|---|
| `editor-blocks.js` | registry default shape |
| `editor-blocks.js` | the picker button |
| `editor-blocks.js` | the editor form |
| `description.js` | the reader-facing renderer |
| `admin-preview.js` | **the reviewer's preview** |
| `editor-sync.js` | **draft sync** |

Miss the last two and the block renders for readers but is invisible to the
reviewer approving it, or is silently lost on sync. Both only ever run inside a
reviewer's session or a background save, which is why they are the easy two to
forget and the hard two to notice. `tests/theorybox.spec.js` asserts all six
from the file list rather than by rendering, because rendering only proves four.

### Details worth keeping

- **The route is an ARRAY**, edited one step per line, sharing the field name
  and the chips with the legacy combo block and the Combo List. A combo reads
  identically in all three places. Blank lines are dropped rather than becoming
  empty chips.
- **Difficulty reuses the table's ordinal ramp** by slot index, so the same
  value looks the same on a card and in the list.
- **The anchor is derived from the title when blank**, reduced to letters,
  digits and hyphens. It lands in an `id` attribute, so a raw title would both
  break the selector that scrolls to it and let a quote manufacture attributes -
  asserted with `" onmouseover="` as the anchor.
- **The video link does not use `var(--accent-blue)`**, for the third time in
  this version: on a character page that is the character's colour, and the
  dark ones are unreadable on a dark card.

### Applied three times in one session, and caught by counting

The patch script that adds the six sites was re-run after a failure partway
through, and the assertions that should have stopped it were on the *later*
edits, not the earlier ones. Result: three copies of the registry entry, three
picker buttons, three editor forms - and the reader renderer still missing.

Caught by counting occurrences rather than by reading the diff, then fixed by
restoring the one file to HEAD and applying once. Worth remembering: a
"patch if absent" script needs its guard on **every** edit, not just the one
being debugged.

### Groups are sections, and the builder belongs to a card (2026-08-16)

Three corrections from the owner, all connected:

**A group is a heading, not a card.** Wrapping it in `.wiki-section` made every
combo card a card inside a card, when the cards are supposed to *be* the
sections. The reference agrees: `==Beginner Combos==` is a heading and the
boxes under it are the combos.

**Read First keeps its card.** It is a mandatory prose section like Overview or
General Strategy - it holds paragraphs, not cards, so nothing inside it needs
to be its own section. Only the groups needed the wrapper removed, and stripping
both was over-applying the correction.

**No block toolbar until a card is selected.** The group editor mounted the
block builder on `group.content` directly, which offered an ADD BLOCK with
nothing to attach a block to - and a block added there became a *sibling* of
the cards rather than part of one. A group's editor is now a list of cards; the
builder appears when one is open and edits that card's write-up.

That last one also fixed a real data bug in the tab-level flush, which wrote the
open buffer onto `group.content` - replacing **every card in the group** with
the open card's write-up.

### The suite started reading the owner's live content

Three tests failed after the owner wrote real combo data onto Boomcat through
Live Server. All three assumed the thing they had just created was index 0:
`comboGroups[0]`, `comboList[0]`, and the nav strip being exactly the fixed two.

Boomcat is the owner's real page and the specs load it live, so indexing from
the front reads *their* content and compares it against the test's input. Each
now reads the index it actually opened (`currentCombosSection`,
`currentComboTableIndex`, `currentComboCardIndex`) and asserts the fixed
entries *lead* the strip rather than being all of it.

This is `never pin tests to owner content` in a shape that had not come up
before: not a hardcoded count, but an assumption that a fresh page is empty.

## Notation colouring: the ten input slots (2026-08-17)

**Combo notation is coloured by input.** A route reads M1 in light red, Skill 1
in light yellow, and so on through the ten the owner specified - in a combo
chip, in a Combo Card's route, and in ordinary prose.

### Derived, not authored

The owner's idea was a per-character `characterSettings` map of move name to
input. Right instinct, and the reason it is needed: **JJS combos are written
name-first** - "MURMURATE > R^ > AIR UPDRAFT", not "2 > R > 1" - so colouring a
route means knowing which slot each NAME belongs to.

But that mapping already exists. Every move in `frame_data` carries an `input`.
A hand-written map beside it would be a second copy of the same fact, drifting
the first time someone edited a move - the failure this version has already
paid for twice.

Measured against the live roster before deciding, not guessed:

| | moves | |
|---|---|---|
| resolve from `input` alone | 396 | 76% |
| multi-key | 33 | `Space + M1`, `Air + 1 Key`, `R into Any 4 Keys` |
| no input at all | 90 | Star Rage's entire kit is `''` |

So the map is **derived**, and `desc_data.characterSettings` is a thin override
for the two things derivation cannot do: filling a blank `input`, and community
shorthand ("Garuda" for "Garuda Stab").

**The 90 blanks are a frame-data gap, not a reason for a second map.** Those
moves show no input on the frame-data page either - filling `input` fixes the
page AND the colouring at once, which is why the override exists but is not the
primary path.

### The rules that make it work

- **Modifiers are not slots.** `Space + M1` is the uppercut - an M1, not a
  jump. Space and Shift are slots in their own right AND modifiers when
  combined, so a multi-key input drops them and keeps what is left. That alone
  takes the 33.
- **First key wins otherwise.** `R into Any 4 Keys` is R: a move is named by
  the key that starts it, and anything after is what it leads into.
- **Longest match first.** Vessel has both *Cursed Strikes* and *Aerial Cursed
  Strikes*; alternation is first-match, so short-first would leave "Aerial"
  bare.
- **Mode-scoped.** An ultimate state has different skills in the same slots, so
  the same name can be a different colour per state. Derivation per slice gets
  this for free; a flat map could not.
- **A bare number is only a slot INSIDE a chip.** "1" and "2" appear in prose
  as frame counts and damage far more often than as inputs, so keys match only
  when a chip is entirely one, and move names match anywhere.
- **Unknown text stays uncoloured.** Contributors write `(X3)` and
  `(PICK THE ONE YOU USED)`. Guessing a colour for those is worse than none.

### The outline took three attempts

Always-on, per slot - owner's call, since an outline's job is to keep the text
readable against whatever is behind it.

1. **Four hard 1px shadows.** At 0.75rem bold monospace that closes the
   counters inside the glyphs: "FLOCK" in dark gray rendered as a white
   lozenge.
2. **A blurred halo.** Legible, but a bright blur on a dark page reads as the
   text *glowing* - the owner caught it immediately, and only on the
   light-outlined slots, because a blurred black halo on a dark background is
   invisible either way.
3. **A stroke painted BEHIND the fill** (`paint-order: stroke fill`), 1px. The
   letter keeps its full weight and the outline sits entirely outside it. The
   hard shadows stay as the fallback for anything without `paint-order`.

The lesson is the same one the combo table taught: this was only ever visible
by rendering it and looking. None of the three attempts differ in any assertion
a test could make.

### The notation writing standard (owner, 2026-08-17)

Settled so the guide the owner is writing and the engine describe the same
thing. **Every rule below already works** - it was measured before being
written down, not specified and then built.

```
<Move Name>                  one input          Murmurate
<Move Name> (<variant>)      named variant      Impetus Updraft (Use Twice)
<Move Name> (<inputs>)       combination        Combination (4+1)
<key>                        bare input         M1 · R · 2
<key><direction>             with a direction   R↑
```

Three separators, each with one job:

| | |
|---|---|
| `>` | between STEPS |
| `+` | between the INPUTS OF ONE MOVE - `4+1`, `1+1` |
| `,` | between ANNOTATIONS - `(Upward, Cancel Murmurate)` |

And the rules that follow:

1. **Repeating a key is still that one slot.** `(1+1)` is Skill 1 twice, not a
   combination - `resolveInputSlot` dedupes, so "1 + 1" resolves to 1 and
   always did.
2. **Different keys are a real combination**, and each input carries its own
   colour inside the parenthetical: `(4+1)` renders 4 orange and 1 yellow.
3. **A combination's NAME takes the FIRST input's colour** - owner's call:
   *"it is the input you need to put in first before doing the other to do the
   variant"*. That is also what `resolveInputSlot` already returns, and it
   matters for the reader: a plain name among coloured ones reads as
   *unrecognised* rather than as *deliberately neutral*.
4. **Anything in parentheses that is not a move or a key stays plain** -
   `(Use Twice)`, `(Charged)`, `(Miss)`.

Measured, per step, on a real page:

| written | result |
|---|---|
| `Impetus Updraft (Use Twice)` | name slot 1, "Use Twice" plain |
| `Impetus Updraft (1+1)` | name slot 1, both `1`s slot 1 |
| `Combination (4+1)` | `4` orange, `1` yellow |
| `Combination (2+R)` | `2` blue, `R` magenta |
| `Circling (Charged)` | name slot 2, "Charged" plain |

**The engine follows the published rule, not the other way round.** If the
owner's guide settles on something different, the engine moves.

## Item 5 SHIPPED: in-page section links (2026-08-17)

Mentioning "The Triple Drill Tech" in a Skill write-up now links to the Tech
section of the Overview tab, and the writer picks it from a list rather than
typing an anchor.

### The premise in the list was wrong, and it was the whole item

The plan said this item "shares TheoryBox's anchor mechanism" and that **"the
ToC already resolves these targets"**. It did not, in three ways, and each one
was load-bearing:

1. **Ids were positional.** `refreshTOC` minted `toc-<slug>-<index>`, where the
   index was the heading's place in the *active tab*
   (`js/pagebuilder.js:891`, before this). Insert one section above a target
   and every id below it renumbered, so a link stored in page content rotted
   silently — and **item 8 of this same version makes reordering sections a
   feature**, which would have broken every such link on purpose.
2. **Only the open tab got ids at all.** `refreshTOC` scopes to
   `div[id^="tab-"]:not(.hidden)`, so a link from Skills into Overview pointed
   at an element that had no id until the reader happened to open Overview
   first — precisely the case the feature exists for.
3. **Nothing read `location.hash`.** Site-wide, the only reader was
   `js/discussions.js:819`, for a thread deep link. A section link pasted into
   Discord landed at the top of the page.

So the item was not "wire up the existing anchors". It was "build the anchor
system, then wire it up". Worth recording because the *estimate* was wrong for
a reason that repeats: the plan described a mechanism by the job it appeared to
do, not by what the code does.

### What it costs to be stable

Ids now come from the heading's own text (`sec-triple-drill-tech`) and are
assigned across **every** tab, open or not. Duplicates — two sections both
called "Notes" — are numbered in document order, so a rename elsewhere on the
page does not disturb them.

`jumpToAnchor` is the resolver. It crosses a tab by **clicking the real button**
rather than un-hiding the panel, so the strip's own bookkeeping runs exactly as
it does for a reader; it opens any `<details>` above the target, because
scrolling to a heading inside a closed accordion lands on nothing; and it
returns `false` rather than throwing when the target is absent.

**It deliberately does not cross a character STATE.** Modes re-render the tabs
rather than hiding a parallel copy, so a section in the other state is not in
the DOM to be found. Reachable later via `?mode=`, but it needs to know *which*
mode holds the target, and nothing records that today.

Arrival by hash is **retried, not resolved once** — the two boot branches differ
in their timing on purpose (character pages fire concurrently with a 500ms ToC
delay, system pages await in order with 150ms), so a single attempt at
`DOMContentLoaded` would catch neither.

`[url=#…]` needed no new vocabulary: `safeUrl`'s allowlist already passed a
fragment. It only needed to stop opening in a new tab — a second copy of the
page scrolled to a section is not what "jump to the Tech section" means.

### The picker had to read data, not the DOM

The editor renders only the tab being edited. A picker built from the preview
could offer links within the current tab and nowhere else — the exact opposite
of the feature. `collectSectionTargets` walks `desc_data` through the **item 0
registry** instead, so Combos and Starter Guide were free and the next tab will
be too. Item 0 has now paid for itself three times.

### Asserting all of them, rather than one, found the bug

The test that mattered checks that **every** id the picker offers is one the
reader's page actually renders. It failed immediately: a matchup heading is
`vs. Crow Charmer` (`js/description.js:1348`), so all twenty of Boomcat's
matchups were offered under an id resolving to nothing.

Checking the *first* entry would have passed — it is Character Overview, which
was always fine. The prefix is now declared on the registry entry
(`headingPrefix`), not special-cased in the collector, so the renderer and the
picker cannot drift apart again.

### A stale asset hash, caught as flake

`character_tabs.js` is content-stamped into every page's script tag. Editing it
without `npm run generate` leaves the browser free to serve the previous copy —
which showed up as an intermittent `collectSectionTargets is not a function`
across test workers, and read as ordinary parallel-run flake.

It is not flake. On the live site it is the **GitHub Pages cache-skew** case
that took the editor down in v0.12, and it would have shipped as a feature that
silently did nothing for up to an hour after deploy. `npm run validate` catches
it; the lesson is that an intermittent failure deserves a cause before it
deserves a re-run.

### Two gaps the owner found by using it (2026-08-17)

**Moves were not linkable at all** — M1s, Skills, Specials, Ultimate. On a
fighting-game wiki that is most of what anyone would want to link to.

The reader page was already fine: `js/framedata.js:286` renders each move card
as `<h2 class="skill-title">`, which is in the anchor selector, so
`sec-explosion` existed and resolved. The *picker* had no idea, because a
move's **name lives in `frame_data`** and only its write-up is `desc_data`
(`moveStrategies[moveId]`). `collectSectionTargets` now takes both.

**The picker is now two levels**, like the ToC — sub-headings nested under
their section behind a caret. It departs from the ToC in defaulting to
**collapsed**: a filled-in character page carries well over a hundred headings,
and this control exists to find one, not to be read through. Searching a
sub-heading expands its parent, since collapsing the only match would hide the
thing just found.

### Checking one direction proved nothing

The first version's strongest test asserted that **every id the picker offers
resolves on the page**. The picker satisfied that completely while offering no
moves whatsoever — it was internally consistent and simply blind to a third of
the site.

Adding the other direction — **every anchor the page renders is also offered** —
caught the rest at once: the Combo List's own heading
(`js/description.js:865`) and the Discussion section. Both are now *declared*
rather than special-cased: `containerHeading: true` on the registry entry, and
a `STRUCTURAL_SECTIONS` list for page furniture that is not editable content.

The general shape, worth keeping: **a consistency check between two derivations
only finds drift in the direction it looks.** "Everything I offer is real" and
"everything real is offered" are different claims, and the second is the one
that finds an omission.

Also stops `"Move Overview and Strategy"` taking an id. It renders above every
move's write-up, so a tab with four M1s had four of them, naming nothing and
consuming the numbering a genuine duplicate would be counted by. The ToC has
skipped it by name since long before this; both sides now read one list.

## Item 6 SHIPPED: Diff View renders every edit type (2026-08-17)

A reviewer now sees what a ticket changes, in language naming a place on the
wiki, with combo notation coloured the same way a reader sees it.

### Seven scopes rendered nothing at all

Measured before building, by running **every scope `applyDeltaToData` accepts**
through the real renderer and counting what came out:

| scope | before |
|---|---|
| `comboIntro` | heading, no diff |
| `comboTable` | heading, no diff |
| `gallery_item` | heading, no diff |
| `gallery_intro` / `intro` | heading, no diff |
| `notes` | heading, no diff |
| `tool_config` | heading, no diff |

A reviewer cannot tell "a heading with nothing under it" apart from "nothing
changed here". **Approving one of those meant approving changes they were never
shown** — the same shape as the merged-ticket bug in v0.14, and worse, because
this was the steady state rather than an edge case. Every one of those tickets
*applied* perfectly; only the review was blind.

The structural cause: `renderDeltaDiff` had no final `else`, so a scope without
a branch fell out silently. **There is one now**, and it says out loud that the
raw view is a fallback and the change is still real. A poor diff beats a blank
space; a blank space only beats nothing if you know it is one.

`comboTable` was a different fault with the same symptom — its entries hold
`rows`, not `content`, so the shared keyed branch compared two empty arrays and
returned before rendering. Rows now diff position by position, named by their
route, because that is how an author recognises a combo.

### Notation was not coloured in Diff View

Reported by the owner. The reader saw colours; **the person approving them saw
plain text** — and the reviewer is the half whose job is to spot a wrong input.

`currentPageMoveSlots()` read `cachedMasterFrameData` and
`currentEditorFrameData`. `admin.html` has neither: it loads a revision into
`currentLive*` / `currentPending*`, so the slot map came back empty and nothing
matched. It now falls back to pending, then live — pending first, so a move the
ticket itself adds also colours.

### Raw JSON, fixed at the source rather than per-scope

`renderStructuredDiff` `JSON.stringify`'d anything that was not a primitive, so
a stat list, an input sequence and a set of combo rows all arrived as one
unbroken brace-filled line. Now: lists of values render as lists, lists of
objects diff item by item, and field names read as words. `worksOn` → "Works
On" comes from a **general rule**, not a lookup, so a field added later reads
correctly without anyone remembering to list it.

### The location label named nothing a reviewer could find

> `Suggested Edit Location: [ COMBOINTRO ➔ FULL ]`

A delta scope and an internal placeholder — neither appears anywhere on the
wiki. Now `Changed: Combos › Read First`. `full` means "the whole section", so
it is dropped rather than printed: there is nothing after the section name to
name.

Also: editing Read First marked **Overview** as the changed tab. Pointing a
reviewer at a tab that did not change is worse than pointing at none — they
look, see nothing, and stop looking.

### Two tests went vacuous rather than failing

Renaming the fields turned two assertions in `admin-structured-diff.spec.js`
into no-ops: they checked that a raw schema key was *absent*, which became true
for the wrong reason. They passed, and tested nothing.

Worth keeping, because it is the counterpart to item 5's lesson. There, a check
in one direction missed an omission. Here, a check written as an absence
survived the change that should have broken it. **An assertion that something
is missing is only as good as the reason it is missing.**

### Two bugs the owner found in the review screen (2026-08-17)

**Every prose diff was rendering as visible markup.** Literal
`<ins class="diff-add">`, `&quot;`, `&#39;` — on character, system and tool
pages alike.

Two correct fixes cancelling each other out. `diffTextLCS` escaped the text and
returned finished `<ins>`/`<del>` tags — right, and safe. Then **item 1 of this
same version** began escaping at every `innerHTML` interpolation in the block
renderer, to close a stored-XSS hole — also right, also safe. The second
escaped the first's tags, and the diff turned into text.

Neither half is wrong. **Nothing tested the pair**, which is the actual gap:
each fix had its own test, and both passed.

The fix could not be an escape opt-out. A flag saying "this content is already
safe" would have to live on the block, and blocks are contributor-submitted —
a crafted payload could set it and walk straight through the hole item 1 just
closed. So `diffTextLCS` now leaves the text **raw** and marks the changed runs
with control characters; the renderer escapes exactly once, as it does for any
content; `resolveDiffMarkers` swaps markers for tags afterwards. Submitted text
carrying those characters is stripped, so a contributor cannot open a tag the
differ never opened.

Two details worth keeping:

- **The early-return paths and the main grouping loop are separate code.** I
  changed the early returns first, which fixed wholly-new blocks and left every
  ordinary mixed edit still broken. There is a test for each now.
- **I wrote the control characters as literal bytes** and had to redo it as
  ``-style escape sequences — the same mistake that made git treat
  `description.js` as binary earlier in this version. The constants carry a
  comment saying why they are written that way.

**And system, tool, gallery and tier list pages kept the old wording.** The
location was baked into each block heading as `[Basic Fundamentals] ➔
Introduction`, so one reviewer read two vocabularies depending on which queue
item they opened, and only the character one named a place. All page types now
share `renderLocation`. The system path also only announces sections that
actually changed — it used to emit a heading for every section of every tab, so
a one-word edit produced a wall of headings with nothing under most of them.

### The XSS spec moved with the guarantee, rather than being relaxed

`admin-difftextlcs-xss.spec.js` asserted that `diffTextLCS`'s return value
contained no raw HTML. Under the new design its output is raw **by design**, so
that assertion had to change — and the tempting move, weakening it, would have
quietly deleted the only coverage of a real past vulnerability.

Instead the tests now drive the whole pipeline — escape, then resolve — and
assert what the reviewer's browser actually ends up with: no element is ever
created from submitted text, and the only tags present are the diff's own. That
is what was ever really at stake; the intermediate string never was.

**When a fix moves where a guarantee lives, the test moves to the new place. It
does not get relaxed to match the new internals.**

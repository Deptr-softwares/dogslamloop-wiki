## Media moderation, as the owner scoped it (2026-08-11)

**The bucket, measured 2026-08-11:** 198 files, 346 MB, average 1.8 MB, largest 14 MB.

| type | files | total | avg each |
|---|---|---|---|
| video/mp4 | 36 | 194 MB | **5.4 MB** |
| video/webm | 130 | 151 MB | **1.2 MB** |
| image/webp | 32 | 716 kB | 22 kB |

Three decisions fall out of that:

- **The 15 MB cap stays.** Owner's call: revisit when Supabase actually warns, not before. Noting only that storage has a clear line you get told about while egress scales with *readers* rather than uploads, so that is the number to watch when the wiki is linked from the Discord.
- **The format is the lever, not the cap.** mp4 is 18% of the files and 56% of the bytes; a WebM here averages 4.6x smaller. 130 of 198 files are already WebM, so the workflow is known - the recent mp4 surge is the new content team still learning the tooling. `uploadWikiMedia` already converts images to WebP and deliberately leaves video alone; it does not need to transcode, it just needs to *say* at upload time that a WebM of the same clip is usually 4-5x smaller. Much cheaper than policy, and it targets the actual bytes.
- **The review queue is a plain list.** 198 items needs a filter (unchecked / flagged) and a sort, not paging or infinite scroll.

**Everything currently in the bucket is already approved.** The owner reviewed all 198 files on 2026-08-11 and confirmed them good. The migration that introduces the queue must seed them as checked - a single `INSERT ... SELECT` from `storage.objects` at migration time, attributed to the owner - rather than opening the feature with a 198-item backlog that has already been cleared. An implicit "anything older than this timestamp is fine" rule would work too but leaves nothing to audit later; explicit rows cost nothing at this size.


Deliberately light. Unchecked media stays fully usable and visible; a review queue in admin lists what nobody has looked at yet; reviewers and the owner work through it; a flagged item becomes unrenderable. Deletion is the owner's alone, possibly extended by a capability column rather than a new role.

Three things to settle, from a first look at the current code:

- **`runMediaGC` in `js/owner.js` can delete the whole bucket.** It destructures three queries without checking their errors, so a failed select yields an empty reference string and every file reads as orphaned — reported to the user as "Deleted N orphaned files". Today an admin confirm stands in front of it. It must not be automated before that is fixed, and it wants a floor: bail on any query error, and refuse when the orphan set is an implausible fraction of the bucket.
- **Automating it needs no Edge Function.** `storage.objects` is a real table, so a `SECURITY DEFINER` function plus pg_cron can do the scan server-side, which also gets the whole-history concatenation out of the browser. Verify first that deleting a `storage.objects` row really removes the file, and that a `LIKE` scan over that jsonb performs.
- **"Unrenderable" is client-side.** A blocked file still sits at its public storage URL. Fine for "get it off the page", not for the case blocking actually exists for — so decide whether blocking also moves or deletes the object.
## Batch added by the owner, 2026-08-11

**10. Make clearing orphaned media safe.** ✅ **Done.** The function is `runGarbageCollector`, not `runMediaGC` — the earlier note had the name wrong.

It built one string from `page_data`, `pending_revisions` and `page_history`, then deleted every bucket file whose name did not appear in it, destructuring those three queries without checking their errors. A failed select contributed nothing, so **every file read as orphaned** — reported as "Deleted N orphaned files" in green. 198 files, 346 MB, one confirm dialog away.

A second, quieter path to the same place turned up while fixing it: PostgREST caps rows per request, and the queries asked for whole tables in one go. A silently truncated read is indistinguishable from a table that genuinely references nothing. `page_history` is the one at risk — it is admin-only, so it is also where a grant regression lands first.

What it does now: error-checks every read and aborts the run on any failure; pages every read (and the bucket listing) to exhaustion with a stable `order('id')`, because an unordered `range()` can drop rows between pages; refuses to treat an empty `page_data` as an empty wiki; separates scanning from deleting, so the scan lists what it found and changes nothing; names the count in the confirmation and says what share of the library it is when that exceeds 25%; and spends the list on use, so a stale scan cannot be re-purged. Deletion reports what was actually removed rather than what was requested.

Name matching is unchanged, and still errs towards keeping files. `tests/media-gc-guard.spec.js` covers it — all 11 cases fail against the pre-fix code, including the two that would have emptied the library.

**11. Multi-file upload in the media library.** ✅ **Done.** One at a time before. The measured evidence for why it mattered: seven raw clips uploaded individually inside fifty minutes on 2026-08-09. `window.uploadWikiMedia` already took a single file and returned `{name, url, width, height}`, so the change is a queue around it plus per-file status — the overwrite guard and the WebP conversion stay per file.

The handler was reading `files[0]` and silently discarding the rest, on both the picker and the drop zone. It now takes the whole list.

**Sequential, not parallel**, and that is a correctness decision rather than a performance one: the overwrite guard reads a snapshot of the bucket, so two uploads in flight together can both pass it for the same name. The WebP conversion is canvas work competing for one main thread anyway.

Three things fell out of doing it as a batch:

- **A rejected file no longer cancels the run.** A duplicate name halfway through ten files used to mean starting over. Failures are collected and reported together at the end, with a per-file row showing state as it goes.
- **The batch needed its own name history.** `uploadWikiMedia` gained an `alsoKnown` parameter: the library's file list is from before the run started, so nothing else knows the run already used `Clip.webm`. Without it the second one gets a raw storage error instead of the guard's explanation.
- **The grid refreshes once at the end**, not per file — a refresh re-lists the whole bucket.

The file input is also cleared after each run, so re-picking the same file after a failure fires a change event instead of looking dead.

**15. MP4 uploads turned off** (owner, 2026-08-12). ✅ **Done.**

An upload gate and nothing more: every MP4 already on the wiki keeps playing, the library still lists them for use on pages, and no renderer changed. The site did not stop supporting the format — it stopped accepting new ones.

The justification is the measurement already in this file: MP4 was 18% of the files and **56% of the total bytes**, averaging 4.6x a WebM. Format is a much bigger lever than any size cap, which is why the 15 MB cap could stay where it is.

Checked on the extension as well as the MIME type. A file renamed by hand arrives with an empty or mismatched type, and a MIME-only check waves it straight through. The rejection message says what to do — convert to WebM, usually 4-5x smaller — rather than only refusing.

**12 and 13. Matchup tiers.** ✅ **Done.** Two additions (Slight Disadvantage, Slight Advantage) and two renames (Unloseable → Dominating, Unwinnable → Hopeless).

The vocabulary is defined in **three** places that must move together: `js/description.js` (live page), `js/editor-previews.js` (editor preview) and `js/editor-tabs.js` (the `tierOptions` array the editor offers). Two independent colour maps and one option list — worth collapsing into one exported constant while touching them.

**The renames are a data change.** Measured across all 30 pages: 380 matchup entries, of which **18 use "Unwinnable" and 14 use "Unloseable"**. `tierColors[mu.tier] || "#ffffff"` means an unrecognised tier silently renders white with the old word still showing, so a rename without a migration quietly degrades 32 real matchups.

Two things follow:

- Migrate `page_data` (a jsonb rewrite of those 32 entries), **but do not rewrite `page_history`** — that is an audit trail, and editing it to say something a reviewer never approved is falsifying the record.
- Which means the renderers need a **legacy alias** regardless — old → new — so history replay and any ticket already in the queue keep rendering. The alias is permanent; the migration is what stops new data using the old words.

One piece of junk data found while counting: a single matchup with the tier `"Aerial Circling tier"`, which is not and never was an option. Worth cleaning in the same migration.

**Verified by simulation, not by Postgres.** The transformation was replayed in Python over all 30 live pages: 8 rows match the `WHERE`, 380 matchups before and after, matchup order preserved in every touched row, no non-tier field altered, 18 → Hopeless and 14 → Dominating. That validates the logic; the SQL dialect itself is unverified until it runs on merge.

Two escaping bugs were fixed in the same statements: `mu.opponent` and `mu.tier` were interpolated raw into `innerHTML` on both the live page and the preview, and the opponent name went unescaped into a `value=""` attribute in the editor. **14. Character and frame-type colours in the editor's colour presets.** ✅ **Done.** The preset row in `js/editor-blocks.js` was seven hardcoded `hsl()` swatches while `window.CHARACTER_COLORS` (js/site_meta.js) and `window.FRAME_COLORS` already existed and already drove those colours everywhere else — the presets simply predated them, so matching a character or a frame phase in prose meant reading a value out of the CSS by hand.

**Owner's choices, 2026-08-12:** grouped rows with labels (over a palette switcher or one flat row), and frame **phases plus i-frame windows** rather than phases alone. So 7 basic + 23 characters + 15 frame/window = 45 swatches, in three labelled groups.

Grouping mattered more than it looks: several characters share a colour (Honored One, Switcher and True Cannon are all the same cyan), so an unlabelled flat row would have shown identical squares side by side with no way to tell them apart. Every swatch now carries its name as a tooltip.

**The parse-time trap was real and is now tested.** `FRAME_COLORS` and `WINDOW_COLORS` are populated by an IIFE reading CSS custom properties, so a module-level constant would have captured empty strings — rendering transparent swatches that apply no colour on click, which looks like a styling glitch rather than a bug. The list is therefore built at render time, and a test asserts the Startup swatch equals what the stylesheet actually resolved to.

Two supporting details: `window.FRAME_COLOR_LABELS` was added next to the colour dictionaries so the picker calls things what the frame-data legend calls them ("InSkill Stun", "Melee I-Frames") rather than inventing wording; and the swatch colours are **whitelisted** against a CSS-colour pattern rather than escaped, because they land inside a `style` attribute where escaping alone would not stop a value closing the declaration.

The popup also had to be resized — it opens upward from the toolbar, so at 45 swatches and 140px wide it ran off the top of the screen and the last group was unreachable.

One existing test needed adjusting: `editor-pr4-dedupe.spec.js` asserted exactly 7 presets. That test is about inline styles being removed, not about how many colours are offered, and the count now tracks the character roster — so it became a floor. Same lesson as the regeneration failure above.

**The media-framing flake, properly diagnosed this time.** `media-framing.spec.js` had a dropdown test failing intermittently since v0.12, and the v0.12 "fix" — adding a `page_data` mock — **made it worse**, because the mock returned an *empty* skills array while the test seeded a move on top. The page's boot rendered one thing, the test rendered another, and whichever landed last won.

Two changes, and the second is the one that matters: the mocks now return exactly what the tests seed (so the two renders agree), **and** the test waits for `networkidle` before touching anything. Matching data alone was not enough — the boot re-renders the builder regardless, and a re-render between opening the custom dropdown and clicking an option discards the wrapper's `open` class, so the option is genuinely not visible. That is why the symptom always read as a mysterious visibility error rather than a data problem.

The general rule for editor specs: **mock what you seed, and let the boot finish before interacting.** Half of that pairing was what the v0.12 fix got wrong.

Verified at CI's real configuration (default workers, no repeats) three times clean. Stressing it at 6 workers x 8 repeats still turns up roughly one failure per hundred, spread across different tests in the file — but that load is outside the envelope this project already measured as unreliable (8 workers were *slower and failing* in the v0.12 measurements), so that number says more about the harness than about these tests.

## The regeneration job had been failing since 2026-08-09 (found 2026-08-12)

Noticed sideways: the owner changed the site version to Beta v0.12 in the owner tools, and the site kept showing v0.11 after a regeneration run. The database said v0.12; `data/site_meta.json`, which is what pages actually read, said v0.11. **The last three scheduled runs of `regenerate.yml` had all failed**, so nothing had regenerated at all — the version, the `Roulette` rename, refreshed portraits, the new page stub, all stuck.

**Two independent causes, either of which alone was enough.**

**1. The workflow's write set was a subset of its check set.** It ran `generate-pages.js --write` — one of the five artifacts `npm run validate` checks — and then validated all five. So any fetch that changed `sitemap.xml` or the hub meta tags left them stale and Validate failed before the commit step. Reproduced exactly, locally, down to the same failure line and counts (40 entries, 31 pages).

The shape is what made it invisible: **the job could only pass when it had nothing to do.** A run with no work and a working run look identical from outside. It broke the day the first `others/` page was created and simply stayed broken.

Fixed by running `npm run generate` instead of one script of it. The invariant now stated in the workflow: whatever `validate` checks, `generate` writes, and the workflow runs the latter.

**2. Three tests pinned counts the owner controls.** With the workflow fixed, the job would still have died at its test step: `generate-pages.spec.js` asserted exactly 30 pages / 22 characters / 8 systems, `social-meta.spec.js` asserted 30, and `registry-roundtrip.spec.js` compared the category list to a literal `['Characters', 'System Pages', 'Site Info', 'Guides']`. One new page and one new category broke all three.

That is worse than a stale sitemap, because the regeneration job runs the suite *before* committing (deliberately — a `GITHUB_TOKEN` push does not trigger `playwright.yml`). **So a test pinned to page count meant the owner could not create a page without a developer editing the suite**, and the failure showed up as "regeneration is broken" rather than anything pointing at tests.

They now assert the contract instead of the snapshot: every stub traces back to a navigation entry, counts are floors rather than equalities, and category order is compared against the committed navigation's own order rather than a literal. A new test feeds `buildPages` a synthetic extra page and asserts a stub appears, so the "owner adds a page" path is covered directly.

`tests/regenerate-workflow.spec.js` locks the invariant itself: every `--check` in `validate` has a `--write` in `generate`, the workflow runs the whole thing, and it still generates before validating and tests before committing. Two of its five cases fail against the old workflow file.

**Three days of backlog landed with the fix**: version to Beta v0.12, `Roulette` correctly spelled at `others/roulette/index.html`, the new page stub, 23 portraits and a 42-URL sitemap.

**Left open, and it belongs to this problem.** `character-modes.spec.js` → "a deep link opens straight into the mode it names" failed once in a full run and passed 11/11 on its own straight after. It is properly mocked (`addInitScript`, `networkidle`), so it is a timing flake under load rather than anything the regeneration touched, and it was not fixed here because guessing at an unrelated flake is worse than recording it.

It matters more than a normal flake though: the regeneration job runs the whole suite before committing, so **any** intermittent failure randomly blocks regeneration, and it presents as "regeneration is broken" rather than as a flaky test. That is the same disguise the count assertions wore. Worth fixing before this job is trusted to be unattended.

## Carried in from v0.12

- **The suite is ~573 specs and ~4.5 minutes, and the obvious explanations are wrong.** Measured 2026-08-11, because the first two guesses were both incorrect and each one nearly became a fix:

  | Hypothesis | Test | Result |
  |---|---|---|
  | Real Supabase calls dominate | blocked `supabase.co` entirely on a 32-navigation spec | 17.3s to 16.8s. **3%.** Only 21 of 81 spec files mock it, and it barely matters. |
  | It is CPU-bound, so more workers help | 1 / 4 / 8 workers on the same spec | 21.8s / 15.1s / 18.6s, and 8 workers *failed 2 tests*. 4x the workers buys 1.44x. |
  | `python -m http.server` is the constraint | replaced it with a Node server | **9.3 min and 31 failures** - worse. Every failure was `page.goto` timing out, because that server called `fs.statSync` per request and blocked its own event loop, where python's threaded handler does not. Reverted. |

  So: the poor worker scaling is real and still unexplained, Supabase is not the cause, and a naive Node server is worse than what is already there. **Next things to try, in order:** (1) the same Node server with async `fs.promises.stat` - the blocking I/O is a known flaw with a known fix, and it would also let 404.html be served the way GitHub Pages does, which `js/page_rescue.js` currently cannot be tested against; (2) failing that, shard CI across a matrix (`--shard=1/3`), which spreads over separate runners and helps whatever the local constraint turns out to be. Neither is urgent.
- **`js/site_utils.js` is cache-busted by content hash.** Editing it by hand means running `npm run generate` before pushing, or `npm run validate` fails. That check exists because a stale cached copy of that one file took the whole editor down live on 2026-08-10.
- **One flaky spec was fixed on the way out**, and the lesson generalises: `page-skeleton-parity` collected `[id^="tab-"]` from anywhere on the page and picked up the nested move-variant tabs `js/framedata.js` builds, so it passed or failed depending on network timing. It blocked a merge on a PR that changed only JSON and markdown.

## Batch added by the owner, 2026-08-11

**10. Make clearing orphaned media safe.** `runMediaGC` in `js/owner.js` builds one string from `page_data`, `pending_revisions` and `page_history`, then deletes every bucket file whose name does not appear in it. It destructures those three queries without checking their errors, so a failed select contributes nothing and **every file reads as orphaned** — reported to the user as "Deleted N orphaned files". 198 files, 346 MB, one confirm dialog away. Needs: bail on any query error, refuse when the orphan set is an implausible share of the bucket, and list what it intends to delete before doing it rather than after.

**11. Multi-file upload in the media library.** One at a time today. The measured evidence for why it matters: seven raw clips uploaded individually inside fifty minutes on 2026-08-09. `window.uploadWikiMedia` already takes a single file and returns `{name, url, width, height}`, so the change is a queue around it plus per-file status — the overwrite guard and the WebP conversion stay per file.

**12 and 13. Matchup tiers.** Two additions (Slight Disadvantage, Slight Advantage) and two renames (Unloseable → Dominating, Unwinnable → Hopeless).

The vocabulary is defined in **three** places that must move together: `js/description.js` (live page), `js/editor-previews.js` (editor preview) and `js/editor-tabs.js` (the `tierOptions` array the editor offers). Two independent colour maps and one option list — worth collapsing into one exported constant while touching them.

**The renames are a data change.** Measured across all 30 pages: 380 matchup entries, of which **18 use "Unwinnable" and 14 use "Unloseable"**. `tierColors[mu.tier] || "#ffffff"` means an unrecognised tier silently renders white with the old word still showing, so a rename without a migration quietly degrades 32 real matchups.

Two things follow:

- Migrate `page_data` (a jsonb rewrite of those 32 entries), **but do not rewrite `page_history`** — that is an audit trail, and editing it to say something a reviewer never approved is falsifying the record.
- Which means the renderers need a **legacy alias** regardless — old → new — so history replay and any ticket already in the queue keep rendering. The alias is permanent; the migration is what stops new data using the old words.

One piece of junk data found while counting: a single matchup with the tier `"Aerial Circling tier"`, which is not and never was an option. Worth cleaning in the same migration.

**14. Character and frame-type colours in the editor's colour presets.** The preset row in `js/editor-blocks.js` is seven hardcoded `hsl()` swatches. `window.CHARACTER_COLORS` (js/site_meta.js) and `window.FRAME_COLORS` both already exist and are already the site's real palettes — the presets simply predate them. Note that `FRAME_COLORS` is read from CSS custom properties at script-parse time, so the picker has to read it after that, not at module load.

## Carried in from v0.12

- **The suite is ~573 specs and ~4.5 minutes, and the obvious explanations are wrong.** Measured 2026-08-11, because the first two guesses were both incorrect and each one nearly became a fix:

  | Hypothesis | Test | Result |
  |---|---|---|
  | Real Supabase calls dominate | blocked `supabase.co` entirely on a 32-navigation spec | 17.3s to 16.8s. **3%.** Only 21 of 81 spec files mock it, and it barely matters. |
  | It is CPU-bound, so more workers help | 1 / 4 / 8 workers on the same spec | 21.8s / 15.1s / 18.6s, and 8 workers *failed 2 tests*. 4x the workers buys 1.44x. |
  | `python -m http.server` is the constraint | replaced it with a Node server | **9.3 min and 31 failures** - worse. Every failure was `page.goto` timing out, because that server called `fs.statSync` per request and blocked its own event loop, where python's threaded handler does not. Reverted. |

  So: the poor worker scaling is real and still unexplained, Supabase is not the cause, and a naive Node server is worse than what is already there. **Next things to try, in order:** (1) the same Node server with async `fs.promises.stat` - the blocking I/O is a known flaw with a known fix, and it would also let 404.html be served the way GitHub Pages does, which `js/page_rescue.js` currently cannot be tested against; (2) failing that, shard CI across a matrix (`--shard=1/3`), which spreads over separate runners and helps whatever the local constraint turns out to be. Neither is urgent.
- **`js/site_utils.js` is cache-busted by content hash.** Editing it by hand means running `npm run generate` before pushing, or `npm run validate` fails. That check exists because a stale cached copy of that one file took the whole editor down live on 2026-08-10.
- **One flaky spec was fixed on the way out**, and the lesson generalises: `page-skeleton-parity` collected `[id^="tab-"]` from anywhere on the page and picked up the nested move-variant tabs `js/framedata.js` builds, so it passed or failed depending on network timing. It blocked a merge on a PR that changed only JSON and markdown.

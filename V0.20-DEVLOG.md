### Three decisions the owner made before building, 2026-09-20

* **Content is CC BY-NC-SA 4.0; the code stays MIT.** Put to them that this
  **permits an attributed, non-commercial mirror**, which is the thing their own
  stated goal names. The option was labelled as not meeting it and they chose
  it anyway. That is their call and it is not to be re-litigated. What it does
  get: a commercial copy, or one that strips the credit, is a breach. The ToS
  adds the only remaining hook, that **automated bulk collection is a breach of
  access** even where the licence would permit the reuse.
* **Legal in the repo, conduct in the CMS.** Privacy, Terms and the licences are
  repo files, so every wording change has a git history to point at. The conduct
  document is a CMS page, because it will move as the forum and the Discord do.
* **The Discord role scheme is in scope**, mapped onto the wiki's existing
  ladder rather than invented beside it.

### Three findings that changed the shape of the work

* **The Writing Guide already promises a Terms of Service.** In its media
  section: *"you will be reminded first time when opening Media Library, and can
  be revisited in the terms of service"*. Contributors are being pointed at a
  document that has never existed. L3 is owed, not new.
* **The licence and the ToS are one problem, and the ToS comes first.**
  Contributors wrote the content, so **they** are its licensors until the terms
  say otherwise. Without a contributor grant, any content licence binds only
  what the owner personally wrote.
* **Cloning the repo does not get anyone the wiki.** The content lives in
  Supabase; the repo holds the engine and generated shells. The realistic
  copy-paste risk is scraping the live site, which a licence barely touches.
  Said to the owner plainly before they chose.

**Engineering, mine to do once chosen:**

  system stub loads it second, before `Buttons.css`. Between those two files,
  which rule wins depends on the page type, so every equal-specificity pair

## Carried warnings

**A release conflicts on stubs, and the fix is to regenerate.** v0.19's release
PR is *not* evidence against this. It merged clean only because `main` had
taken no `chore: regenerate` commit since v0.18, so there was nothing on the
other side to conflict with. The next release that follows a regeneration on
`main` will conflict on every stamped stub, exactly as v0.18's did on 62 files.
Resolve toward the integration branch, run `npm run generate`, then check that
nothing only `main` had was reverted.

**`data/search-index.json` and `data/search-fulltext.json` are now in that
surface too.** They regenerate per branch from Supabase like every other
artifact. Regenerate, never hand-merge.

**"Regenerate, never hand-merge" has a blind spot**, and v0.19 found it: it
recovers anything a generator owns and **silently discards anything in the same
files that it does not.** Taking the integration branch's side on 64 stamped
HTML files dropped a hand-added script tag from 17 pages, with the suite green
and no error anywhere. The searchbar simply would not have existed. Derived
tests now pin it; the general shape does not have a general fix.

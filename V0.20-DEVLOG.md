### Three decisions the owner made before building, 2026-09-20

* **Content is CC BY-NC-SA 4.0; the code stays MIT.** Put to them that this
  **permits an attributed, non-commercial mirror**, which is the thing their own
  stated goal names. The option was labelled as not meeting it and they chose
  it anyway. That is their call and it is not to be re-litigated. What it does
  get: a commercial copy, or one that strips the credit, is a breach. The ToS
  adds the only remaining hook, that **automated bulk collection is a breach of
  access** even where the licence would permit the reuse.
* **Legal in the repo, conduct in the CMS.** Privacy, Terms and the licences are
  repo files, so every wording change has a git history to point at. The conduct
  document is a CMS page, because it will move as the forum and the Discord do.
* **The Discord role scheme is in scope**, mapped onto the wiki's existing
  ladder rather than invented beside it.

### Three findings that changed the shape of the work

* **The Writing Guide already promises a Terms of Service.** In its media
  section: *"you will be reminded first time when opening Media Library, and can
  be revisited in the terms of service"*. Contributors are being pointed at a
  document that has never existed. L3 is owed, not new.
* **The licence and the ToS are one problem, and the ToS comes first.**
  Contributors wrote the content, so **they** are its licensors until the terms
  say otherwise. Without a contributor grant, any content licence binds only
  what the owner personally wrote.
* **Cloning the repo does not get anyone the wiki.** The content lives in
  Supabase; the repo holds the engine and generated shells. The realistic
  copy-paste risk is scraping the live site, which a licence barely touches.
  Said to the owner plainly before they chose.

## Carried warnings

**A release conflicts on stubs, and the fix is to regenerate.** v0.19's release
PR is *not* evidence against this. It merged clean only because `main` had
taken no `chore: regenerate` commit since v0.18, so there was nothing on the
other side to conflict with. The next release that follows a regeneration on
`main` will conflict on every stamped stub, exactly as v0.18's did on 62 files.
Resolve toward the integration branch, run `npm run generate`, then check that
nothing only `main` had was reverted.

**`data/search-index.json` and `data/search-fulltext.json` are now in that
surface too.** They regenerate per branch from Supabase like every other
artifact. Regenerate, never hand-merge.

**"Regenerate, never hand-merge" has a blind spot**, and v0.19 found it: it
recovers anything a generator owns and **silently discards anything in the same
files that it does not.** Taking the integration branch's side on 64 stamped
HTML files dropped a hand-added script tag from 17 pages, with the suite green
and no error anywhere. The searchbar simply would not have existed. Derived
tests now pin it; the general shape does not have a general fix.

## Built 2026-09-24: the three bugs, and FT2

### Bug 1: a Combo Card named after the switch was still "New Combo"

Two faults behind one symptom, and only the reproduction found the second.

**The card list read `card.title` directly.** That is dead data once Multiple
Sections is on, because `description.js` renders a tab per section and each
section carries its own heading, so the card's own title reaches no reader.

**`seedCardSections` copied the card's title into the section's TAB LABEL.** For
a card switched on before it was named that is the template default, so "New
Combo" was planted as a genuine label and renaming never cleared it. Readers saw
it on the tab. The label is seeded EMPTY now: it is an optional override for the
case the owner's reference shows, a tab reading "In Corner 6H" over a much
longer heading, and the reader already falls back to the title when it is blank.

`window.comboCardLabel` reads TITLE before label, the opposite of the reader's
tab row, because it is naming a card rather than a tab. It reads the FIRST
section rather than the open one, because a reader lands on tab 0 and using the
open tab would rename the card every time one was clicked.

### Bug 2: the Combos preview snapping back to the first tab

**Found only because the owner sent a screen recording.** Three written
descriptions and four probes had all aimed at the editor form. It is the
PREVIEW: the form edits section 2, the author types one line into Route, and the
preview jumps to section 1.

**The cause is the shape of the v0.19 fix, not a new bug.** v0.19 solved this
and solved it inline in `populateTextSection`. `renderDocumentTab` is a second
repaint path, clears its container the same way, and never got it, so the
Section Box was fixed everywhere except the two tabs a Combo Card lives in.

Capture and restore are now `window.captureNestedViewState` and
`window.restoreNestedViewState`, called from both. Still matched BY POSITION:
the title is what is being typed when somebody renames a section.

### FT2: blocks open expanded again, folders stay collapsed

The owner's revert of v0.16 fine-tuning 2, after living with it: *"navigating
through huge amount of content is easier than navigating through a bunch of
boxes that have a tiny preview. Though, keep folder collapsed."*

**Folders needed no change.** `isBlockFolderCollapsed` is true for anything not
in the `expanded` set and `resetBlockFolderState` empties it, so folders have
always opened collapsed. The comment in `initStrategyBlockBuilder` claiming they
"start everything expanded" was simply wrong and is corrected.

The block set is INVERTED, `expandedBlocks` to `collapsedBlocks`, rather than
gaining a `startExpanded` flag. A flag would have to be consulted everywhere the
set already is, and the two would disagree the first time somebody added a third
state. `js/editor-folders.js` records the same decision for the same reason.

`tests/editor-workspace-collapse.spec.js` changed with the contract rather than
being relaxed. The collapse machinery is untouched and most of that file still
tests it; those tests now collapse first, through the real button, because the
default no longer does it for them.

### PR #203's CI: cancelled at the cap, and I had already seen the answer

Merged 2026-09-24T11:39:59Z, merge commit `7f27fb01`, after a second run came
back green: 1,918 passed, 1 skipped (pre-existing, the base has it), 0 failed,
0 flaky. The count reconciles exactly against the base's 1,914: the five new
tests are four in `combo-card-sections` and one in `block-multiselect`.

**The first run was CANCELLED, not failed.** It hit `timeout-minutes: 30` at test
#1388 of about 1,830, and every test that ran had passed. All 54 failure marks
were one file, `block-multiselect.spec.js`: 18 tests, each failing all three
attempts at exactly 30.1s. 18 x 3 x 30s is the whole job.

**The cause was FT2.** The spec clicked and hovered `.block-card-summary`, the
label a COLLAPSED block shows. FT2 opens blocks expanded, where it is
`display: none`, and click and hover both wait for visibility.

**The feature was never broken, and that was measured rather than assumed**,
because the Ctrl-click listener's own comment rests on the assumption FT2 changed
(*"every block opens collapsed, so for most cards the header IS the card"*). On
an expanded card 88% of the header is still free non-control area: the row is
~1285px and the block-type picker is 112px of it, at the far left. The spec now
clicks the header row's centre, which is what an author clicks in either state,
and gained a test for the collapsed path that nothing else covers any more.

**How it shipped, which is the part worth keeping.** That spec was in the
derived blast radius and was run before pushing. It failed 18 of 19. The output
was read with `tail`, the reporter prints failures ABOVE the passed count, and
the radius was reported green. The rule is now in the `writing-tests` skill:
grep the summary lines, never tail them.

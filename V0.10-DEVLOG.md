## Scope: Owner Tools

The owner-facing half of what was originally one large v0.9. v0.9 shipped the user-visible parts (page router, Discord link previews, blog); this is everything that only the owner sees.

**Sequencing note carried over from v0.9:** almost nothing here is visible to site readers. Worth deciding up front whether to pair it with something showable, or accept it as a maintenance release and say so plainly in the changelog.

1. **Personnel roster** — a real list of everyone holding a role, not the current blind by-email lookup. Needs a new `list_personnel()` `SECURITY DEFINER` RPC: `user_roles`' only policy is `auth.uid() = user_id`, there is no `profiles` table, and `auth.users` is not PostgREST-reachable, so no client can enumerate today. Fold in the self-XSS cleanup at `js/owner.js:98,100` while that file is open.
2. **Page permissions manager** — `page_permissions` has a public-read policy but no write policy and no write grant, so it has only ever been seeded by migration. **Owner-confirmed: `required_role` becomes real**, which is a live behaviour change — `js/editor-core.js:418` and the INSERT policy in `20260731000000_page_permissions.sql` both ignore it today. Verify against a real trusted-editor session, not just an admin one.
3. **`site_pages` table + the regeneration Action** — deferred from v0.9 R4 deliberately: they exist to serve page create/delete, and building them without it would have meant granting a CI job commit access for a table nothing writes to. Full design (fail-safes, tombstones, the `GITHUB_TOKEN`-doesn't-trigger-workflows trap, anon-key-not-service-role reasoning) is in the v0.9 plan file.
4. **Page create/delete UI** — depends on 3.
5. **Account/data deletion tooling (anonymize)** — owner-confirmed: email and account go, past edits stay attributed to a placeholder so `page_history` survives. **Ships with the `privacy-policy.html` "Deleting your data" rewrite in the same commit** — that page currently promises no self-serve button *yet*, and splitting them means shipping a page that lies about your own privacy practices.
6. **FAQ editing** — `data/faq.json` is static; edits need a commit. Simplest of the content items, so do it first as the template for the rest.
7. **Credits/collaborators** — reconcile `index.html`'s hardcoded `.credits-list` against `systems/collaborators/`'s own `collaborators_data.json`. Two sources of truth today.
8. **Hub text editing** — owner-editable headings/descriptions for the three dashboards, emitted statically by the generator alongside their meta tags.

**Nice-to-have carried from v0.9:** per-character portraits as `og:image`. Every page currently previews with the site logo. This needs the generator to read `page_data.desc_data.profile.image` from Supabase, which is exactly what item 3's Action makes possible — so it falls out of that work cheaply.

**Before starting**: confirm scope is still current, and re-verify the claim that `systems/collaborators` is `editRole: locked` and bypasses the CMS before planning around it.

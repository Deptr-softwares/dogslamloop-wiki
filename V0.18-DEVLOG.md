## What reading the code changed about the list

Four things, all established against the code on 2026-09-08 rather than assumed.
Three of them move an item between categories, which is why they are here and
not in a commit message.

### The reorder mechanism already exists, so two of the three ordering items are small

`js/editor-reorder.js` is v0.15's item 8 and its header states the intent
plainly: *"A ninth strip added later gets reordering by declaring where its array
lives."* Seven strips declare one today (`editor-system.js:18,35`,
`editor-tabs.js:183,218,247,294,337`).

* **F3, Combo Lists** — the control is simply not rendered on that strip. The
  submit side is **already done**: `desc.comboList` is in `EXTRA_KEYED_SECTIONS`
  (`js/character_tabs.js:410`) keyed by `starter`, and `scanEveryOrder`
  (`js/editor-core.js:1246`) walks every keyed section. So this is a render
  change, not a pipeline change.
* **F4, rows inside a Combo List** — genuinely different and **not** free. Rows
  are table rows edited through a modal (`js/editor-tabs.js:1148-1203`), not
  `.daw-tab-item` entries, so the shared strip mechanism does not reach them.
  The owner's *"not sure why this isn't implemented yet, but it should be
  simple"* is right about the outcome and not about the route.

### B2 was filed as a feature and is a data-loss bug

The owner's list asks to *"add ordering to System Type pages navigation tab"*.
**The control is already there** — `editor-system.js:18` renders
`reorderStripControls('desc.tabs')`, and clicking it does move the array.

What is missing is that **nothing records the move**. `buildSystemDeltas`
(`js/editor-system.js:218`) emits `system_tab` per tab and `system_section` per
section, and section order rides along as `meta.order` on the tab payload
(`:239`). No delta ever names the **sequence of tabs**. So reordering tabs
changes no tab's metadata and no section's content, `differs()` finds nothing,
and the contributor is told "no changes detected".

That is the same class as the v0.15 finding that *reordering never submitted and
never applied, because position was not in the delta model at all* — fixed then
for character pages, never for the tab strip on system pages.

It moves to Bugs because the difference matters to how it is verified: a missing
feature is proven by building it, and silent data loss is proven by **losing
something first**. The spec below starts from a repro.

### FT5 stops being optional

B2 introduces a new system-page delta shape. FT5 is "Diff View renders the new
system-pages engine". Shipping B2 without FT5 means reviewers approve a tab
reorder they cannot see — which is bug 4's lesson from v0.15, in the exact same
place. **They land together.**

### B1 — CLOSED. Environmental, and the first diagnosis was wrong twice over

**Closed 2026-09-08 by the owner:** *"It was from slow connection, I believe.
Now I didn't experience it when using Live Preview anymore."* No code shipped
for it, and none should — there is nothing in the render path to fix.

**The measurement is kept because it is what makes closing this safe.** Without
it, "the owner stopped seeing it" would be indistinguishable from a bug that had
merely gone quiet. The strip provably renders once, correctly, so a transient
wrong state has to come from outside the render — which is exactly what a slow
connection produces.

**And the diagnosis this section originally carried was wrong.** It stated, as
established, that `afterChange()` renders the strip with its default selection
and `reselect()` corrects it one tick later, so the flash was one render of
index 0. That was reasoned from the code and never measured.

Measured, it is false. A `MutationObserver` over the move, recording the strip's
rendered order, its active index and the underlying array on **every** mutation:

| strip | distinct frames | intermediate bad state |
|---|---|---|
| `desc.matchups` | 2 | none |
| `desc.tabs.0.sections` | 2 | none |
| `desc.tabs` | 2 | none |
| live preview pane, during a section move | 6 mutations, straight to the new order | none |

`afterChange()` and `reselect()` are both synchronous inside the same click
handler, so the browser never gets to paint between them. There is exactly one
render, and it is already correct. `.block-just-moved` was checked too and is a
colour flash with no transform, so it cannot move anything.

The probes were also the wrong shape while they ran: all four vary the *strip*
and none vary the *control*, so they were closer to one piece of evidence
repeated than to four. That is v0.16's bug-1 lesson recurring in the same repo —
*"a cannot-reproduce is a claim about the probes, not the bug"*. It happened to
land on the right answer here, and it was still the wrong method.

**The lesson worth keeping is the order of operations, not the outcome.** The
fix was written into this file as a plan, and measuring first is what stopped it
being written into the code. A render-path fix would have shipped, changed
nothing an owner on a slow connection could see, and left a permanent "fixed"
entry against a fault that was never there.

## Batch 1 — B2, FT5, F3, F4 — SHIPPED 2026-09-08

PR [#178](https://github.com/Deptr-softwares/dogslamloop-wiki/pull/178), merge
commit `cc2fd50`.

Scoped as B1 + B2 + FT5 + F3. B1 closed as environmental before any code was
written, and **F4 was pulled in** because it finishes the same screen as F3 —
so four shipped rather than three. B2 was discarding the owner's edits every
time they used a control that had been on the strip for three versions.

### B1 — closed, no code

Environmental. See the section above. Nothing was written and nothing should be.

**The verification method is worth reusing** the next time a "it flickers"
report arrives: a `MutationObserver` over the interaction, asserting that no
intermediate frame paints a state the settled one contradicts. Asserting the
final state alone always passes, because the whole complaint is about frames
that no longer exist by the time an ordinary test looks.

### B2 — a tab-order delta for system pages

Shape follows `meta.order`, which already solved this one level down:

> *The order travels as a list of KEYS. A reorder that carried section content
> would let moving a section overwrite an edit somebody else made to it in the
> meantime — the whole-document bug in miniature.* (`editor-system.js:236-238`)

So the tab order travels as a list of **tab keys**, in its own scope, carrying
no tab content. Same reasoning one level up.

Open, to settle before writing SQL or the payload:

1. **Scope name.** `system_order` is the obvious one and sits beside
   `system_tab` / `system_section` without overloading either.
2. **Backward compatibility.** `scanOrder` in `editor-core.js:1197` refuses to
   emit when identities are missing or duplicated, and `applyDeltaToData`
   refuses the same two shapes — *"Losing a reorder is visible and repeatable;
   shuffling somebody's page is neither."* Tab keys must be checked for the same
   two failure modes before this emits anything.
3. **Merge.** `js/admin-merge-compiler.js` batches `system_section` deltas by
   key. Two contributors reordering the same tab strip is a genuine conflict,
   not a merge — decide before building, not at the first ticket.

### FT5 — Diff View renders the system-pages engine

`js/admin-diff.js:514` already walks `currentPendingDescData.tabs`, so this is
not a blank start. What FT5 has to end at is **every** system-page delta scope
having a rendering, including B2's new one, verified by making the picker and
the renderer disagree in both directions:

> *"Everything I offer resolves" and "everything real is offered" are different
> claims.* — v0.15's section-link picker was internally consistent and blind to
> a third of the site.

### F3 — the Combo List strip gets its controls

`reorderStripControls('desc.comboList')` on the strip that renders the list
sub-section, plus `registerInserter` for the same spec so `+` inserts in place
rather than appending.

**The submit path needs no change**, and that claim is the one to falsify first:
if an order delta does not appear when only the order changed, the assumption
that `scanEveryOrder` covers `comboList` is wrong and the item is bigger than
this section says.

The Techs tab shares this machinery through the same vocabulary, so `techList`
gets it in the same change or the two diverge — the exact drift
`js/character_tabs.js`'s own header exists to prevent.

## Batch 2 — F6, F7, FT1, FT2 — BUILT 2026-09-08

### A first-visit modal is a change to every editor spec at once

F6 opens a modal on editor boot. Every Playwright test gets a fresh context
with empty `localStorage`, so it opened over the page in **all 59 specs that
load `edit.html`** and timed out their first click.

It surfaced as one unrelated-looking failure — `styling-and-credit`'s
combo-card credit test, a 30-second timeout on `addDocumentGroup`. Two things
identified it: it failed identically **in isolation**, so it was not load, and
reverting FT2 did not fix it, which ruled out the change just made.

**Nothing is wrong with the notice.** A modal that blocks the page until
dismissed is what was asked for. What was wrong is that 59 files were
implicitly asserting that nothing covers the editor on load, and not one of
them is about that.

Seeded once in `playwright.config.js` via `storageState`, not dismissed per
spec: 59 files would have to remember, and so would every editor spec written
afterwards. `tests/editor-notices.spec.js` overrides it back to empty, so the
seeding cannot hide a broken notice — the one spec that proves the notice fires
is the one spec that runs without the seed.

**Carry this forward:** anything rendering over a shared page on load is a
suite-wide change, and the cost lands on files with no reason to mention it.

### The two notices

One module, one mechanism, two surfaces — both `edit.html` only
(`#interactive-builder` and `#media-modal-overlay` exist nowhere else).

`showEditorNotice` takes a notice **ID** and looks the body up in a table in the
module. It deliberately does **not** take an HTML argument: this is the one
place in the project where `innerHTML` receives markup rather than escaped
text, and the shape of the function is what stops a caller passing contributor
text into it later.

The Writing Guide link is `target="_blank"` — a behaviour decision rather than a
change to the copy, and load-bearing: the editor holds unsaved work, so a
same-tab navigation out of it discards whatever was typed.

**The z-index is stated, and the hit test did not prove it.** Falsifying found
that `elementFromPoint` passes with the rule deleted, because the notice is
appended to body last and wins at the shared 10000 on DOM order. That is exactly
the mechanism `style/editor.css`'s confirm-layer comment blames for two shipped
bugs. A second assertion compares resolved z-index values, and fails with the
rule removed.

### The copy was revised after shipping verbatim

Both texts arrived with *"Do not change anything"* and shipped exactly as
written. The owner asked the same day for the grammar to be corrected.

`Local Resource` was left singular and capitalised: beside a lowercase "local
resources" in the same sentence it reads as the name of a Writing Guide
section, and renaming somebody's heading is not a grammar fix.

### FT1 removed a second place the same decision lived

`js/input_slots.js` carried an `outline: 'light' | 'dark'` field per slot.
Nothing read it except a test asserting it held one of those two values, so the
moment the CSS moved to a single black outline the field was wrong and nothing
could notice. The invariant is asserted against `ColorCoding.css` directly now,
on **both** the `@supports` stroke and the `text-shadow` fallback — changing one
and not the other splits the two populations of reader.

The brightened fills are asserted **per slot against its own old value**. A
single shared luminance floor was tried first and was wrong: it put Shift, which
went from 12% to 45% lightness, under a bar set by the brightest of the four —
a test dictating a palette rather than checking one.

**The three neutrals are the open question.** Q, Space and Shift are spread at
roughly 45/62/82 to stay discriminable, and that spread is a judgement made
here, not by the owner. It is the one part of FT1 worth their eye.

### FT2 states the darkness test once

The `<50%` lightness check already existed twice in `js/site_meta.js`, under a
comment insisting the two must never disagree. This would have been a third
copy in a different file, so it became `window.isDarkCharacterColor`, which
`--character-ink`, the title shadow engine and the name outline all ask.
Unparseable input returns false — a bad colour means no outline rather than an
outline applied on a guess.

Both halves of the selector do work, and the spec covers three cases so neither
can be deleted silently: dark-on-dark outlines, light-on-dark does not,
dark-on-light does not.

## Batch 3.5 — sizing and the third drifted roster — BUILT 2026-09-09

Four follow-ups the owner raised after seeing batch 3 on the live site. Named
3.5 by them, because none of it is a new scope item — it is batch 3 finished.

### The same bug, a third time

`js/tier-editor.js`'s `loadRoster` read `entry.image` off a `navigation.json`
entry, which carries no `image` field on any character. So `meta.image` was
undefined and `portrait()` fell through to a **guessed Supabase URL** built from
the display name — stale art, and an outright 404 for the five characters whose
files end `Portrait2.webp` or drop the suffix.

**Three near-identical `loadRoster` functions, two of them silently wrong.**
`certified-tier-lists.js` has always been right; `free_submit_tier_list.js` was
fixed for this exact fault in FT3 **one batch ago**; this is the third.

`CLAUDE.md` prefers small per-file duplication to cross-file coupling, and that
preference has now produced the same visible bug twice in two batches. Fixed in
place rather than unified — **unifying is the owner's call, not a thing to do
while they asked for something else** — but recorded here and in the code rather
than quietly patched a third time. If it happens a fourth, the convention is
what needs revisiting, not the copy.

### A claim in two test comments was false

Both said the editor kept 60px *"because its drag-and-drop hit-testing was built
around it"*. The drag resolves through `document.elementFromPoint` plus
`closest('.tier-dropzone, .tier-editor-tray')` and reads **no dimension at
all**. Checked against the code before enlarging anything, because had it been
true the boxes could not have grown.

One of the two was not testing the editor either — it renders a bare
`.tier-portrait` on the *certified* page, so what it measured was the base size.
Both renamed, both comments corrected. The assertions are kept, because what
they are actually worth is real: the base stays 60px so every surface scopes its
own size.

### Three sizes, on purpose

Base `.tier-portrait` 60px (history renderer, admin preview) · certified page
78px · editor 96px · Free Submit flex-grown from 108px to a 168px cap.

The editor's 96px is not an arbitrary step: `.tier-editor-row .ctl-chars` and
`.tier-editor-tray` already set `min-height: 96px`, so it fills the row that
exists rather than growing it. Free Submit **grows into the row** rather than
taking a bigger fixed size, because a tier holds anything from nobody to the
whole roster and one number is either cramped or a postage stamp. The cap is the
judgement call in that rule: without it a tier holding one character renders it
900px wide.

### Icon boxes borrow the roster card, value for value

The character's colour moves from the fill to the **border** over the site's
dark ground with the same `-45deg` hatching — every value copied from
`.roster-card.has-icon` rather than re-chosen, because two answers to "what does
an icon box look like" would be visible on one site. The colour travels as
`--char-color`, since an inline background would beat the rule that reads it.

PR [#180](https://github.com/Deptr-softwares/dogslamloop-wiki/pull/180), merge

**The version's first migration**, `20260909000000_tier_list_art_style.sql`. It

### FT3 was a drifted copy, not a missing feature

The Free Submit renderer already drew an `<img>` and already had the
name-underneath fallback for when it 404s. What it never had was a **src**:
`loadRoster` read `entry.image` off a `navigation.json` entry, and
`navigation.json` has no `image` field on **any** of its 24 characters. So the
src was never set and the fallback — the name on the character's colour — was
all anyone ever saw. Exactly what the owner reported.

`js/certified-tier-lists.js` reads `data/portraits.json` correctly, a few lines
from an otherwise identical `loadRoster`. **The two were copies and one
drifted.** `CLAUDE.md` prefers small per-file duplication to cross-file
coupling, and this is what that costs when the bill comes. Named in the code
rather than fixed silently, because the same pair can drift again.

### FT4's real risk was which body to copy

`save_tier_list` gains a parameter, so it is dropped and recreated whole. **Four
migrations define it.** The current one is `20260827000003_owner_role.sql`,
which uses `is_owner()`. But `20260818000000` — the one that last *added* a
parameter, and therefore the obvious template — still reads
`get_my_role() = 'admin'`.

Copying the obvious one would have re-locked the owner out of every tier list,
silently, while looking like a faithful copy. A test asserts the rebuilt body
contains `is_owner()` and no literal role comparison anywhere.

No new policy or grant: column privileges are not used on this table, so a new
column inherits the table-level `GRANT UPDATE` and the existing per-row policy.
Adding one would be a second gate saying the same thing.

**The editor board follows the control immediately**, not on save. Choosing
between two pieces of art is a decision made by looking at them, and a board
still drawing portraits after you pick icons reads as broken until you open the
live page.

### Two things the tests caught rather than me

- **`page.selectOption` timed out.** `.editor-select` is enhanced into the
  site's own dropdown and the native element is hidden. That is the *correct*
  outcome — a bare input would have rendered an OS dropdown among a page of
  custom ones, which is the bug `media-framing.spec.js` exists to hold shut — so
  the spec drives the real control, which is also the only way to prove the
  change listener fires at all.
- **A built regex matched nothing and passed as green.** Escaping turned
  `(uuid, …)` into a capture group, so an assertion about a `REVOKE` was
  checking something else entirely. Replaced with plain substrings.

### A2, and what it actually proved here

Baselines refreshed **before** the tier work, so this batch's diff would show on
its own rather than against a four-month-old reference. Three of six changed on
the refresh (character-page from batch 2's colour work, homepage and
tierlist-page from roster drift); three did not.

Re-run after FT3 and FT4: **all six unchanged.** That is a real result, not a
null one — the tier list page loads *nobody* by default, so it renders no
portraits, and the Free Submit tool is not in the visual set at all. **The six
screenshots do not reach either surface this batch changed.** For this batch the
suite proved the absence of unintended change elsewhere, which is worth having
and is not what it was reached for.

## The suite is close to its limit

Recorded here because it is not any one version's problem and will keep
surfacing as one.

**1452 tests against a single `python -m http.server` with 4 workers.** At the
v0.17 release a slow CI runner turned one flaky test into eight plus a hard
failure; a re-run of the identical commit came back **1439 passed, 1 flaky, 12.6
min**. Nothing was wrong with the code, and half an hour went into proving it.

The failure mode to recognise: **a burst of flakes across unrelated
page-loading specs, with the run time up by a quarter.** That shape is load, not
a regression. Read the conclusion (`CANCELLED` is not `FAILURE`), compare the
duration against recent runs, and re-run before diagnosing.

The real fix is a threaded server or parallel-safe fixtures. Not urgent; it will
stop being optional when a release is blocked by it rather than delayed.

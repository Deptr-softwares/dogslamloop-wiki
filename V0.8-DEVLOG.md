## The tests now run themselves

- **Nothing player-facing.** Every code change to the site now automatically runs the full test suite (147 checks) before it can be merged, instead of relying on someone remembering to run it locally. If something breaks, we find out immediately rather than after it's already live.

**Technical**: new `.github/workflows/playwright.yml` - checkout, Node 20, `npm ci`, `npx playwright install --with-deps chromium` (only chromium is configured in `playwright.config.js`, so installing the full browser matrix would be dead download time), `npx playwright test`, then upload the HTML report as an artifact. Runs on push and PR to `main`. No config change was needed: `playwright.config.js` already had `reuseExistingServer: !process.env.CI` waiting for this, and its `python -m http.server` webserver command works as-is on `ubuntu-latest`. Also added a `"test": "playwright test"` script to `package.json` (which had no `scripts` key at all) so `npm test` locally matches what CI runs.

## The admin page actually works on a phone now

- **The review workflow is usable on mobile.** Opening a ticket used to squeeze the status panel and the discussion log into two ~150px columns side by side, which made the chat basically unreadable and jammed the vote buttons together. They now stack full-width.
- **The PAGE HISTORY button is reachable again.** The Pending/Live/Diff/History row ran off the right edge of the screen since History was added - it now wraps into a tidy 2x2 grid.
- **The header stops eating the screen.** OWNER TOOLS / RECENT CHANGES / HUB used to stack as three more full-width rows before any of the actual queue was visible. They're now behind a single MENU button, so the header is one row.
- **Long technical diffs no longer run off the side of the screen** with no way to scroll them back.

**Technical**, all inside `@media (max-width: 900px)` except where noted - desktop was confirmed unchanged by screenshot comparison at 1440px:
- `.ticket-workspace`/`.ticket-left-col`/`.ticket-right-col` (`style/admin.css`) had **no mobile rule at all**; now stack to a column with a dashed divider replacing the vertical one.
- `#version-toggle-bar` gained `flex-wrap` + `flex: 1 1 calc(50% - gap)` and `white-space: normal` on its buttons (overriding `.btn-sys`'s own `nowrap`, which is what made the label clip inside its own shrunken button rather than the button itself overflowing).
- `.diff-stacked-pre`/`.diff-stacked-old`/`.diff-stacked-new` (`style/editor.css`) - **not** in a media query, this overflows at any width: a bare `<pre>` defaults to `white-space: pre` and never wraps, so a serialized JSON blob with no whitespace ran straight off the side. Added `pre-wrap` + `overflow-wrap: break-word`, with `overflow-x: auto` on the parents as the fallback.
- Header: the 3 nav links are wrapped in a new `#admin-secondary-actions` panel toggled by a new `MENU ▾` button (`admin.html`, `js/admin-core.js`'s `toggleAdminMobileMenu` + a click-outside handler). The panel reuses `.manga-select-options`' existing look (accent border + hard offset shadow) rather than inventing a new dropdown style. `id="owner-tools-link"` was deliberately left on the same element since `admin-core.js` looks it up by id.

**Two real bugs found while doing this, both fixed:**
1. **Every one of these mobile rules initially did nothing.** The selectors all have plain base rules *later* in `admin.css`, and a media query adds no specificity of its own - so on an equal-specificity tie the later rule silently won and the entire block was inert. Caught because the new tests failed against the supposedly-fixed code. Fixed with a `body` prefix to settle the tie by specificity, which is the convention this file already established (there's a long comment at `#version-toggle-bar`'s own mobile rule explaining the identical trap).
2. **The fix caused a new overlap.** Once the toggle bar wrapped to two rows it grew from ~50px to ~115px tall, and the floating BACK TO QUEUE button (pinned at `bottom: 4.5rem`, calibrated for a one-row bar) landed on top of it and completely covered the LIVE VERSION button. Both that offset and the pane's `padding-bottom` raised to `8rem`. Caught by screenshotting the result rather than trusting the passing tests - the assertions at the time didn't cover it.

**Verification**: 7 new specs in `tests/admin-mobile-rehaul.spec.js`, each confirmed via revert-confirm-restore to genuinely fail against pre-fix code. Includes a desktop-unchanged spec and a regression test for the overlap in (2). Full suite 147/147.

## The inbox works now

- **You'll actually get told what happened to your edit.** The bell icon in the sidebar has never worked - it always said "No new messages" no matter what, even though approvals and rejections were being recorded properly the whole time. Every notification you were ever sent is still there and will now show up.
- **The unread counter works too.** That little red dot on the bell was reading from the wrong place and never appeared.
- **You now get notified when staff open a discussion on your submission, and when they first reply** - previously a submission could sit under discussion indefinitely with no way to know unless you happened to check My Submissions yourself. Only the first reply notifies, so an active back-and-forth doesn't spam you.
- **Marking a notification as read now sticks** instead of coming back unread next time you loaded a page.

**Technical**: the system was split in half and neither half worked.
- `js/pagebuilder.js`'s dock (the visible bell) read its badge count from a `system_inbox` table, and on click built its **own** modal - reusing the same literal `id="site-notification-modal"` as the real one - reading `system_inbox` again. **That table has no migration and has never existed**, so both queries silently returned nothing.
- Meanwhile `js/site_utils.js`'s `initNotifications` correctly queried the real `user_notifications` table and built a correct, complete modal on every page load - but nothing anywhere ever removed `.hidden` from it. No `openNotificationModal` existed in the repo at all.
- Fixed by pointing the badge count at `user_notifications` and replacing the whole duplicate-modal block with a call to a new `window.openNotificationModal()` in `site_utils.js`. That function re-runs `initNotifications()` at click time rather than relying on page-load order (`initAuthDock` runs first, so the modal may not exist yet), which also means the list is always current instead of a load-time snapshot.
- New migration `20260807000000_user_notifications_update_policy.sql`: the table had SELECT/INSERT/DELETE policies but **no UPDATE policy**, so `markNotifRead` was silently RLS-denied. The optimistic UI made it look like it worked until the next page load.
- Ticket notifications added to `js/admin-actions.js` (`openTicketCurrentPreview`) and `js/admin-tickets.js` (`postTicketMessage`). "First reply" is derived from the existing `ticket_chat` array (no prior message from anyone but the author), not a new schema column. Neither fires on your own submission.

**Two further bugs found and fixed while wiring this up:**
1. **A latent XSS, activated by this very fix.** `site_utils.js` had no `escapeHtml` at all, and dropped `n.message` straight into `innerHTML` plus `n.id`/`n.link` into an inline `onclick=""` attribute. Notification text is staff free-text (the "Staff Note" typed into admin.html's prompt), so this was a real injection surface that was only dormant because the modal was unreachable - **making it reachable would have made it live.** Added a local `escapeHtml` (same precedent as `js/history.js`) and converted the inline handlers to `data-` attributes with a delegated listener, since HTML-escaping alone doesn't close an `onclick` attribute (the browser unescapes before the JS parser sees it).
2. `clearAllNotifications` targeted `#site-notification-modal .auth-body`, but the modal is built with `.modal-body` - the selector never matched, so the optimistic wipe silently did nothing.

**Verification**: 5 new specs in `tests/notifications-dock-wiring.spec.js` (all 5 confirmed failing pre-fix) and 4 in `tests/admin-ticket-notifications.spec.js` (the 2 positive cases confirmed failing pre-fix; the 2 negative cases guard against over-notification and pass either way, as expected). Full suite 156/156.

**Not covered by tests, needs manual confirmation**: the RLS UPDATE policy. Every auth spec in this repo mocks Supabase and never touches real Postgres, so RLS is invisible to the suite. The migration must be applied and then verified with a real authenticated update.

## A footer, a privacy policy, and a proper 404 page

- **Every page now has a footer** with the copyright, a link to the license, a link to the new privacy policy, and a short "fan-made wiki, not affiliated with the developers" line.
- **New privacy policy page.** Short and plain-language, not a wall of legal boilerplate: what's stored if you never log in (nothing), what's stored if you make an account (email + display name), what happens to your edits, which third parties are involved, and how to get your data deleted.
- **Bad links now land on a real page.** Mistyping a URL used to show GitHub's generic error page with no way back into the wiki. There's now a proper 404 with the full sidebar navigation and links to all three dashboards.

**Technical**:
- `window.buildSiteFooter()` in `js/pagebuilder.js`, self-firing on `DOMContentLoaded` (matching `site_utils.js`'s existing precedent - `pagebuilder.js` previously had no listener of its own and relied entirely on per-page inline calls). Injecting it beats editing 41 files by hand. Guarded on `.site-layout` being present, which is exactly what excludes `edit.html`/`admin.html`/`owner.html` - the only 3 pages without that wrapper, and the 3 that load `editor.css`'s unconditional `body { overflow: hidden }`, where an appended footer would exist but never be scrollable to. Links resolve through the existing `getRootPath()` so they're correct at every folder depth.
- `.site-footer`/`.site-footer-inner`/`.site-footer-link` added to `style/Layout.css` next to the existing "Footer & Credits" block.
- New `privacy-policy.html` and `404.html` at the repo root, both using the standard content-page chrome so they inherit the real sidebar nav (and the footer) rather than being dead ends.
- `404.html` carries a `<base href="/">`. GitHub Pages serves that one file for **any** unmatched path, so the address bar could be at any depth - without a base, every relative path in the page (and every path `getRootPath()` computes for the sidebar) would resolve against that arbitrary depth and 404 in turn. `CNAME` confirms the site is served from the domain root, so `/` is always correct.

**Verification**: 6 new specs in `tests/site-footer.spec.js` (depth resolution at 3 levels, a real HTTP fetch confirming the privacy link isn't itself a 404, the editor-page exclusion, idempotency), 4 in `tests/404-page.spec.js`, and both new pages added to `tests/smoke.spec.js`'s no-console-errors sweep. The 4 content-page visual baselines were updated: the page grew by exactly 96px (the footer) and both sidebars are `position: sticky`, so they re-render at a different offset in Playwright's stitched full-page capture. The `admin`/`edit` baselines were left untouched by the change, which independently confirms the footer exclusion works. Full suite 168/168.

**Caveat**: `python -m http.server` (the test webserver) does not replicate GitHub Pages' fallback-to-404.html routing, so the suite verifies the page renders, not that it gets served for bad URLs. That needs one bogus URL against the live domain after deploy.

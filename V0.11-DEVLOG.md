### 5. Editable site meta

Two different things under one name, with **different delivery mechanisms** — don't conflate them:

- **`data/site_meta.json`** (`version`, `tagline`) is fetched at runtime by `js/site_meta.js` and written into every `.site-subtitle`. Table → generated JSON, exactly like `faq.json`. Note the three hub pages have stale hardcoded fallbacks in their markup (`Alpha v0.1`, `Alpha v0.4`) that are overwritten on load.
- **The `<meta>`/OG block** in each hub page **must stay static in the served HTML.** Discord, Twitter and Facebook unfurlers do not run JavaScript, so a runtime-injected tag is never seen — this is the same reason v0.9's OG work had to come from the generator. All three hub pages are also in `NEVER_TOUCH`. So this needs a **marked region** (`<!-- BEGIN GENERATED: hub-meta -->` … `<!-- END -->`) that a script rewrites from the table, committed by `regenerate.yml`. Live after the next regeneration run, not instantly — same model the FAQ card already states in its own hint text.

**Items 4 and 5 are not new scope.** They are v0.10's original item 4 ("site text + meta tag editing for the three hub pages"), which was the one item of nine that did not ship. Infrastructure to match: `site_faq`/`site_collaborators` (`20260808000005_site_content.sql`) established the table → owner card → generated JSON pattern, and `owner.html` already carries six tool cards to sit alongside.

### 7. Make archiving a page actually archive it

Added by the owner 2026-08-09, who asked for an optional way to hide a page's "physical buttons" on archive. Tracing it first turned up that the current behaviour is **not** what the UI implies.

**What archiving does today:**

1. `setPageStatus` sets `status = 'archived'` ([js/owner.js:429](js/owner.js#L429)).
2. `fetch-registry.js` drops every non-live row from `navigation.json` ([scripts/fetch-registry.js:54](scripts/fetch-registry.js#L54)).
3. Sidebar, roster grid and systems directory all rebuild from that file, so those entries do disappear.
4. **`generate-pages.js` never prunes** — it writes stubs for pages in `navigation.json` and has no `status` awareness whatsoever. The archived page's `index.html` stays in the repo and keeps serving **HTTP 200 with its full original content.**

So an archived page is still reachable by direct link, by search engine, and by any Discord embed already posted. It does not 404. The tombstone described at [20260808000003_site_pages.sql:40-43](supabase/migrations/20260808000003_site_pages.sql#L40-L43) — "archived pages get a tombstone stub - HTTP 200 with a 'this page has been archived' body - rather than being deleted, so existing links and Discord embeds do not start 404ing" — **was designed but never built.**

**Decided:** build the tombstone as originally specified, plus the optional toggle.

- **Tombstone.** `generate-pages.js` gains `status` awareness and emits an archive-notice stub for `archived` rows. Serves 200, so old links and embeds still resolve instead of breaking. This means the generator must read archived rows, which `fetch-registry.js` currently filters out before they ever reach `navigation.json` — so the status has to survive into the generator's input rather than being dropped upstream. Emitting nothing is not an option: the file already on disk would simply persist, which is the current bug.
- **Optional hide toggle**, per page, separate from `status`. Covers the entry points that do **not** come from `navigation.json` and therefore survive archiving today: matchup and counterplay cards on *other* character pages, tier-list rows, and the hardcoded links in `index.html`. Off by default — archiving stays reversible and low-consequence.
- **Not chosen:** deleting the page file outright. It gives the cleanest "no confusion" result but breaks every Discord link already posted and removes the URL from search with no explanation for anyone following an old one.

`--check` determinism has to hold through this: a page's stub must be byte-identical for a given status, or CI's committed-stub comparison starts failing on unrelated PRs.

## Design decision: hub prose is CMS content, not a new table

Raised by the owner mid-planning ("take a look at how system type pages get their content created in `description.js`"), and it re-shaped items 4, 5 and 6 before any code was written.

**The site already has the pipeline this needs.** `page_data` holds block arrays; `generateHTMLForBlocks` renders them; the editor already authors them. Two consumers already exist *outside* character pages — `populateTextSection` ([js/description.js:390](js/description.js#L390)) and `renderPostBody` ([js/posts.js:35](js/posts.js#L35)) — so rendering authored blocks into an arbitrary container is established precedent, not new ground. System pages carry no hardcoded content at all: `loadPageDescriptions(pageId, 'system')` builds their entire body at runtime.

The original plan was a new table plus bespoke `owner.html` textareas for text the existing editor can already author. Dropped.

**Instead:**

- Each hub gets a `page_data` row — `main-hub`, `character-hub`, `systems-hub` — stored with `page_type: 'system'`. Note this deliberately differs from their `site_pages.page_type` of `'hub'`: the two columns govern different things (`page_data.page_type` drives the editor and renderer, `site_pages.page_type` drives navigation), and matching the editor's expectation is what makes this cost zero.
- `desc_data.tabs[]` are used as **named slots**, one per authored region, keyed by `tabId`.
- Hub pages render a named slot into a named container. They must **not** call `loadPageDescriptions`, which appends tab containers to `.main-content-area` and would take the page over.
- Authoring is `edit.html?page=character-hub&type=system`. **No editor changes** — `editor-core.js` reads `type` straight off the query string and already branches on `'system'` ([js/editor-core.js:29](js/editor-core.js#L29), [:63](js/editor-core.js#L63)). Using tabs as slots also means the editor's existing tab UI becomes the slot picker for free.

**Consequences for the scope above:** item 4 collapses into "add a slot and render it". Item 5 loses its body-text half; only the `<meta>`/OG marked-region work survives, and that survives because unfurlers do not run JavaScript, which no amount of CMS solves.

**Item 6 splits along the same line.** Authored slots: both hub intros, the Start Here reading path, How to Contribute. Computed in code: roster grid, what-needs-work, recently-updated, tier snapshot, wiki stats, terminology reference. The rule is that anything the owner would want to reword is a slot, and anything derived from data stays code.

## Build order

Chosen so each stage lands in code the next one needs, and so nothing gets done twice:

1. **`robots.txt` + `sitemap.xml` + archiving (items 2, 3, 7).** All three are generator work in `scripts/` — `sitemap.xml` and the tombstone both need `generate-pages.js` to become `status`-aware, so they are one pass, not three.
2. **Hub CMS (items 4, 5).** New table, `owner.html` card, and the marked-region rewrite. Builds on the generator changes above.
3. **Dashboards (item 6).** The largest piece, and entirely front-end.
4. **Accessibility baseline (item 1) last, deliberately.** It touches the router skeleton and therefore every page. Doing it before stage 3 would mean auditing the dashboards' markup separately after writing it; doing it last covers the new markup in the same pass.

## Stage 1 — SHIPPED (2026-08-09)

Items 2, 3 and 7, plus the fold-in. Suite 308 local, `npm run validate` green.

**`robots.txt`** — disallows the staff and authoring tools (`admin`, `owner`, `edit`, `post-editor`, `submissions`, `history`) and points at the sitemap. Stated in the file itself, because it will otherwise be mistaken for one: this is not a security control. Every page listed there is protected by RLS and an RBAC gate; `robots.txt` only asks well-behaved crawlers not to list them.

**`sitemap.xml` + `scripts/generate-sitemap.js`** — 41 URLs, generated from `navigation.json`, wired into `npm run validate` and `npm run generate`. No `<lastmod>`, `<changefreq>` or `<priority>`, deliberately: the honest source for `lastmod` is `site_pages.updated_at`, which is a network read this script does not make, and a build timestamp would mark every page as changed on every run — the exact signal `lastmod` exists to avoid sending. Google ignores the other two outright.

Archived pages cannot leak in, because they never reach `navigation.json`. External links are excluded, since a sitemap may only list URLs on its own origin.

**Archiving now actually archives.** The missing channel was that `fetch-registry.js` drops non-live rows before `generate-pages.js` ever sees them, so the generator could not know a page had been archived:

- `fetch-registry.js` gained `buildArchived()` and now writes `data/archived-pages.json` alongside `navigation.json`. Navigation is written first — it is the higher-blast-radius artifact, so a crash between the two writes leaves the menus correct and only the manifest stale.
- `generate-pages.js` takes the manifest as an optional second input and emits `tombstoneStub()`: HTTP 200, `noindex, follow`, a short explanation, and a link back to the relevant hub. Self-contained apart from the shared stylesheets — no router, no Supabase, no `page_boot`. An archived page has no content to load, and booting the whole stack to render one paragraph is only a way for a tombstone to break.
- Two failure modes refuse rather than guess: a page that is both archived and live raises a problem (the two artifacts are written by the same run, so disagreement means a hand-edit or an interrupted run), and a `NEVER_TOUCH` page never gets a tombstone.
- `20260809000000_page_hide_entry_points.sql` adds `hide_entry_points`, defaulting false so the migration changes no behaviour on its own. No new policy or grant needed — the existing admin policy is table-level and the existing grants are unqualified, so they extend to new columns. Worth stating rather than leaving as an absence, given this project has been caught twice by a policy without a grant.
- `site_utils.js` gained `fetchArchivedPages()` and `isEntryPointHidden()`, next to `fetchNavigationData()` because it answers what that file cannot. Returns `{}` on any failure: a missing manifest must degrade to "nothing is hidden", not blank a roster.

**Still to wire (stage 3):** the manifest's runtime consumers — matchup/counterplay cards, tier-list rows — and the new dashboard widgets, which read `page_data` and `pending_revisions` rather than `navigation.json` and would otherwise surface archived characters. That last point came from the owner mid-build and is the reason the helper exists now rather than later.

## Stage 2a — SHIPPED (2026-08-09): hub prose is CMS content

Item 4, and the body-text half of item 6's authored slots. Suite 322 local.

`20260809000001_hub_content.sql` seeds `page_data` rows for `main-hub`, `character-hub` and `systems-hub`, stored as `page_type: 'system'` so `editor-core.js` edits them with **zero changes**. Tabs are used as named slots. `page_permissions` rows make all three admin-only to submit — which also makes true two statements `20260731000000_page_permissions.sql` explicitly declined to act on, having noted at the time that the dashboards "don't correspond to any real page".

`js/hub_content.js` renders one slot into one container. It deliberately does **not** call `loadPageDescriptions`, which appends tab containers to `.main-content-area` and would take a hub page over, wiping the roster grid with it. A test asserts the roster survives and that no `#system-dynamic-nav` appears.

**The fallback is the load-bearing part.** The existing static markup is left in every hub page and is replaced only when a slot actually has content. These are the first paragraphs on the three most-visited pages, and a brief Supabase outage must not read as "this wiki is empty". Reverting that one guard turns 9 of 14 tests red, so it is pinned rather than assumed. It also makes the pre-merge state correct rather than broken: migrations apply on merge, so until this lands there is no row and visitors get the static copy — expected, not a bug.

**Editing route:** `edit.html?page=main-hub&type=system` (likewise `character-hub`, `systems-hub`). Edits go through the review queue like any other revision rather than writing live, so hub copy changes carry the same audit trail as wiki content; as an admin you approve your own.

**Consequence worth knowing:** `index.html` now loads `description.js` and `internalstyling.js`, which it did not before, because rendering authored blocks requires them. `internalstyling.js` installs a `MutationObserver` on `main` and colorises character names and frame-data terms in `.strategy-paragraph`, `.wiki-text` and `.update-table` cells — all of which the homepage's update-log, FAQ and blog widgets emit. So homepage widget text is now colourised the way the same text already was on `systems/updatelog`, which removes a real inconsistency. The visual baseline for the homepage still passes, so no current content changed; this only shows up when a widget mentions a character or a frame term. The observer terminates rather than looping: `applyInternalStyling` marks each element `is-styled` and its own selector excludes those.

### The fold-in was bigger than it looked

`navigation.json` has **three** consumers in `pagebuilder.js`, not the two found while planning. `buildGlobalSidebarMenu` was the one missed — and the widest-reach of them, since the sidebar renders on every page.

It was caught by a test, not by reading: the first run of `tests/entry-point-escaping.spec.js` fired `window.__xss` even with the roster and directory already fixed. Each of the three fixes was then confirmed load-bearing by reverting it alone and watching exactly one test go red.

Same shape as the `.btn-sys` lesson in memory — a change to shared data needs checking against *every* consumer, not the ones the investigation happened to start from.

- `buildSystemsDirectory`: inline `onclick` replaced with `data-href` + a delegated listener, and category/name/URL escaped.
- `renderFilteredRoster`: name, URL and image escaped.
- `buildGlobalSidebarMenu`: category, name and URL escaped. Its header `onclick` was left alone — it interpolates nothing, so it is static markup rather than the user-influenced-handler pattern.

This stopped being theoretical in v0.10, when `site_pages` became admin-editable through `owner.html`: a page named with an apostrophe broke the directory handler outright.

`tests/entry-point-escaping.spec.js` clicks a real directory button and asserts it navigates. A render-only assertion would have passed against a directory whose buttons all did nothing — the post-editor lesson from v0.9.

### Fold-in candidate found while planning

`buildSystemsDirectory` ([js/pagebuilder.js:459](js/pagebuilder.js#L459)) interpolates `category`, `sys.name` and `sys.url` unescaped into `innerHTML`, and `sys.url` into an inline `onclick` — the exact pattern `CLAUDE.md` says never to use. Not anonymous-reachable, but v0.10 made `site_pages` admin-editable through `owner.html`, so a page name containing a quote now breaks the button. Small fix; belongs with the dashboard work since that code is being touched anyway.

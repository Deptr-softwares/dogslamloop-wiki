## Scope: Owner Tools

The owner-facing half of what was originally one large v0.9. v0.9 shipped the user-visible parts (page router, Discord link previews, blog); this is everything that only the owner sees.

**Framing, owner-confirmed 2026-08-08: this is a maintenance release**, and the changelog should say so plainly rather than dressing up admin plumbing as a feature drop. The one genuinely visible item is **character portraits in Discord link previews** (item 9 below), which the owner explicitly asked to include and call out in the log.

1. **Personnel roster** — a real list of everyone holding a role, not the current blind by-email lookup. Needs a new `list_personnel()` `SECURITY DEFINER` RPC: `user_roles`' only policy is `auth.uid() = user_id`, there is no `profiles` table, and `auth.users` is not PostgREST-reachable, so no client can enumerate today. Fold in the self-XSS cleanup at `js/owner.js:98,100` while that file is open.
2. **Page permissions manager** — `page_permissions` has a public-read policy but no write policy and no write grant, so it has only ever been seeded by migration. **Owner-confirmed: `required_role` becomes real**, which is a live behaviour change — `js/editor-core.js:418` and the INSERT policy in `20260731000000_page_permissions.sql` both ignore it today. Verify against a real trusted-editor session, not just an admin one.
3. **`site_pages` table + the regeneration Action** — deferred from v0.9 R4 deliberately: they exist to serve page create/delete, and building them without it would have meant granting a CI job commit access for a table nothing writes to. Full design (fail-safes, tombstones, the `GITHUB_TOKEN`-doesn't-trigger-workflows trap, anon-key-not-service-role reasoning) is in the v0.9 plan file.
4. **Page create/delete UI** — depends on 3.
5. **Account/data deletion tooling (anonymize)** — owner-confirmed: email and account go, past edits stay attributed to a placeholder so `page_history` survives. **Ships with the `privacy-policy.html` "Deleting your data" rewrite in the same commit** — that page currently promises no self-serve button *yet*, and splitting them means shipping a page that lies about your own privacy practices.
6. **FAQ editing** — `data/faq.json` is static; edits need a commit. Simplest of the content items, so do it first as the template for the rest.
7. **Credits/collaborators** — reconcile `index.html`'s hardcoded `.credits-list` against `systems/collaborators/`'s own `collaborators_data.json`. Two sources of truth today.
8. **Hub text editing** — owner-editable headings/descriptions for the three dashboards, emitted statically by the generator alongside their meta tags.

9. **Character portraits in Discord previews** (owner-confirmed 2026-08-08, and the one item to feature in the changelog). Every page currently unfurls with the site logo; each character page should use its own portrait from `page_data.desc_data.profile.image`.

   **The design constraint, worked out before building so it doesn't derail mid-phase:** the generator must stay deterministic, because `npm run validate` runs `generate-pages --check` in CI and compares committed stubs byte-for-byte. If the generator fetched portraits live at generation time, CI would need network access *and* would fail whenever someone changed a portrait in Supabase after the last commit — the stubs would be legitimately stale through no one's fault.

   So the portrait URL must be a **committed input, not a live fetch**: the Action (item 3) queries Supabase and writes portrait URLs into the committed artifact it already regenerates, and `generate-pages.js` reads only from that file. The generator keeps exactly one input and stays offline; freshness is the Action's job. This is why portraits genuinely ride along with item 3 rather than being independently cheap.

   **Verified against production 2026-08-08, so this is de-risked before it starts:**
   - 22 of 26 `page_data` rows carry `desc_data.profile.image`. The 4 without (`starter_guide`, `hud`, `tierlist`, `terminologies`) are all system pages, which should keep the site logo anyway — so every character page is covered and the fallback is only exercised where it is the correct answer.
   - Portraits are Supabase Storage URLs on a different origin, and fetch cleanly with **no auth header** (`HTTP 200`, `image/webp`) — which is exactly how an unfurler requests them.
   - WebP is already proven to work with Discord: the site logo is WebP and the owner confirmed that embed rendered.

   Still to handle at build time: system pages and any character with no portrait must fall back to the site logo rather than emitting a broken `og:image`.

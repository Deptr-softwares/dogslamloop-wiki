## Features

### 1. Dynamic Roster Icon *(carried feature 7)*

The character icon in the Roster Selection, with the name hidden until hover.
Three states, from the concept image: **Normal** (icon only), **Hover Over —
Transition** (a slit opening under the icon, name partly revealed), **Complete
Transition** (slit at full width, name fully shown).

**The icon sits ON TOP of the solid colour** (owner, 2026-08-24). No border to
draw, and the fallback is free: a character with no icon file shows the solid
colour that is already there today. That is the cheaper of the two options and
the owner picked it for exactly that reason.

**The slit's width comes from the name length ALONE.** The concept originally
varied it by name length *and* WIP status; the owner replaced the WIP half —
see the WIP marker below.

**No data field. Resolve the path client-side.** From `cms_config.pageId` in
`navigation.json`: `honored_one` → `medias/images/HonoredOneIcon.webp`, with
`onerror` hiding the `<img>` so the solid colour shows through.

This is deliberate and it is the whole reason the feature is cheap.
`navigation.json` is generated from `site_pages`, so an icon *column* would
reach the site only via the nightly regeneration job **and** the next release —
the same latency that pushed the Techs flag into `page_data` in v0.15. A
convention plus a fallback has neither problem, and it matches what the owner
asked for: *"the owner only need to upload the Icon."*

**SHIPPED.** All 22 characters resolve.

The plan above said "two renames". Looking at the two files corrected that:

* `HeadoftheHeiIcon.webp` **is** a proper icon — a 750×750 transparent character
  render like the rest of the set — and was referenced by nothing, so it was
  renamed to `HeadHeiIcon.webp`.
* `Boomcat.webp` **is not an icon at all.** It is the meme cat used by the
  homepage's image card at `index.html:276`. Renaming it into the icon slot
  would have put a joke in the roster *and* broken the homepage. The owner's
  call (2026-08-24) was to keep the joke: it is **copied** to
  `BoomcatIcon.webp`, and the original stays where the homepage expects it.

So the fallback path is now exercised only by a character added later, which is
exactly when the owner has not uploaded an icon yet.

**Also verified:** roster cards have no image at all today. `navigation.json`
entries carry no `image` field, so `char.image` in
`js/pagebuilder.js:602` is always undefined and the `roster-card-bg-image`
branch never runs. The concept's *"fall back to the current solid color icon
design"* is describing today's state exactly.

**WIP gets its own icon in a corner of the character icon, like `isEA` does**

### 3. Hidden Characters *(F3)*

A new `isHidden` toggle in the owner tools, **defaulting to false even when the
key is not initialised**.

- The Roster Selection's **"Hide WIP" filter is replaced by "Show Hidden"**.
- `isWip` stays as a separate owner toggle, marking whether a page is done.
- Test with **Boomcat**.

**What "hidden" means here, and what it does not.** The owner clarified
(2026-08-24): these are characters *"only playable in a Private Server —
basically people know about them, they are just hidden away from the Public and
Ranked games."* Publicly known, not secret. That matters, because this repo is
public: a page's name, URL and stub are committed regardless of any flag, so
`isHidden` hides a character from the roster UI and from nothing else.

That is a correct fit for private-server characters. It would **not** be a
correct fit for an unreleased one — see the new item raised at the bottom of
this file.

Removing "Hide WIP" is a small mercy on its own: with `isWip` true everywhere,
that button currently empties the roster.

### 4. Reset the Free Submit Tier List *(F4)*

An owner tool to clear the Free Submit community ranking ahead of a game update
whose balance changes invalidate it.

Migration requirements, per the `supabase-migration` skill: caller check
**inside** the function first (`IS DISTINCT FROM 'admin'` → `RAISE EXCEPTION`
with `ERRCODE '42501'`), `REVOKE ALL FROM PUBLIC` and `FROM anon` before any
`GRANT EXECUTE`, and `SET search_path TO 'public'`. It is destructive and
irreversible, so it goes behind the custom confirm modal, not a browser
`confirm()`.

### Fine-tuning 1 — "Combo Card", not "THEORYBOX"

**This was filed as a missing feature and is not one.** The original list asked
to *"Add a TheoryBox to the Add Blocks button in the Editor."* The Add Block menu
already creates one — it is labelled **`+ Combo Card`** and carries
`data-type="theorybox"` (`js/editor-blocks.js:471`, shipped in v0.15 by
`bd0115e`).

The confusion is a naming mismatch the UI creates itself. The block **type
selector** builds its options from `Object.keys(blockTemplates)` uppercased
(`js/editor-blocks.js:1702-1704`), so it prints the raw template key
`THEORYBOX`, while the menu shows a hand-written friendly name. The owner looked
for the name the dropdown gave them and it was not there under that name.

**"Combo Card" wins** (owner, 2026-08-24). Fix the *selector*, not the menu: give
the type selector a label map so it stops leaking internal template keys. Every
block type has this problem, not just this one — the dropdown reads
`THEORYBOX`, `YOUTUBE`, `PARAGRAPH` because nothing ever mapped them.

### Bug 2 — the workspace stops shaking, 2026-08-25

*Scrolling a long list of blocks no longer jolts up and down.*

**SHIPPED.** The cause was arithmetic, not scroll handling. `js/editor-blocks.js`
runs a virtualization engine: an `IntersectionObserver` that, when a card leaves
the builder's 800px margin, measures it with `getBoundingClientRect()`, pins
`card.style.height` to that number and `display: none`s its children.

`getBoundingClientRect().height` is a **border-box** height. There is no global
`box-sizing` reset in this project, so `.block-card` was laying out as
`content-box` and that one assignment made the card **18px taller than it had
just been** — `0.5rem` of padding top and bottom plus two 1px borders, counted a
second time.

So every card crossing the boundary changed the height of the content *above*
the reader. The browser corrected the scroll position to compensate, the
correction moved other cards across the boundary, and the workspace bounced.
The trace that found it, scrolling in 220px steps:

```
content height   10325 → 10307 → 10289 → 10271 → 10271 → 10289 → 10271 → 10289
scrollTop asked    1320    1540    1760    1980    2200    2420
scrollTop landed   1320    1558    1796    2016    2254    2474   ← drifting
```

After: content height constant at 9947, and `scrollTop` lands exactly where it
is put.

`box-sizing: border-box` on `.block-card` makes the assignment mean what the
code already says. It is the only rule that gives a card an explicit height, and
with `height: auto` the two box models lay out identically — so nothing else
moves. Three tests, two of which fail against the pre-fix code with the owner's
own symptom; the third is a control asserting the engine still unloads cards, so
that deleting the observer cannot be mistaken for a fix.

### Bug 3 — reproduced and diagnosed, 2026-08-24

**Two reports, one defect.** The list filed "cannot preview a Techs tab" (B3)
and "switching views always lands on Overview" (carried bug 5) separately. They
are the same code path, noticed through two different tabs. Same shape as v0.15,
where bugs 3 and 6 turned out to be one bug on the character-state axis.

**The owner's reproduction:** a merged ticket opens in Diff View on **Skills**
(correct — one of its three changed tabs). Clicking **Pending Submission** to see
the real content leaves the strip highlighting Skills while the pane renders the
**Character Overview**. The two halves of the UI disagree about where you are.

**The cause is `js/admin-preview.js:975-981`.** On every switch into `pending`
or `live`, `switchVersionView` resets the content pane to the default tab:

```js
const defaultTabId = window.getDefaultCharacterTabId();
window.getCharacterTabIds({ includeInjected: true, editableOnly: true })
    .filter(tab => tab !== defaultTabId)
    .forEach(tab => { /* hide */ });
const overviewTabToShow = document.getElementById(`tab-${defaultTabId}`);
if (overviewTabToShow) overviewTabToShow.classList.remove('hidden');
```

It never touches the nav strip, so the `.active` button keeps pointing wherever
the reviewer was. Its own comment states the intent — *"Restores the same default
(overview visible, everything else hidden) a fresh revision load already starts
with"* — and that is the mistake: it restores the **content** default without
the **strip**, and a reviewer who navigated to Skills on purpose did not ask to
be sent back.

Techs is caught by the same loop (`editable: true` in the registry), which is
why it can never be previewed: select it, switch to Pending Submission, and the
pane is Overview again.

**The fix** is to re-apply the active tab after the reset via
`setActiveRevisionTab` — reading which button is actually `.active` rather than
assuming the default — so both halves agree and the reviewer keeps their place.
`setActiveRevisionTab` (`js/admin-diff.js:460`) already moves the strip and the
pane together, and exists because of this exact class of bug: *"the old code —
which set `.active` on a nav button and nothing else — left the strip pointing at
one tab while the content pane showed another."*

**SHIPPED.** Seven tests, all driving the real `switchVersionView`. Four failed
against the pre-fix code with the owner's own symptom — *"the strip says skills
but the pane is showing overview"*.

It restores the tab the **strip** names, falling back to the default when the
strip names a tab this page does not have — a real case, since a reviewer
working a queue can read a Techs tab and then open a ticket for a character
with Techs off.

**Falsification found two paths nothing was protecting.** Deleting the
`setActiveRevisionTab` call left all five original tests green, and so did
replacing the pane sweep with a no-op: each was covering for the other, because
in every test the strip already pointed at the right tab and never had to move,
while `setActiveRevisionTab` was quietly doing the sweep's work. Two tests now
pin the cases where each is the only thing left — a strip naming a missing tab,
and no strip at all.

**Ruled out:** the optional-tab flag reaching the preview. `js/admin-preview.js:41-42`
does call `applyOptionalTabsFromPageRow(liveData)`, and 16 characters genuinely
have `techs: true` in production (verified 2026-08-24), so Techs is a live,
configured tab and not an unconfigured one.

## The editor workspace, shipped 2026-08-24/25

**The workspace opens quiet.** Every block and every folder starts collapsed, a
collapsed block says what it holds in one line, folders lost their grey box, the
Hub button survives a collapse, and Media Library moved down beside Add Block
with the styling buttons in two rows.

Four decisions worth not re-deriving:

* **Block collapse state is a WeakSet keyed by the block OBJECT.** Not by index
  — that changes under reorder, insert and delete, so state keyed by position
  hands one block another's. Not a flag on the block — that serialises into
  `desc_data` and ships one author's scroll position to every reader.
* **Folders track what is OPEN, not what is closed.** Inverting the set rather
  than adding a `startCollapsed` flag keeps one source of truth. The rename
  carry-over had to invert with it: it only moved state in the branch that is
  now the default, so renaming an *open* folder would have quietly shut it.
* **The collapsed-block label was not requested and is not optional.** A list
  reading HEADING / PARAGRAPH / LIST identifies nothing, so the author opens
  every block to find one — worse than the wall it replaced.
* **Two rows of styling buttons is a grid, not flex-wrap.** Wrapping gives two
  rows at one pane width and three at another. Asserted at 1600, 1280, 1024.

### Three bugs found while doing it, none of them v0.16's own

1. **The textarea auto-size cap was never applied at render time.** The owner's
   2026-08-17 "grow to fit, then STOP and scroll" fix went into the `input`
   handler only, so a field arrived on screen uncapped with no scrollbar and
   started behaving only once typed in. Both paths share one sizer now.
   *(v0.16 made this visible by rendering everything collapsed, where
   `scrollHeight` is 0 — that part was mine.)*
2. **The mobile-only SHOW PREVIEW button has been visible on desktop.**
   `editor.css` declares its own `.btn-sys { display: inline-flex }` *after*
   `.editor-mobile-preview-btn { display: none }` — equal specificity, later in
   the same file. Fourth instance of the equal-specificity/source-order family
   here. Fixed by scoping to the parent, not reordering.
3. **The folder picker repeated what the indent already said** on a collapsed
   block, and was the widest thing on the row. Removed at the owner's call.

**Three constraints on F5, established 2026-08-24:**

- **`expert` cannot be a role.** `user_roles` has `UNIQUE(user_id)` and a `CHECK`

  has to be a separate column plus a new `can_review_page()` function.

  Needs resolving at design time.
- **Experts get a visible badge** (owner, 2026-08-24) — not only a queue

`[crow_charmer]`, and a Register expert too has `[register, crow_charmer]`. An
expert can open, chat in and review tickets **only** for their own characters —
otherwise the same powers as a reviewer.

# v0.18 — blocks and builders *(inventory, not spec)*

**Features:** SectionedBox (F2) · Seconds Data (F6)

**Fine-tuning:** the Tier List Editor reusing the live Certified Tier List
render, with drag-and-drop inside it (FT1)

**Carried:** multicolor shortcode · box-in-a-list *(feature 9, which fell
through the v0.15/v0.16 split and has been in neither list)*

The two genuinely large builds, kept together and last.

**SectionedBox** is a new block type with two behaviours. Inside a Combos/Techs
group it wraps itself in the same box wrapper a Combo Card uses; **everywhere
else the wrapper is removed** so it blends with ordinary blocks and does not
produce wrapper-on-wrapper styling. It holds an Introduction, Sections, and
Contents in Sections — Introduction and Contents both use the Accordion
recursive logic to hold other Blocks; Sections is add/remove tabs. It renders as
a box with a title, a row of switchable tabs, and the current tab's content
(defaulting to the first). It needs editor, reader, Diff View and admin-preview
representations.

**Seconds Data** sits **next to** Estimated Data, not replacing it (owner,
2026-08-24 — the list had floated replacement, and the owner decided against).
A solid block with no tick divisions, into which seconds are typed. **JJS is
60fps server-side**, so seconds convert to timeline width at 60 frames per
second — `phaseWeight` in `js/framedata.js:79` is where that lands.

**FT1 was abandoned once before, under Gemini.** `js/tierlist.js` still carries
the "LIVE PREVIEW DISABLED" notice from that attempt. The owner's framing this
time is the opposite of the one that failed: reuse the live page's own renderer
and make its contents drag-and-drop, *"instead of trying to re-use the editor
engine and creating new elements to work with."*

**Search stays last**, as it always has.

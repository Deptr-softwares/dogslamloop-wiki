### Character states and the Ultimate tab (this batch)

The item the plan calls the blocker for all character content.

**The data model is additive, and that is the whole trick.** `frame_data.modes`
declares which states exist, `modeData` holds each one's content, and the
reserved id `base` always means the existing top level. No states declared is
one implicit base state — which is exactly what all 22 existing characters
already are, so their pages render byte-identically. The first test in
`tests/character-modes.spec.js` exists to keep it that way.

Declaration is deliberately separate from content, so renaming or reordering
the toggle never rewrites a block, and a state's content is addressed by a
stable id rather than an array position.

**The editor never learns about states.** `currentEditorDescData` and
`currentEditorFrameData` are re-pointed at the active state's slice of the
master objects; every existing writer keeps writing through them unchanged.
The slice is a live reference into the master, so the writes land correctly
with no plumbing, and for the base state the slice *is* the master by identity.

Only two paths had to know: drafts persist the master rather than the slice
(saving the slice would restore a draft containing only that state and silently
drop the base kit), and a state edit ships wrapped once as
`mode` / `<state>::<scope>::<key>`, unwrapped once in `applyDeltaToData`. The
nine scopes in between are untouched, and a base-state edit still emits the
plain scope — so every ticket already sitting in the queue keeps applying.

Both the toggle and the Ultimate tab are **injected at runtime, not generated
into the stub**. That is deliberate and it is the point: a state added in the
editor appears on the page when it is approved, not on the next regeneration
run.

Three supporting changes worth remembering:

- `setupTabs` registers tab groups instead of closing over the id list it was
  given, so the six buttons wired at boot know to hide a tab added after them.
  Without it, clicking Skills left the Ultimate tab open underneath.
- `fetchCloudCharacterData` shares in-flight requests. A character page boot had
  four callers racing for the same row; the states module made five.
- An empty move tab now says so instead of rendering a blank void — a normal
  state to land on once you can switch to a state nobody has written yet.

**The review side was most of the risk.** Every one of these was the same
failure — showing a reviewer the base kit while they approve an edit to
something else: the preview now opens on the state the ticket edits, the diff
compares against that state's live data, and the changed-tab markers and queue
label unwrap so a state edit names its state and section instead of reading
"MODE". The merge compiler scans per state; it scanned only the top level, so a
merge that swept up a state edit found no conflict for it, emitted no delta for
it, and deleted the ticket on success — the same data-loss class as the
compile-time snapshot fixed in PR #40.

One unrelated fix found on the way: the `gallery` page type was missing from
`renderEditorTabNav`'s exclusion list when it shipped in PR #41, so a gallery
editor showed six character tabs that did nothing.

### Phase 0 — one data layer *(retracted 2026-08-10, kept for the reasoning)*

> **This is no longer the plan.** The argument below rests on an inflated
> traffic estimate — 1.4M is the game Discord's membership, not the wiki's
> readership, and the owner corrected it: there will not be 1.4M readers at
> once or even monthly. `navigation.json` is 12.5 KB and cacheable.
>
> The real blocker was never local-vs-cloud. **GitHub Pages serves a URL only
> if a real file sits at that path**, so the page stub is the gate, not the
> JSON. Moving the registry to Supabase would not have fixed the feedback loop.
> The fix worth building is the `404.html` fallback that renders live pages,
> which is now a v0.12 item in its own right.

Groundwork, and first because site-wide search wants one clear answer to "where does data come from", and that answer does not exist yet.

**The problem is not "a mix of local and cloud".** Almost every dataset already has a database table, and that table is already the source of truth. The gap is narrower and worse:

> The browser reads a committed artifact while the owner edits the table.

Those artifacts refresh only when `regenerate.yml` runs. So the loop is: edit → saved to the database → **invisible on the site** until a workflow run that nothing prompts you to do.

That single gap caused three separate confusions on 2026-08-09:

| Symptom | Actual cause |
|---|---|
| Archived "Source Code" button still on both dashboards | `navigation.json` not regenerated |
| Reordered Start Here list did not change the site | `renderHubList` read `site_meta.json`, not the table |
| A tool that said "Live immediately" and was not | the hint was written against the wrong mental model |

The third is the tell. The rule was never written down, so each new renderer picked its source by copying whatever file sat next to it.

**Inventory**

| Artifact | Table behind it | Read at runtime by | Read at build by |
|---|---|---|---|
| `data/navigation.json` | `site_pages` | 6 call sites | `generate-pages`, `generate-sitemap`, `validate-navigation` |
| `data/site_meta.json` | `site_meta` | `site_meta.js` (version/tagline) | `generate-hub-meta` |
| `data/faq.json` | `site_faq` | `home_widgets.js` | — |
| `collaborators_data.json` | `site_collaborators` | collaborators page | — |
| `data/archived-pages.json` | `site_pages.status` | `isEntryPointHidden` | `generate-pages` |
| `data/page-previews.json` | `page_data` | — | `generate-pages` |
| `data/updates.json` | **none** | update log + homepage | — |
| `tierlist_data.json` | `page_data` | tierlist page | — |

**Three rules**

1. **The database is the runtime source for anything the owner can edit.** The committed file is a fallback for when Supabase is unreachable, never the primary. A save must be visible on reload, with no workflow run in between.
2. **Artifacts exist for build consumers and crawlers, not for the browser.** `generate-pages.js` must stay offline and deterministic — CI compares committed stubs byte-for-byte. `sitemap.xml`, `robots.txt` and the OG tags are fetched as files by crawlers and unfurlers that do not run JavaScript. Those keep their artifacts; the browser stops reading them.
3. **One module owns every read.** `js/site_data.js`, where each dataset declares `live` (table first, file fallback) or `static` (file only, with the reason). The policy being emergent rather than declared is exactly what allowed rule 1 to be violated three different ways.

**What changes**

- **`navigation.json` → live.** The big one. Reading `site_pages` at runtime also carries `status`, so **`archived-pages.json` stops being a runtime concern entirely** — archived becomes a filter on the same query, and the "I archived it and it is still there" class disappears. In-memory cache per page load, not `sessionStorage`: one query per page is cheap, and a stale cache is the bug being fixed.
- **`faq.json`, `collaborators_data.json`, `site_meta.json` → live.**
- **`updates.json` → needs a `site_updates` table.** Publishing a changelog currently requires a commit; it is the only owner-facing content still hand-edited in the repo.
- **`page-previews.json`, `archived-pages.json` → static, build-only.** Stated as a decision rather than left as an accident.
- **`generate-*.js` keep reading files.** Unchanged, deliberately.

**Guardrails, so this cannot recur**

- **`scripts/check-data-sources.js`**, wired into `npm run preflight`: fails if any file in `js/` reads a `data/*.json` that has a table behind it, unless it goes through `js/site_data.js`. Mechanical, and it would have caught the `renderHubList` bug before it shipped.
- **Source-of-truth tests.** The existing specs mocked the JSON file and asserted the page rendered the mock — which passes whether the page reads the file or the table, so it only ever proved the renderer works. The pattern that works is to make the two sources **disagree** and assert the table wins. Already applied in `tests/hub-content-source.spec.js`; extend to every live dataset.
- **`npm run preflight`** = `validate` + `test` + the new check, so there is one command rather than a list to remember.

**What this is not:** "move everything to the cloud". Four datasets must stay as files, and moving them would break CI determinism or make the site invisible to Discord and Google. The goal is one clear rule per dataset, not one storage location for all of them.

## Process, changed after v0.11

v0.11 shipped correctly but the session was messy: three things were built and then discarded because the owner's request was misread — CMS-slot editing for hub prose, the iframe live preview, and completeness-driven "pages that need work". In every case the correct reading was already present in the owner's first message.

Two changes:

1. **Write the scope back before building.** One page, in the owner's own words, confirmed before any code. Cheap, and it catches a misread while it still costs nothing.
2. **"What to check before pushing" is tooling, not memory.** `npm run preflight` above. The owner should not be the one finding a bug that a mechanical check could catch — both v0.11 follow-up bugs were found by the owner on the live site.

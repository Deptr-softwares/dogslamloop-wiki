## Security hotfix (pre-v0.9): privilege escalation via `assign_role_by_email`

**Not part of v0.9's scope** — found while researching the role model for the personnel-roster item, fixed and shipped on its own. **Deliberately not in `data/updates.json` and not announced on Discord**, on the owner's instruction: internal record only.

**The hole.** `public.assign_role_by_email(target_email, assigned_role)` is `SECURITY DEFINER` — it runs with the database owner's rights, which it needs in order to read `auth.users` and write `user_roles`. But it never checked *who was calling it*. Postgres grants `EXECUTE` on a new function to `PUBLIC` by default, and no migration ever revoked that, so the grant reached `anon` — and the anon key is public by design, shipping in `js/site_utils.js` and therefore present in the page source of every page on the site.

**Confirmed exploitable against production before the fix**, not merely suspected from reading the code: an unauthenticated `POST /rest/v1/rpc/assign_role_by_email` carrying only the public anon key returned `HTTP 200` and the function's own `"Error: User with this email not found."` string. The probe used a deliberately nonexistent email so the function returned before reaching any `DELETE`/`INSERT` — nothing was modified to establish this.

**Impact had it been used**: anyone who knew or guessed an account's email address could set any role on it — granting themselves `admin` (full moderation access, owner tools, and direct `page_data` writes via the "Admin Write Live Data" policy), or revoking the owner's own `admin` row to lock them out of their own site. No login required.

**Age**: present since the original schema (`20260727000000_remote_schema.sql:58`). The v0.6 role-model rewrite (`20260801000000_role_model_fix.sql:92`) changed the body from a toggle to a set-operation to fix an unrelated multi-role bug, and carried the missing guard forward unchanged.

**Not exploited.** The owner audited `user_roles` immediately and confirmed it holds exactly the expected 9 trusted people plus 1 test account — this was found before anyone used it.

**Scope of exposure checked, not assumed**: the schema's other four `SECURITY DEFINER` functions were reviewed. `get_my_role()` only ever returns the caller's own role; `archive_page_version`, `check_revision_rate_limit` and `rls_auto_enable` are triggers rather than client-callable RPCs. `assign_role_by_email` was the only exposed one.

**Fix** — `supabase/migrations/20260807000001_secure_assign_role_by_email.sql`, three layers so no single mistake re-opens it:
1. `REVOKE ALL ... FROM PUBLIC`/`anon`/`authenticated` — closes the actual inherited grant.
2. An internal caller check (`get_my_role() IS DISTINCT FROM 'admin'` → `RAISE EXCEPTION`, errcode `42501`). This is what makes a future stray `GRANT` non-fatal, and additionally stops an *authenticated* non-admin (a contributor with a valid session) from escalating. `auth.uid()` resolves to the caller inside a `SECURITY DEFINER` function — it reads the request's JWT claims, not the definer's identity — which is the same mechanism every existing RLS policy already relies on.
3. `SET search_path TO 'public'`, which every other `SECURITY DEFINER` function in this schema already pins and this one never did.
4. An explicit `GRANT EXECUTE TO authenticated` so `owner.html`'s legitimate use keeps working and the grant is stated rather than silently inherited.

**Verification**: Playwright cannot reach this — every auth spec in the repo mocks Supabase and never touches real Postgres. Verified directly against production after the migration auto-applied on merge: the original anon probe must now be refused rather than returning `HTTP 200`, and an admin must still be able to assign a role through `owner.html` (the real regression risk being over-tightening and breaking the only legitimate caller). Full suite 168/168 (no JS changed).

**Noted, deliberately not fixed here**: `js/owner.js:98,100` interpolate `error.message` and `data` into `innerHTML` unescaped, and `data` echoes the email the admin typed. That is self-XSS by an admin on an admin-only page using their own input — negligible, and folding it into a security migration's commit would muddy an audit trail that should stay surgical. Worth cleaning up during v0.9's owner-page work, when that file is being rewritten anyway.

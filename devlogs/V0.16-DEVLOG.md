### 1. Dynamic Roster Icon *(carried feature 7)*

The character icon in the Roster Selection, with the name hidden until hover.
Three states, from the concept image: **Normal** (icon only), **Hover Over —
Transition** (a slit opening under the icon, name partly revealed), **Complete
Transition** (slit at full width, name fully shown).

**The icon sits ON TOP of the solid colour** (owner, 2026-08-24). No border to
draw, and the fallback is free: a character with no icon file shows the solid
colour that is already there today. That is the cheaper of the two options and
the owner picked it for exactly that reason.

**The slit's width comes from the name length ALONE.** The concept originally
varied it by name length *and* WIP status; the owner replaced the WIP half —
see the WIP marker below.

**No data field. Resolve the path client-side.** From `cms_config.pageId` in
`navigation.json`: `honored_one` → `medias/images/HonoredOneIcon.webp`, with
`onerror` hiding the `<img>` so the solid colour shows through.

This is deliberate and it is the whole reason the feature is cheap.
`navigation.json` is generated from `site_pages`, so an icon *column* would
reach the site only via the nightly regeneration job **and** the next release —
the same latency that pushed the Techs flag into `page_data` in v0.15. A
convention plus a fallback has neither problem, and it matches what the owner
asked for: *"the owner only need to upload the Icon."*

**SHIPPED.** All 22 characters resolve.

The plan above said "two renames". Looking at the two files corrected that:

* `HeadoftheHeiIcon.webp` **is** a proper icon — a 750×750 transparent character
  render like the rest of the set — and was referenced by nothing, so it was
  renamed to `HeadHeiIcon.webp`.
* `Boomcat.webp` **is not an icon at all.** It is the meme cat used by the
  homepage's image card at `index.html:276`. Renaming it into the icon slot
  would have put a joke in the roster *and* broken the homepage. The owner's
  call (2026-08-24) was to keep the joke: it is **copied** to
  `BoomcatIcon.webp`, and the original stays where the homepage expects it.

So the fallback path is now exercised only by a character added later, which is
exactly when the owner has not uploaded an icon yet.

**Also verified:** roster cards have no image at all today. `navigation.json`
entries carry no `image` field, so `char.image` in
`js/pagebuilder.js:602` is always undefined and the `roster-card-bg-image`
branch never runs. The concept's *"fall back to the current solid color icon
design"* is describing today's state exactly.

### 3. Hidden Characters *(F3)*

A new `isHidden` toggle in the owner tools, **defaulting to false even when the
key is not initialised**.

- The Roster Selection's **"Hide WIP" filter is replaced by "Show Hidden"**.
- `isWip` stays as a separate owner toggle, marking whether a page is done.
- Test with **Boomcat**.

**What "hidden" means here, and what it does not.** The owner clarified
(2026-08-24): these are characters *"only playable in a Private Server —
basically people know about them, they are just hidden away from the Public and
Ranked games."* Publicly known, not secret. That matters, because this repo is
public: a page's name, URL and stub are committed regardless of any flag, so
`isHidden` hides a character from the roster UI and from nothing else.

That is a correct fit for private-server characters. It would **not** be a
correct fit for an unreleased one — see the new item raised at the bottom of
this file.

Removing "Hide WIP" is a small mercy on its own: with `isWip` true everywhere,
that button currently empties the roster.

**SHIPPED.** One column, `NOT NULL DEFAULT false`, so all 52 existing rows keep
the visibility they already have with no backfill — behaviour-preserving by
construction rather than by assertion. **No policy and no grant**: `site_pages`
is granted `ON TABLE` rather than column by column (checked in
`20260808000003_site_pages.sql`), so a new column inherits what is there, and
adding one would only be a second place for the two to disagree.

`Show Hidden` has the **opposite polarity** to the filters beside it — hidden
characters are out by default and the toggle lets them in — which is why it is
named the way it is rather than "Hide Hidden".

A test asserts that hiding is a roster filter **and nothing more**: the stub is
still committed, and the entry is still in the `navigation.json` the page
fetched. The next reader will assume otherwise, and this is a public repo.

**The usual migration consequence applies.** `is_hidden` does not exist in
production until the release merges to `main`, so the owner's Page Details card
will error on that column until then. Expected, per the deploy model — not a
regression to chase.

### 4. Reset the Free Submit Tier List *(F4)*

An owner tool to clear the Free Submit community ranking ahead of a game update
whose balance changes invalidate it.

Migration requirements, per the `supabase-migration` skill: caller check
**inside** the function first (`IS DISTINCT FROM 'admin'` → `RAISE EXCEPTION`
with `ERRCODE '42501'`), `REVOKE ALL FROM PUBLIC` and `FROM anon` before any
`GRANT EXECUTE`, and `SET search_path TO 'public'`. It is destructive and
irreversible, so it goes behind the custom confirm modal, not a browser
`confirm()`.

**SHIPPED.** An RPC rather than a client `DELETE`. `free_submit_votes` has no
DELETE grant for anyone but a voter removing their own row, and it should stay
that way: a blanket admin DELETE policy would be a **standing capability**
reachable from any session holding an admin token, protecting nothing. One
function that checks the caller and does one specific thing is narrower.

Every item on the migration checklist is met, and the two that carry history
here are the caller check coming **before** anything is read or written — a
check after the DELETE is not a check — and `REVOKE ... FROM PUBLIC` *and* `FROM
anon` before the grant, since creating a function grants PUBLIC by default and
this project has already had one unauthenticated escalation from exactly that.

**`DELETE`, not `TRUNCATE`**: MVCC-safe alongside a concurrent
`submit_tier_votes`, and it does not take the table lock that would block every
voter mid-ballot. It returns the row count, because *"done"* on a destructive
action tells the owner nothing about whether it did what they meant.

**`free_submit_tiers` is left alone** — the six tiers and their colours are the
scale the ranking is expressed in, not the ranking. Clearing it would leave the
page with nothing to sort by, and it is not what "reset the list" means.

The button sits in its own row behind a dashed red rule. It is otherwise the
same size in the same column as SAVE SETTINGS, and the red fill would be the
only thing between "save my settings" and "delete every vote".

### Fine-tuning 1 — "Combo Card", not "THEORYBOX"

**This was filed as a missing feature and is not one.** The original list asked
to *"Add a TheoryBox to the Add Blocks button in the Editor."* The Add Block menu
already creates one — it is labelled **`+ Combo Card`** and carries
`data-type="theorybox"` (`js/editor-blocks.js:471`, shipped in v0.15 by
`bd0115e`).

The confusion is a naming mismatch the UI creates itself. The block **type
selector** builds its options from `Object.keys(blockTemplates)` uppercased
(`js/editor-blocks.js:1702-1704`), so it prints the raw template key
`THEORYBOX`, while the menu shows a hand-written friendly name. The owner looked
for the name the dropdown gave them and it was not there under that name.

**"Combo Card" wins** (owner, 2026-08-24). Fix the *selector*, not the menu: give
the type selector a label map so it stops leaking internal template keys. Every
block type has this problem, not just this one — the dropdown reads
`THEORYBOX`, `YOUTUBE`, `PARAGRAPH` because nothing ever mapped them.

**SHIPPED.** One `BLOCK_TYPE_LABELS` map now feeds both surfaces, and the Add
Block menu is **generated from it** rather than hand-written — which is what
stops the two drifting apart a second time, since hand-written names beside
derived ones is the arrangement that caused this. Option values stay the template
keys, so the dropdown still edits what it always did. `blockTypeLabel()` falls
back to the key, so a template added without a label gets an ugly name rather
than vanishing from the dropdown that edits it.

The test that matters is the **two-way** one: the menu and the dropdown must
offer the same set of types *and* the same name for each. A one-directional check
would have passed happily while the dropdown said `THEORYBOX` and the menu said
Combo Card — which is exactly the state that was shipped.

### Bug 2 — the workspace stops shaking, 2026-08-25

*Scrolling a long list of blocks no longer jolts up and down.*

**SHIPPED.** The cause was arithmetic, not scroll handling. `js/editor-blocks.js`
runs a virtualization engine: an `IntersectionObserver` that, when a card leaves
the builder's 800px margin, measures it with `getBoundingClientRect()`, pins
`card.style.height` to that number and `display: none`s its children.

`getBoundingClientRect().height` is a **border-box** height. There is no global
`box-sizing` reset in this project, so `.block-card` was laying out as
`content-box` and that one assignment made the card **18px taller than it had
just been** — `0.5rem` of padding top and bottom plus two 1px borders, counted a
second time.

So every card crossing the boundary changed the height of the content *above*
the reader. The browser corrected the scroll position to compensate, the
correction moved other cards across the boundary, and the workspace bounced.
The trace that found it, scrolling in 220px steps:

```
content height   10325 → 10307 → 10289 → 10271 → 10271 → 10289 → 10271 → 10289
scrollTop asked    1320    1540    1760    1980    2200    2420
scrollTop landed   1320    1558    1796    2016    2254    2474   ← drifting
```

After: content height constant at 9947, and `scrollTop` lands exactly where it
is put.

`box-sizing: border-box` on `.block-card` makes the assignment mean what the
code already says. It is the only rule that gives a card an explicit height, and
with `height: auto` the two box models lay out identically — so nothing else
moves. Three tests, two of which fail against the pre-fix code with the owner's
own symptom; the third is a control asserting the engine still unloads cards, so
that deleting the observer cannot be mistaken for a fix.

### Bug 1 — SHIPPED, 2026-08-25, after a screen recording found it

*Typing in a long paragraph no longer drags the workspace upward away from what
you are writing.*

**The owner recorded it** (`Bug Showcase.mp4`, 33s, decoded frame by frame in a
browser because the only `ffmpeg` on this machine is Playwright's stripped
build). The recording showed the one variable twelve probes had all missed:
**the workspace was scrolled to the very bottom**, with the block they were
typing in as the last thing in the list.

**The cause.** Measuring a textarea means collapsing it first — `height: auto` on
a textarea is its `rows` height, *not* its content height, so `scrollHeight` only
reports the real content once the box is out of the way. That collapse is visible
to the scroll container for one layout pass. When the contributor is at the
bottom of the range, the container's scroll range shrinks by whatever the field
just lost, **the browser clamps `scrollTop` to the new maximum, and restoring the
height does not restore the scroll.** The clamp is permanent, and it happens once
per keystroke — the owner's *"every single letter type just keep moving me
upward"*.

Measured on a 211px field: `scrollTop` **349 → 188** on the first character,
exactly the **161px** the field lost collapsing to its 50px minimum.

**The fix** puts the scroll position back after the measurement, read and written
in the same task so no frame is painted in between — an invisible restore rather
than a correction the reader sees. `autoSizeEditorTextareasIn` wraps its whole
sweep in one save/restore rather than one per field, because sizing a list
collapses each in turn and the clamp compounds.

**Why the twelve probes missed it, and what to take from that.** Every one of
them typed into a block with content *below* it. There the scroll range has slack
to shrink into, so nothing moves, and the probe passes while the bug is fully
present two hundred pixels further down the same page. The missing variable was
not the page, the block type, the renderer version or the browser — it was
**where in the scroll range the contributor was standing**. The regression test
asserts its own setup is really pinned to the bottom, so it cannot drift back
into testing the case that never broke.

The table below is kept as the record of what was eliminated, and of a probe that
lied convincingly.

#### The twelve that did not reproduce it

| Scenario | Result |
|---|---|
| Synthetic `input` on a capped textarea | inner scroll held at 440 |
| Programmatic `focus()` on an off-screen card | **jumped 426px** — artifact of the probe, see below |
| Real mouse click, then real typing at the end | held at 1948 |
| Same, against the **pre-#129** renderer served over the live page | held at 1986 |
| Typing that genuinely grows the card (175px → 252px) among 25 blocks | held at 5017 |
| Same, virtualizer disconnected | unchanged |
| The real Writing Guide (system page) | held at 688 |
| Caret 60 lines deep in a 120-line block, then typing | inner scroll held at 787 |

**The one jump was my own test harness.** `element.focus()` scrolls its element
into view; a mouse click does not, because the element is already where the
pointer is. That probe reported a clean 426px teleport and would have justified
a fix for something no contributor can trigger.

What this rules out: the virtualizer, the autosize, the 400ms preview debounce,
the block list being rebuilt under the caret, and the pre-#129 renderer. **This
one needs the owner's specific page and block type** — reported as "a block with
a lot of content", and the eight above all had that.

#### The owner checked it on Live Server, 2026-08-25: already fixed

They suggested the collapse memory or the scrollbar fix from the previous pass.
Both were tested directly, and **neither is the mechanism**:

- **The scrollbar.** A faithful pre-#129 world — old renderer served over the
  live page *and* the `overflow: hidden` rule put back, which the earlier probe
  had missed — behaves identically to this branch. Caret walked 43 lines deep:
  inner scroll `467` then, `468` now; both held steady through typing; the wheel
  reached `767` / `768`. The field was always scrollable. Restoring the
  scrollbar is a real fix for the combo card and the QA changelog; it is not
  what fixed this.
- **The virtualizer, seen while typing rather than while scrolling.** 40 blocks,
  all expanded as they were pre-#129, caret in a block growing a line at a time
  until cards crossed the observer's margin (33 → 34 unloaded). Workspace
  `scrollTop` held at `8279` for fourteen insertions under `content-box`, and at
  `7937` under `border-box`. The growth happens *below* the caret, where scroll
  anchoring handles it correctly. Bug 1 is **not** bug 2 seen from another angle.

  That run did confirm bug 2's arithmetic independently, though: the two
  workspaces differed by exactly **594px = 33 unloaded cards × 18px**.
- **A re-render dropping the scroll position** — the classic where
  `innerHTML = ''` collapses the container and clamps `scrollTop` to 0.
  `renderBlockList()` at `scrollTop` 6000 returns 6000, immediately and after
  settling.

**All twelve shared one assumption nobody had written down**: that the block
being edited had content below it. Under that assumption the scroll range has
slack, the collapse costs nothing, and the bug is invisible — which is why the
count kept going up without the confidence going anywhere.

**Two things worth keeping from this.**

*A "cannot reproduce" is a statement about the probes, not about the bug.* This
one was closed by observation on 2026-08-25 and reopened by a video on the same
day, and both readings were reasonable on the evidence available. The mistake
was not the closure — it was that twelve near-identical probes were counted as
twelve pieces of evidence when they were really one, repeated with the variable
that mattered held constant throughout.

*One probe lied convincingly.* Programmatic `element.focus()` scrolls its element
into view where a mouse click does not, so it reported a clean 426px teleport for
something no contributor can trigger. It was the closest thing to a reproduction
in the whole set and it was pointing at nothing. Had it been trusted, the fix
would have gone into the wrong function and the real bug would have survived it.

### Bug 6 — Reviewer never received the Trusted Editor perks

**Raised by the owner 2026-08-25, checked, not yet built.** The decision was made
a while ago that a reviewer has a trusted editor's perks. It reached exactly one
of the three.

| Perk | Reviewer? | Where |
|---|---|---|
| Submit to a `trusted_editor`-restricted page | **No** | RLS `Guests can submit revisions`, `20260808000006_role_cleanup.sql:57`, and the client mirror at `js/editor-core.js:603` |
| Vote discount (+1 instead of +2 to merge) | **No** | `js/admin-queue.js:178`, `js/admin-tickets.js:16` |
| Submission cooldown bypass | **Yes** | `check_revision_rate_limit()` — `caller_role IN ('trusted_editor','reviewer','admin')` |

The restricted-page gate reads:

```sql
get_my_role() = 'admin'
OR (pp.required_role = 'trusted_editor' AND get_my_role() = 'trusted_editor')
```

A reviewer matches neither branch. What they actually experience: the Edit button
appears (that is `edit_role`, a different gate), they write the whole edit, and
Submit refuses with *"READ ONLY: you require the 'Trusted Editor' or 'Admin'
role."* The work is done before the wall.

**Both layers must change together.** Fixing only the policy leaves the client
refusing before a request is sent; fixing only the client swaps a message for a
raw Postgres rejection.

**SHIPPED, 2026-08-25.** Both decisions were the owner's:

* **A shared rank ladder**, not `'reviewer'` appended to three lists.
  `role_rank()` in SQL and `window.roleRank`/`roleMeets` in JS — deliberately
  the same ladder rather than shared code, since SQL cannot call the JS and a
  perk enforced only in the browser is a suggestion. **The database is the
  boundary; the JS decides what the interface shows**, and a test pins the two
  sets of numbers together, because two ladders that disagree is worse than the
  literal lists this replaced.
* **Admin gets the vote discount too.** Consistent with a ladder: at or above
  `trusted_editor`.

The gate is now `role_rank(get_my_role()) >= role_rank(pp.required_role)`, so a
page asking for `trusted_editor` admits admin, reviewer and trusted_editor while
one asking for `admin` still admits only admin. **That second line is the one
worth checking twice** and it has its own test — widening the trusted_editor
gate must not widen the admin one.

Both ladders are **total**: unknown, empty and NULL all rank 0, because
`NULL >= anything` is NULL — the same trap this codebase hits with `<>` against
`get_my_role()`, and the SQL gets it from `ELSE 0`.

**The vote discount is a workflow convention, not a security boundary**, and
that is worth stating plainly since the change looks like a permission
relaxation. It decides whether the MERGE button renders; the write behind it is
gated separately by `Admin Write Live Data`. Nobody gained access they did not
have. The ticket note now reads *"Staff Perk Applied"* rather than *"Trusted
Editor Perk"*, since a reviewer reading the old wording on their own ticket
would reasonably wonder whose perk they were getting.

**Originally recorded as three things to settle. The third stands:**

1. **`admin` has no vote discount either** — `isTrusted` tests one literal
   string, so an admin's own submission also needs +2. Probably moot since they
   can force-approve, but it is the same shape and should be settled in one pass.
2. **There is no role hierarchy anywhere.** `author_roles` is an array, but
   `UNIQUE(user_id)` means it always holds one item, so `.includes(...)` is just
   `role === ...`. Every perk is an independent literal list, which is precisely
   why granting reviewer one perk granted none of the others. `list_personnel`
   already ranks roles (`'trusted_editor' THEN 3`); the perks do not use it.
   Appending `'reviewer'` to three lists works; a shared rank helper is what
   stops the fourth perk repeating this.
3. **This needs a migration**, so it is the second v0.16 item with SQL and gets a
   real Supabase preview. Migrations apply on merge to `main`, so reviewer
   submissions to restricted pages stay broken between the migration landing and
   the release.

### Bug 5 — intercepting your own submission, 2026-08-25

*Editing your own pending submission opens the right kind of page again.*

**SHIPPED.** The EDIT button built `edit.html?char=<id>&editTicket=<id>` and never
passed the page type. `js/editor-core.js` reads `urlParams.get('type') ||
'character'`, so a submission against a **system, tool or tier list** page opened
the editor in character mode: a character tab strip over system data, and the
intercepted ticket rendering into nothing. The page id survived either way, which
is why this looked like it worked right up until the page was not a character.

`js/admin-actions.js` had the identical omission, so a reviewer intercepting the
same ticket from `admin.html` hit it too. Both fixed, duplicated rather than
shared — `submissions.js` is not loaded on `admin.html`. The tab logic stays
different on purpose: the reviewer's strip is the honest target there, and the
contributor's page has no strip to read.

The character deep link is now guarded to character pages. `matchups`,
`counterplay` and `m1s::5H` are character vocabulary; a system page's scopes are
`system_tab` / `system_section` and its editor builds its own tabs, so deriving a
character tab for one was inventing a destination.

**RLS was checked first and is not involved** — the obvious suspect, since this
is a permission-shaped symptom. `Authors can view own revisions` (SELECT) and
`Authors can update own pending revisions` (UPDATE, non-final statuses only) both
exist, and `pending_revisions` carries `GRANT ALL` to `authenticated`. Verified in
`supabase/migrations`, not assumed.

### Bug 4 — the purple tag stays in its card, 2026-08-25

*A ticket for one section of a system tab no longer pushes its tag off the side
of the card.*

**SHIPPED.** `Badges.css` gives every `.update-badge` `white-space: nowrap` —
correct for the hand-written ones (`WIP`, `EA`, `TICKET OPEN`, `S`/`M`/`L`), and
it stays. `.badge-patch-delta` is the only badge whose text is not written by
hand: it carries `[PATCH: <scope>: <key>]`, and a system-section key is
`${tabKey}::${secKey}` built from two slugified titles, so it runs past 80
characters.

Measured before the fix: **402px wide inside a 190px column, and the same 402px
inside a 320px one** — `nowrap` means it never shrinks at all — hanging 229px
past the card's right edge.

`overflow-wrap: anywhere` rather than `break-word` on purpose: only `anywhere`
also shrinks the element's min-content size, which is what lets it yield as a
flex item in `.admin-queue-badges-row`. `break-word` would wrap the text and
still reserve the full unbroken width.

Scoped to the one badge, which has exactly one consumer
(`js/admin-queue.js:135`). The new tests assert the short badges still compute
`nowrap`, so a fix that reached for the shared base cannot pass them.

**The second surface was checked and needs nothing.** `history.js:121` renders
the same tag with its own inline styles and no `nowrap`, so it already wraps —
swept six widths down to 390px with a real system-section key and it never
overflowed. The only case that broke it there needed underscores, which
`slugifySystemKey` cannot produce (`[^a-z0-9]+` → `-`).

### Bug 3 — reproduced and diagnosed, 2026-08-24

**Two reports, one defect.** The list filed "cannot preview a Techs tab" (B3)
and "switching views always lands on Overview" (carried bug 5) separately. They
are the same code path, noticed through two different tabs. Same shape as v0.15,
where bugs 3 and 6 turned out to be one bug on the character-state axis.

**The owner's reproduction:** a merged ticket opens in Diff View on **Skills**
(correct — one of its three changed tabs). Clicking **Pending Submission** to see
the real content leaves the strip highlighting Skills while the pane renders the
**Character Overview**. The two halves of the UI disagree about where you are.

**The cause is `js/admin-preview.js:975-981`.** On every switch into `pending`
or `live`, `switchVersionView` resets the content pane to the default tab:

```js
const defaultTabId = window.getDefaultCharacterTabId();
window.getCharacterTabIds({ includeInjected: true, editableOnly: true })
    .filter(tab => tab !== defaultTabId)
    .forEach(tab => { /* hide */ });
const overviewTabToShow = document.getElementById(`tab-${defaultTabId}`);
if (overviewTabToShow) overviewTabToShow.classList.remove('hidden');
```

It never touches the nav strip, so the `.active` button keeps pointing wherever
the reviewer was. Its own comment states the intent — *"Restores the same default
(overview visible, everything else hidden) a fresh revision load already starts
with"* — and that is the mistake: it restores the **content** default without
the **strip**, and a reviewer who navigated to Skills on purpose did not ask to
be sent back.

Techs is caught by the same loop (`editable: true` in the registry), which is
why it can never be previewed: select it, switch to Pending Submission, and the
pane is Overview again.

**The fix** is to re-apply the active tab after the reset via
`setActiveRevisionTab` — reading which button is actually `.active` rather than
assuming the default — so both halves agree and the reviewer keeps their place.
`setActiveRevisionTab` (`js/admin-diff.js:460`) already moves the strip and the
pane together, and exists because of this exact class of bug: *"the old code —
which set `.active` on a nav button and nothing else — left the strip pointing at
one tab while the content pane showed another."*

**SHIPPED.** Seven tests, all driving the real `switchVersionView`. Four failed
against the pre-fix code with the owner's own symptom — *"the strip says skills
but the pane is showing overview"*.

It restores the tab the **strip** names, falling back to the default when the
strip names a tab this page does not have — a real case, since a reviewer
working a queue can read a Techs tab and then open a ticket for a character
with Techs off.

**Falsification found two paths nothing was protecting.** Deleting the
`setActiveRevisionTab` call left all five original tests green, and so did
replacing the pane sweep with a no-op: each was covering for the other, because
in every test the strip already pointed at the right tab and never had to move,
while `setActiveRevisionTab` was quietly doing the sweep's work. Two tests now
pin the cases where each is the only thing left — a strip naming a missing tab,
and no strip at all.

**Ruled out:** the optional-tab flag reaching the preview. `js/admin-preview.js:41-42`
does call `applyOptionalTabsFromPageRow(liveData)`, and 16 characters genuinely
have `techs: true` in production (verified 2026-08-24), so Techs is a live,
configured tab and not an unconfigured one.

## The editor workspace, shipped 2026-08-24/25

**The workspace opens quiet.** Every block and every folder starts collapsed, a
collapsed block says what it holds in one line, folders lost their grey box, the
Hub button survives a collapse, and Media Library moved down beside Add Block
with the styling buttons in two rows.

Four decisions worth not re-deriving:

* **Block collapse state is a WeakSet keyed by the block OBJECT.** Not by index
  — that changes under reorder, insert and delete, so state keyed by position
  hands one block another's. Not a flag on the block — that serialises into
  `desc_data` and ships one author's scroll position to every reader.
* **Folders track what is OPEN, not what is closed.** Inverting the set rather
  than adding a `startCollapsed` flag keeps one source of truth. The rename
  carry-over had to invert with it: it only moved state in the branch that is
  now the default, so renaming an *open* folder would have quietly shut it.
* **The collapsed-block label was not requested and is not optional.** A list
  reading HEADING / PARAGRAPH / LIST identifies nothing, so the author opens
  every block to find one — worse than the wall it replaced.
* **Two rows of styling buttons is a grid, not flex-wrap.** Wrapping gives two
  rows at one pane width and three at another. Asserted at 1600, 1280, 1024.

**Why profiles came back, and it is not only scheduling.** The inventory's
argument was that the expert, profiles and uploader credit all want *a place
where a person exists on this site*. Checking the schema for what that place
currently is:

| Table | How it names a person |
|---|---|
| `pending_revisions` | `author_name text` — copied in by the submitting page |
| `page_discussions` | `author_name` — set server-side by a trigger, never trusted from the client |
| `moderation_log` | `moderator_name text NOT NULL DEFAULT ''` |

**There is no person record anywhere.** Every name is denormalized onto the row
that needed it, and `getDisplayName` (`js/site_utils.js:1415`) reads
`session.user.user_metadata` — which only exists for *the viewer's own session*.
A name for anybody else is not queryable at all.

So an expert badge and a profile want the same missing thing: **one
`user_id`-keyed, publicly readable person record, with the RLS policy and anon
grant to match.** Building `page_experts` and that table in the same version
means one design pass over "who is this person and who may see them", rather
than two that have to agree later. Uploader credit still rides on it in v0.18 —
that argument is not spent, only partly spent.

**Design note carried forward:** `anonymize_user_by_email` hard-deletes the
`auth.users` row, which is why `pending_revisions.author_id` had to drop
`NOT NULL` and `page_discussions.author_id` is `ON DELETE SET NULL`. A profiles
table is the third instance of that trap. `ON DELETE CASCADE` on its `user_id`,
the same as `page_experts`.

## The precedent: a capability, not a role

The owner's *"moderators not tied to a set role"* is **`can_moderate`**, v0.14
item 2 (`20260813000001_thread_moderation.sql:36`):

```sql
ALTER TABLE "public"."user_roles"
    ADD COLUMN IF NOT EXISTS "can_moderate" boolean NOT NULL DEFAULT false;
```

> *'Thread moderation without full reviewer rights. Independent of role: admin
> and reviewer can always moderate, and this grants it to anyone else.'*

Its comment states the rule the whole schema follows: **"A column, never a second
role."** `user_roles` has `UNIQUE(user_id)` deliberately — two rows once broke
`get_my_role()` with *"more than one row returned by a subquery"*, which broke
that user's access to everything, not just the thing the second role was for.

Two capabilities exist already: `bypass_cooldown` (v0.13) and `can_moderate`
(v0.14). **The expert is the third, and it is the same idea one dimension
further out** — not "can this person moderate" but "can this person review *this
page*".

## The blocker the capability pattern does NOT solve

```sql
"role" text NOT NULL
CHECK (role = ANY (ARRAY['admin','reviewer','trusted_editor','viewer']))
```

`role` is **NOT NULL**. Every `user_roles` row therefore carries one of those
four, which means a capability column can only be granted to somebody who
*already holds a role*. `set_user_capability` says this outright: *"Deliberately
cannot create a row. A capability is an extra on top of a role."*

So `can_moderate` is independent of *which* role you hold — but not of holding
one. **That is the whole of the "default to the authenticated role" problem**
the source list flagged and could not resolve: an expert who is simply a
knowledgeable player has no role, and there is no value that column can take for
them.

## The resolution: a table, not a column *(owner's call, 2026-08-25)*

```sql
CREATE TABLE public.page_experts (
    user_id uuid NOT NULL REFERENCES auth.users(id)            ON DELETE CASCADE,
    page_id text NOT NULL REFERENCES public.site_pages(page_id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, page_id)
);
```

Three reasons, in order of weight:

1. **It dissolves the CHECK problem entirely.** Its own table, its own row — no
   role required, so there is nothing to default to.
2. **Referential integrity.** `page_id` is owner-editable. A `text[]` of ids
   rots silently when a page is renamed; a foreign key cannot.
   `site_pages.page_id` is already `PRIMARY KEY` (`20260808000003:47`), so the
   FK costs nothing.
3. **The badge needs the reverse query.** *"Who are the experts of Crow
   Charmer"* is an index scan on a table and an array scan on a column.

**This deliberately departs from the column pattern**, and the reason is worth
keeping: the two existing capabilities are scalars — you either may moderate or
you may not. This one is *scoped to a thing*, and a scalar cannot express a
relationship. Do not "correct" it back into a column later.

**`ON DELETE CASCADE` on `user_id` is load-bearing.**
`pending_revisions.author_id` references `auth.users` with **no `ON DELETE`
clause**, so deleting a contributor already raises a constraint violation. This
must not become the second thing blocking account deletion.

## `can_review_page()` — extending the ladder

```sql
CREATE OR REPLACE FUNCTION public.can_review_page(target_page_id text)
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER
SET search_path TO 'public' AS $$
    SELECT public.role_rank(public.get_my_role()) >= public.role_rank('reviewer')
        OR EXISTS (SELECT 1 FROM public.page_experts pe
                   WHERE pe.user_id = auth.uid() AND pe.page_id = target_page_id);
$$;
```

Same shape as `can_moderate()`, but built on `role_rank()`
(`20260825000001_role_rank.sql`) so it does **not** become the fourth
independent list of role names. Bug 6 existed precisely because every perk
tested a literal.

Grants: follow `can_moderate()`, which is granted to `anon` as well as
`authenticated` because its SELECT policy calls it for every reader. Check
whether that is true here before copying it — if no anon-facing policy calls
`can_review_page()`, anon does not need it.

## The two policies F5 must rewrite

Both are page-blind today (`20260727000000_remote_schema.sql:275-277`):

```sql
CREATE POLICY "Staff can manage queue" ON pending_revisions
    USING (get_my_role() = ANY (ARRAY['admin','reviewer']));
CREATE POLICY "Staff can view queue" ON pending_revisions FOR SELECT
    USING (get_my_role() = ANY (ARRAY['admin','reviewer']));
```

Both become `can_review_page(page_id)`. **This is the highest-risk change in the
version**: too loose and an expert gets the whole queue, too tight and reviewers
lose it. Note that "Staff can manage queue" has no `FOR` clause, so it is `FOR
ALL` — the write gate as well as the read one.

The three probes are not optional here, and the third is the one that matters:
anon fails · a non-expert with no role fails · **an expert succeeds on their own
page and fails on somebody else's**. The last is two probes, not one.

## The role-list sweep

Counted 2026-08-25: **~18 literal role lists** (`= ANY (ARRAY['admin',
'reviewer'])` and similar) across 10 migrations. v0.16's bug 6 fixed **one**.

Bug 6 was not an isolated defect — it was one instance of a pattern that is
still everywhere, including inside `can_moderate()` itself
(`thread_moderation.sql:54`). Rewriting them against `role_rank()` is
mechanical and **behaviour-preserving today** (rank ≥ 3 *is* admin-or-reviewer),
which is exactly why it should happen while these files are already open for F5
rather than as its own risky pass later.

`check_revision_rate_limit()` carries a different one —
`caller_role IN ('trusted_editor','reviewer','admin')` = rank ≥ 2 — in two
places (`20260810000000:93` and `20260812000005:52`). Same treatment.

## The cache-stamp fix — scheduled 2026-08-25, after it hid the release

Only **3 of the 11** scripts a character page loads carry a `?v=` stamp. A
release that changes an unstamped renderer therefore serves a **fresh skeleton
against a stale script**, and the reader sees the old page with no way to know
why.

It was deferred twice for the same reason — the fix restamps 62 pages, so it
should ride along with other work rather than ship as a 62-file diff on its own.
This is that ride-along.

**What moved it out of "unscheduled": it hid v0.16 from the owner on release
day.** Third occurrence, and the first to cost a release:

| When | What was reported | What it was |
|---|---|---|
| 2026-08-20 | — | Reproduced deliberately. Theoretical at the time. |
| 2026-08-24 | Combos / Starter Guide / Techs "not rendering" | Cache skew. Owner cleared it; no hotfix shipped. |
| **2026-08-25** | **"Are you sure the Roster Selection changes landed?"** | **Both roster features invisible. See below.** |

**The 2026-08-25 evidence, read off production rather than reasoned about:**

```
index.html          Cache-Control: max-age=600    cf-cache-status: DYNAMIC
js/pagebuilder.js   Cache-Control: max-age=3600   (no ?v= stamp)
```

Live `js/pagebuilder.js` contained `Show Hidden` and all the icon code, with
`last-modified: Tue, 25 Aug 2026 14:14:37 GMT` — one minute after `bda5a16`
merged. Every `medias/images/*Icon.webp` returned 200. The deploy was entirely
correct.

The decisive check was **`navigation.json`, which contains the string `WIP` zero
times.** The `(WIP)` still showing inside the roster card names could therefore
only be *appended by code* — and only the pre-v0.16 `pagebuilder.js` does that,
since v0.16 moved it into the 🚧 corner marker. That is what identified a stale
script rather than a failed deploy, and it is the check to reach for next time:
**find something the new code renders from data, and ask the data.**

The skeleton refreshes in ten minutes. The renderer is held for an hour and the
browser never revalidates, because nothing in its URL changed. **Both** headline
roster features — the dynamic icon and `Show Hidden` — live in that one
unstamped file, so both vanished together and the release looked like it had not
landed at all.

**The fix is one line**, in `scripts/asset-version.js:35`:

```js
const SHARED_MODULES = ['character_tabs.js', 'input_slots.js', 'site_utils.js'];
```

`stampSharedAssets` builds its regex from that array and already rewrites both
the generated stubs and the hand-authored pages, so adding a name is the whole
change. `pagebuilder.js` is the one to add first — it renders the roster, the
dashboard columns and the character page.

**Two things to settle at design time, neither of them obvious:**

1. **How far to go.** All 11 scripts, or only the renderers that actually change
   often? The three current members are hashed *together* on purpose (the file's
   own header explains why: `site_utils.js` parses `character_tabs.js` output at
   load, so serving one fresh against one stale is the exact failure). Adding
   `pagebuilder.js` to that pool means every edit to it invalidates the other
   three as well. That is the safe direction to err in, and worth stating out
   loud rather than discovering in a diff.

2. **`index.html` is `max-age=600` and `DYNAMIC`; the scripts are `max-age=3600`
   and cached at the edge.** The stamp is the fix, but the TTL split is *why*
   the window exists at all, and it is Cloudflare configuration rather than
   anything in this repo. Worth a look while this is open.

**Expect the 62-page restamp.** `npm run generate` must run or `validate` fails,
the same way it did twice in v0.16 as a side effect of touching `site_utils.js`.
The diff is large and almost entirely one substituted query string.

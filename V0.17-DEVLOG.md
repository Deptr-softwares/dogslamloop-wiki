## The precedent: a capability, not a role

The owner's *"moderators not tied to a set role"* is **`can_moderate`**, v0.14
item 2 (`20260813000001_thread_moderation.sql:36`):

```sql
ALTER TABLE "public"."user_roles"
    ADD COLUMN IF NOT EXISTS "can_moderate" boolean NOT NULL DEFAULT false;
```

> *'Thread moderation without full reviewer rights. Independent of role: admin
> and reviewer can always moderate, and this grants it to anyone else.'*

Its comment states the rule the whole schema follows: **"A column, never a second
role."** `user_roles` has `UNIQUE(user_id)` deliberately — two rows once broke
`get_my_role()` with *"more than one row returned by a subquery"*, which broke
that user's access to everything, not just the thing the second role was for.

Two capabilities exist already: `bypass_cooldown` (v0.13) and `can_moderate`
(v0.14). **The expert is the third, and it is the same idea one dimension
further out** — not "can this person moderate" but "can this person review *this
page*".

## The blocker the capability pattern does NOT solve

```sql
"role" text NOT NULL
CHECK (role = ANY (ARRAY['admin','reviewer','trusted_editor','viewer']))
```

`role` is **NOT NULL**. Every `user_roles` row therefore carries one of those
four, which means a capability column can only be granted to somebody who
*already holds a role*. `set_user_capability` says this outright: *"Deliberately
cannot create a row. A capability is an extra on top of a role."*

So `can_moderate` is independent of *which* role you hold — but not of holding
one. **That is the whole of the "default to the authenticated role" problem**
the source list flagged and could not resolve: an expert who is simply a
knowledgeable player has no role, and there is no value that column can take for
them.

## The resolution: a table, not a column *(owner's call, 2026-08-25)*

```sql
CREATE TABLE public.page_experts (
    user_id uuid NOT NULL REFERENCES auth.users(id)            ON DELETE CASCADE,
    page_id text NOT NULL REFERENCES public.site_pages(page_id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, page_id)
);
```

Three reasons, in order of weight:

1. **It dissolves the CHECK problem entirely.** Its own table, its own row — no
   role required, so there is nothing to default to.
2. **Referential integrity.** `page_id` is owner-editable. A `text[]` of ids
   rots silently when a page is renamed; a foreign key cannot.
   `site_pages.page_id` is already `PRIMARY KEY` (`20260808000003:47`), so the
   FK costs nothing.
3. **The badge needs the reverse query.** *"Who are the experts of Crow
   Charmer"* is an index scan on a table and an array scan on a column.

**This deliberately departs from the column pattern**, and the reason is worth
keeping: the two existing capabilities are scalars — you either may moderate or
you may not. This one is *scoped to a thing*, and a scalar cannot express a
relationship. Do not "correct" it back into a column later.

**`ON DELETE CASCADE` on `user_id` is load-bearing.**
`pending_revisions.author_id` references `auth.users` with **no `ON DELETE`
clause**, so deleting a contributor already raises a constraint violation. This
must not become the second thing blocking account deletion.

## `can_review_page()` — extending the ladder

```sql
CREATE OR REPLACE FUNCTION public.can_review_page(target_page_id text)
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER
SET search_path TO 'public' AS $$
    SELECT public.role_rank(public.get_my_role()) >= public.role_rank('reviewer')
        OR EXISTS (SELECT 1 FROM public.page_experts pe
                   WHERE pe.user_id = auth.uid() AND pe.page_id = target_page_id);
$$;
```

Same shape as `can_moderate()`, but built on `role_rank()`
(`20260825000001_role_rank.sql`) so it does **not** become the fourth
independent list of role names. Bug 6 existed precisely because every perk
tested a literal.

Grants: follow `can_moderate()`, which is granted to `anon` as well as
`authenticated` because its SELECT policy calls it for every reader. Check
whether that is true here before copying it — if no anon-facing policy calls
`can_review_page()`, anon does not need it.

## The two policies F5 must rewrite

Both are page-blind today (`20260727000000_remote_schema.sql:275-277`):

```sql
CREATE POLICY "Staff can manage queue" ON pending_revisions
    USING (get_my_role() = ANY (ARRAY['admin','reviewer']));
CREATE POLICY "Staff can view queue" ON pending_revisions FOR SELECT
    USING (get_my_role() = ANY (ARRAY['admin','reviewer']));
```

Both become `can_review_page(page_id)`. **This is the highest-risk change in the
version**: too loose and an expert gets the whole queue, too tight and reviewers
lose it. Note that "Staff can manage queue" has no `FOR` clause, so it is `FOR
ALL` — the write gate as well as the read one.

The three probes are not optional here, and the third is the one that matters:
anon fails · a non-expert with no role fails · **an expert succeeds on their own
page and fails on somebody else's**. The last is two probes, not one.

## The role-list sweep

Counted 2026-08-25: **~18 literal role lists** (`= ANY (ARRAY['admin',
'reviewer'])` and similar) across 10 migrations. v0.16's bug 6 fixed **one**.

Bug 6 was not an isolated defect — it was one instance of a pattern that is
still everywhere, including inside `can_moderate()` itself
(`thread_moderation.sql:54`). Rewriting them against `role_rank()` is
mechanical and **behaviour-preserving today** (rank ≥ 3 *is* admin-or-reviewer),
which is exactly why it should happen while these files are already open for F5
rather than as its own risky pass later.

`check_revision_rate_limit()` carries a different one —
`caller_role IN ('trusted_editor','reviewer','admin')` = rank ≥ 2 — in two
places (`20260810000000:93` and `20260812000005:52`). Same treatment.

**As of 2026-08-26 this sweep is a PREREQUISITE, not a cleanup.** F12 renames
what `admin` means, and every one of those 18 lists currently reads `admin` with
the *old* meaning. Sweep first, rename second — the reasoning is in F12 below.

**PASS 1 SHIPPED 2026-08-27** as `20260827000001_role_ladder_sweep.sql`: eleven
policies and two functions, plus an `is_staff()` helper naming "reviewer and
above" once. Three findings worth keeping:

* **It was eleven policies, not twelve.** `"Staff can moderate discussions"` on
  `page_discussions` reads like the twelfth site and **does not exist** —
  `20260813000001` dropped it deliberately and never recreated it, because *"a
  policy can only constrain which rows"* and leaving it would leave staff able
  to rewrite a contributor's post body. **A mechanical sweep would have handed
  back the one power v0.14 removed.** Checking every `DROP POLICY` before
  rewriting anything is what caught it.
* **Not every perk is the same bar.** `check_revision_rate_limit()` is
  trusted_editor-and-above, not staff, and is written as its own rank comparison
  so the sweep cannot flatten two different perks into one. Bending it to
  `is_staff()` would silently have taken the cooldown bypass from every trusted
  editor.
* **The main test is not a list of the eleven.** It replays every migration,
  computes which policies are still live, and asserts none of them names a role
  — so a policy written next month with a literal fails there rather than
  becoming the thing pass 2 misses.

## F12 — the `owner` / `admin` split

**The owner's words:** *"right now the wording 'admin' role in the site actually
mean 'owner'. I am thinking that if I were to create an admin role and give
myself the owner role instead. The owner would have access to the owner tools
and everything in it. And admin role would have the ability to Force Accept,
Force Reject, Self-approve change on top creating Ticket, Request change, and
intercept submission."*

This supersedes `CLAUDE.md`'s current statement — *"There is no `owner` role. The
site owner is an `admin`"* — which must be rewritten as part of this item.

### The ladder gains a rung

```
owner 5 · admin 4 · reviewer 3 · trusted_editor 2 · viewer 1 · (no role) 0
```

`role_rank()` already exists and is the one place that states the order, so the
rung is a one-line change *there*. Everywhere else is the problem.

### Blast radius, counted 2026-08-26

| Where | Count | What it means today | After the rename |
|---|---|---|---|
| `IS DISTINCT FROM 'admin'` — owner-tool RPC guards | **14** | "owner only" | must become `'owner'` |
| `= ANY (ARRAY['admin','reviewer'])` and similar | **18** | "owner or reviewer" | must become a rank test |
| `page_permissions.required_role` CHECK | **1** | allows `trusted_editor \| admin` | must allow `owner` |
| JS files comparing against `'admin'` | **10 files** | mixed | each needs reading |

**~33 SQL sites and 10 JS files.** This is the largest permission change since
the v0.14 moderation work.

### Sweep first, rename second — this is the whole implementation plan

Renaming `admin` while 32 literals still spell it means touching all 32 in one
migration against a live database, where a single miss is a silent privilege
change nobody sees. Doing the sweep first makes the rename tractable:

1. **Pass 1 — sweep.** Rewrite all 18 lists as `role_rank(get_my_role()) >=
   role_rank('reviewer')`, and leave the 14 owner-tool guards alone for now.
   **Behaviour-preserving and independently verifiable**, because at this point
   `admin` still means what it always meant.
2. **Pass 2 — rename.** Add `owner` to the CHECK and to `role_rank()`, migrate
   the existing admin row(s) to `owner`, and change the 14 guards from `'admin'`
   to `'owner'`. The 18 swept sites need **no further edit** — `>= reviewer` is
   still correct once `owner` outranks everything.

Pass 1 is the reason this is doable. Do not merge them into one migration.

### VERIFIED AGAINST PRODUCTION — three pages would silently widen

`page_permissions` is anon-readable, so this was read off production rather than
assumed (2026-08-26):

```
template        trusted_editor
tierlist        trusted_editor
writing_guide   trusted_editor
main-hub        admin
character-hub   admin
systems-hub     admin
```

**Three hub pages are restricted to `required_role = 'admin'`, which today means
the owner and nobody else.** After the rename, `role_rank('admin') >=
role_rank('admin')` passes and **the new admin can edit all three hubs** — a
privilege widening that no test would catch and that nobody asked for.

The rename migration must `UPDATE page_permissions SET required_role = 'owner'`
for those three rows, in the same transaction as the CHECK change. **Do not
write the CHECK before the data**, or the update fails against its own
constraint.

### Open at design time

- **Does `admin` get owner-tool access at all? DECIDED: NO** (owner,
  2026-08-27): *"The new admin should not get the owner tool access at all (for
  now, I will decide if in the future, I can allow admin to access some of the
  tools)."*

  So all 14 `IS DISTINCT FROM 'admin'` guards become `IS DISTINCT FROM 'owner'`
  in pass 2, and `owner.html`'s client-side RBAC gate goes to owner-only. **Note
  the "for now".** Per-tool access is a live possibility, so pass 2 should not
  bake "owner" into fourteen separate literals any harder than it has to — an
  `is_owner()` helper alongside `is_staff()` keeps that a one-line change later
  rather than a fifteenth sweep.
- **"Self-approve change"** is listed as an admin power. Read the security note
  under F13 first: an unprivileged version of self-approval appears to be
  reachable today, and the fix and this feature touch the same policy.

### PASS 2 SHIPPED 2026-08-27 — and pass 1 was half the sweep

`20260827000003_owner_role.sql`. The ladder gains a rung, `is_owner()` names the
top of it once, both CHECK constraints learn the new value, and the three hub
pages move off `admin` in the same transaction that allows `owner`.

**The finding that matters more than the feature: pass 1 reported itself
complete and had done roughly half the job.**

It grepped for `= ANY (ARRAY['admin','reviewer'])`, found eleven policies, swept
them, and shipped a test asserting no live policy names a role — written against
the same regex. **Fifteen more policies and four functions compare with plain
equality** (`get_my_role() = 'admin'`, `ur.role = 'admin'`), so neither the grep
nor the test ever saw them.

They all fail **open**. Left alone, the new admin would have gained the page
registry, the FAQ, the collaborators list, site meta, site settings, the blog,

created, silently.

**Two were worse than a widening:**

* **`can_delete_media()`** — `ur.role = 'admin'`. Would have moved the only
  irreversible action on the site *off* the owner and *onto* the new admin.
  Kept with the owner; an admin who should have it gets the per-user flag,
  which is what the flag exists for.
* **`anonymize_user_by_email()`'s last-account guard** — counted `role = 'admin'`.
  After the rename it would have protected an admin who cannot reach the tool at

**The lesson, stated so it is not relearned:** grep for the shape you are about
to invalidate, not the shape you happened to write down first. This is v0.16's
"grep for what you DELETED" one turn further out — there the missing string was
one I had removed, here it was one I had never looked for.

The widened test checks equality against `'admin'` **specifically**, in both
policies and functions, with comments stripped. `'owner'` is the new correct
comparison and `'viewer'` is a soft *ban* — genuinely a name rather than a rank,
which `free_submit_eligibility` and `report_discussion_post` test deliberately.

### How the bodies were changed, and why it matters

Eleven function bodies and fifteen policies were **lifted by script and
substituted**, never retyped. ~300 lines of plpgsql where a dropped clause would
be invisible in review. The two that would have hurt most:

```
"Voters read their own votes"   user_id = auth.uid() OR is_owner()
"Owners edit their own list"    owner_id = auth.uid() OR is_owner()
```

Losing those `OR` halves locks every voter out of their own vote and every
tier-list holder out of their own list.

### The anon regression, from pass 1

`is_staff()` is not `SECURITY DEFINER`, so it runs as the caller — and it calls
`role_rank()`, which was revoked from `anon`. `"Anyone can read published tier
lists"` has no `TO` clause and anon holds SELECT on that table, so **every
logged-out reader would have hit `permission denied for function role_rank`**
where a tier list should be. Fixed in `20260827000002`; caught while writing
pass 2, not by a test.

`tests/anon-callable-closure.spec.js` is now the general form: any non-definer
function anon may call must only call things anon can execute. **A test
asserting "is_staff is granted to anon" would have stayed green through the
entire regression** — that assertion was in pass 1, and it was.

### Deliberately not done

**Nobody's role is changed by the migration.** The owner is setting both
accounts from the Supabase dashboard, which uses the service role and bypasses
RLS (owner, 2026-08-27). Two consequences, stated because they are sharp:

1. The CHECK must land **before** `'owner'` can be typed — the dashboard rejects
   the value until then.
2. Between the release merging and that edit, **nobody holds `owner`**, so every

### The reviewer side — CORRECTED 2026-08-27, then FIXED

**The mechanism recorded here on 2026-08-26 was wrong, and the wrong version is
kept because it is the more tempting reading.** It said batching is disabled
during an intercept and only `finalPayloads[0]` is written, so the other deltas
are dropped. That looks right from `js/editor-core.js:1231` alone — and it is
not, because the intercept branch never runs the diff scanner at all. It pushes
**exactly one** payload built from the ticket's own `target_scope`, so
`payloadsToInsert.length > 1` was never true there and `finalPayloads[0]` was
never dropping anything. Reading two lines without the branch that feeds them.

**The real mechanism.** The intercept rebuilt its delta by reading the ticket's
own scope out of the editor:

```js
dPayload = window.currentEditorDescData[scope];
```

For a **`multi`** ticket — a batch — there is no `currentEditorDescData.multi`,
so that is `undefined`. supabase-js serializes the update with `JSON.stringify`,
**which drops undefined values**, so `delta_payload` was never in the PATCH and
the column kept its old contents. `author_id`, `status` and `qa_metadata` all
updated and the request returned no error, which is exactly why it presented as
a successful write. A legacy whole-page ticket (`is_delta` false,
`target_scope` null) resolved to `undefined` the same way.

**A merged ticket is `multi`.** So is a batched submission. In a queue with a
MERGE TICKETS button that is the common case, not a corner —
`js/admin-merge-compiler.js:470` writes `target_scope: 'multi'` and
`js/editor-core.js` batches into the same shape.

**SHIPPED.** `window.buildInterceptDelta` is extracted and returns `null` for
anything it cannot scope, which routes those through the ordinary diff scanner
and re-batches them — so the batching engine's intercept exclusion is gone,
which is the right change for a reason unrelated to the one first written down.
The empty-scan guard is now unconditional, because the scanner can genuinely
come back empty during an intercept and falling through would take
`finalPayloads[0]` as `undefined`.

An explicit `delta === undefined` guard is kept rather than left to the
branches. **A write that silently does nothing is worse than one that fails**,
and that is the whole lesson of this bug.

**What the tests could not do:** prove the PATCH reaches Postgres without the
column. That needs the owner's two Boomcat rows. The seven specs pin the
rebuild's contract instead, and two of them fail against the pre-fix code.

- **Not `ticket_open`.** `js/submissions.js:146` allows editing in both

**SHIPPED.** Routed on intent; refused when the intent cannot be honoured; the

**Still worth knowing what the real trigger was.** The fix turns a silent wrong

## F13 — contributors join the discussion on their own ticket

**The owner's words:** *"There should be no reason why they get a notification of
'Staff are discussing your submission'"* without being able to reply.

The notification is real — `js/admin-actions.js:204-208` sends *"Staff opened a
discussion on your revision. Check My Submissions to follow along."* And
`js/submissions.js:75` already renders `rev.ticket_chat` to the author. **They
can read the conversation and cannot answer it.**

### The RLS already allows it, which makes this mostly a UI item

`"Authors can update own pending revisions"` (`20260802000000:31-36`) permits an
author to UPDATE their own row while `status IN ('pending','ticket_open')`. So
appending to `ticket_chat` needs **no new policy**.

### SECURITY — read this before touching that policy

That same permissiveness looks like a live hole, found while scoping this item:

```sql
CREATE POLICY "Authors can update own pending revisions" ON pending_revisions
FOR UPDATE USING (
    auth.uid() = author_id AND status IN ('pending', 'ticket_open')
)
WITH CHECK (auth.uid() = author_id);      -- <- no status restriction
```

`USING` decides which rows may be updated; `WITH CHECK` decides what the row may
become. The check tests **only ownership**, so an author appears able to
`UPDATE ... SET status = 'approved'` on their own pending row. If so:

- it leaves the queue — `js/admin-queue.js:61` selects
  `.in('status', ['pending','ticket_open'])`, so staff stop seeing it;
- it becomes **world-readable** — `"Public can view approved revisions"` is
  `FOR SELECT USING (status = 'approved')`, granted to `anon`;
- it does **not** publish to the live page, since merging to live is a separate
  write to `page_data`.

So the impact is moderation bypass and public visibility of unreviewed content,
not live defacement. **Read from the policy text, not yet probed** — confirm
with a real contributor JWT against a preview branch before treating it as fact,
and note it is exactly the "self-approve" power F12 wants to grant *admins*
deliberately.

**The fix is an RPC, not a tighter policy.** RLS cannot restrict *which columns*
an update touches, and the table already carries `GRANT ALL TO authenticated`,
so revoking down to `GRANT UPDATE (ticket_chat)` would break the other author
paths. A narrow `post_ticket_message(revision_id, text)` matches the precedent
`20260813000001` set for exactly this reason: *"There is now no path in the
schema by which anybody edits somebody else's post text."*

Author messages need a visual distinction from staff ones in both
`js/admin-tickets.js` and `js/submissions.js` — reuse the `type` field, which
`requestChanges()` already established as additive (`type: 'changes_requested'`,
absent on older messages).

## The cache-stamp fix — scheduled 2026-08-25, after it hid the release

Only **3 of the 11** scripts a character page loads carry a `?v=` stamp. A
release that changes an unstamped renderer therefore serves a **fresh skeleton
against a stale script**, and the reader sees the old page with no way to know
why.

It was deferred twice for the same reason — the fix restamps 62 pages, so it
should ride along with other work rather than ship as a 62-file diff on its own.
This is that ride-along.

**What moved it out of "unscheduled": it hid v0.16 from the owner on release
day.** Third occurrence, and the first to cost a release:

| When | What was reported | What it was |
|---|---|---|
| 2026-08-20 | — | Reproduced deliberately. Theoretical at the time. |
| 2026-08-24 | Combos / Starter Guide / Techs "not rendering" | Cache skew. Owner cleared it; no hotfix shipped. |
| **2026-08-25** | **"Are you sure the Roster Selection changes landed?"** | **Both roster features invisible. See below.** |

**The 2026-08-25 evidence, read off production rather than reasoned about:**

```
index.html          Cache-Control: max-age=600    cf-cache-status: DYNAMIC
js/pagebuilder.js   Cache-Control: max-age=3600   (no ?v= stamp)
```

Live `js/pagebuilder.js` contained `Show Hidden` and all the icon code, with
`last-modified: Tue, 25 Aug 2026 14:14:37 GMT` — one minute after `bda5a16`
merged. Every `medias/images/*Icon.webp` returned 200. The deploy was entirely
correct.

The decisive check was **`navigation.json`, which contains the string `WIP` zero
times.** The `(WIP)` still showing inside the roster card names could therefore
only be *appended by code* — and only the pre-v0.16 `pagebuilder.js` does that,
since v0.16 moved it into the 🚧 corner marker. That is what identified a stale
script rather than a failed deploy, and it is the check to reach for next time:
**find something the new code renders from data, and ask the data.**

The skeleton refreshes in ten minutes. The renderer is held for an hour and the
browser never revalidates, because nothing in its URL changed. **Both** headline
roster features — the dynamic icon and `Show Hidden` — live in that one
unstamped file, so both vanished together and the release looked like it had not
landed at all.

**The fix is one line**, in `scripts/asset-version.js:35`:

```js
const SHARED_MODULES = ['character_tabs.js', 'input_slots.js', 'site_utils.js'];
```

`stampSharedAssets` builds its regex from that array and already rewrites both
the generated stubs and the hand-authored pages, so adding a name is the whole
change. `pagebuilder.js` is the one to add first — it renders the roster, the
dashboard columns and the character page.

**Two things to settle at design time, neither of them obvious:**

1. **How far to go.** All 11 scripts, or only the renderers that actually change
   often? The three current members are hashed *together* on purpose (the file's
   own header explains why: `site_utils.js` parses `character_tabs.js` output at
   load, so serving one fresh against one stale is the exact failure). Adding
   `pagebuilder.js` to that pool means every edit to it invalidates the other
   three as well. That is the safe direction to err in, and worth stating out
   loud rather than discovering in a diff.

2. **`index.html` is `max-age=600` and `DYNAMIC`; the scripts are `max-age=3600`
   and cached at the edge.** The stamp is the fix, but the TTL split is *why*
   the window exists at all, and it is Cloudflare configuration rather than
   anything in this repo. Worth a look while this is open.

**Expect the 62-page restamp.** `npm run generate` must run or `validate` fails,
the same way it did twice in v0.16 as a side effect of touching `site_utils.js`.
The diff is large and almost entirely one substituted query string.

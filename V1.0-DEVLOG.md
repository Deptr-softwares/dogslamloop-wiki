### Decided 2026-10-02

Each was put to the owner with the alternative, and chosen:

* **Discord to wiki: Supabase checks the two forum channels every 10 seconds.**
  An Edge Function on a Supabase Cron schedule reads new messages over Discord's
  HTTP API. Rejected: an always-on bot holding Discord's live connection (the
  gateway). It is instant and sees edits and deletions as they happen, but it
  needs a server running all day outside Supabase, which is a monthly cost and a
  second thing to keep alive. The price of polling: Discord does not tell a
  poller about edits or deletions, so the last day of messages is re-checked to
  catch them. If the delay ever matters, a gateway bot can replace the poller
  without changing the database side.
* **Wiki to Discord: a webhook, under the writer's name.** Shows as
  "Real Deptr [APP]: Hello"; Discord's APP tag already marks it as relayed.
  Rejected: messages under the bot's own name ("Bot: Real Deptr: Hello"). The
  price: Execute Webhook has no `message_reference`, so a site reply cannot be a
  Discord reply. It is sent as a normal message opening with a quote of what it
  answers.
* **Roles: synced for people who signed in with Discord, by hand on Discord for
  everyone else.** Owner's wording: *"Synced for users who signed in with
  Discord, manual discord-side for users who signed in via other methods"*.
  Read as **one way, wiki to Discord**: a role set in the owner tools gives the
  matching Discord role. A Discord role never grants a wiki power, because that
  would let anyone with Manage Roles on Discord make a wiki reviewer. *Told to
  the owner; correct this line if they meant both ways.*
* **Old posts: start fresh.** Each character's Discord post shows only messages
  from the day it is linked. The old posts stay on the wiki.
* **Role scheme, the owner's questions answered:** no member list is needed (the
  bot gives roles itself). *Moderate discussion* gets a Discord role, because
  moderating the connected forum means moderating both halves and that power on
  Discord only comes through a role. *Upload media* does not; it does nothing on
  Discord. *Expert* is optional, as one role rather than one per character:
  **the owner's call, not yet made.**

Stated to the owner as defaults, not objected to:

* Deleting on either side deletes on the other, for an author removing their
  own message and for a moderator removing someone else's.
* A wiki ban (`viewer`) stops that person's Discord messages being copied to the
  wiki, when their Discord account is linked. Discord bans are Discord's.
* Hidden characters get no Discord post until they are shown.
* Discord caps a message at 2,000 characters and the site at 4,000: a long site
  post is cut on Discord, with a link to the full post.
* Pictures in Discord messages are copied into Supabase Storage. Discord's links
  expire (`CLAUDE.md`, the media rule).

### Checked against the documentation, 2026-10-02

**Discord** (`docs.discord.com`, which `discord.com/developers/docs` now
redirects to):

* *Execute Webhook*: in a forum channel, "you must provide either `thread_id`
  in the query string params, or `thread_name` in the JSON/form params", and
  `thread_name` creates a post. With `thread_id`, "the thread will
  automatically be unarchived". There is no `message_reference` parameter.
  `?wait=true` returns the created message, which is where its id comes from.
  Edit and Delete Webhook Message both take `thread_id`.
* *Forum channels*: only threads can be created in them, and they show as
  posts. A post is created with `POST /channels/{id}/threads` carrying a
  message. Creating a post needs `SEND_MESSAGES`; replying needs
  `SEND_MESSAGES_IN_THREADS`. Active posts: `GET /guilds/{id}/threads/active`;
  archived: `GET /channels/{id}/threads/archived/public`.
* *Message Content intent*: without it, `content`, `embeds`, `attachments`,
  `components` and `poll` come back empty, **over the HTTP API too**, not only
  the gateway. "Apps with fewer than 10,000 users can access privileged intents
  by enabling them in the Developer Portal."

**Supabase**:

* Edge Functions are scheduled with `pg_cron` plus `pg_net`, with credentials
  in Vault. Supabase Cron runs "anywhere from every second to once a year";
  no more than 8 jobs at once, each under 10 minutes.
* Branching: on merge, "Edge Functions declared in `config.toml` are deployed"
  to production, alongside migrations.

Checked 2026-10-04:

* **Webhook names**: 1 to 80 characters, never containing `clyde` or `discord`
  (any case), otherwise the nickname rules. A wiki display name like
  "DiscordFan" would be refused, so names are cleaned before sending and fall
  back to a fixed one; the message is never dropped for its name.
* **Secrets on a preview branch** are set per branch
  (`supabase secrets set --project-ref <branch-ref>`). A preview branch must
  never post to the real server, so **with no secrets the relay does nothing**,
  and a preview branch is never given any.
* **Locked posts**: "Sending a message will automatically unarchive the
  thread, unless the thread has been locked by a moderator", and without
  `MANAGE_THREADS` nobody can post in one. The documentation says nothing about
  webhooks there, so a refused send is expected and handled: the post stays on
  the wiki, marked as not sent.

### The roles, from the owner, 2026-10-04

| Discord role | Wiki |
|---|---|
| Boomcat | `owner` |
| Admin of DSL | `admin` |
| Reviewer of DSL | `reviewer` |
| Trusted Editor of DSL | `trusted_editor` |
| *(none)* | `viewer` |
| Moderation Perms | `can_moderate` |
| *(Character name)* Expert | a `page_experts` row for that character |

The Expert roles already exist, one per character, and each gives a private
channel for that character's experts. Owner: *"they all follow the pattern
(Character name) Expert; and the experts have their own private channel to
discuss things regarding their character and submission related to their
characters."* So syncing experts also opens or closes that channel.

What follows from the list:

* **A bot can only give roles below its own highest role**, so the bot's role
  sits above Admin of DSL and every Expert role. That makes the bot token able
  to make anyone a Discord admin: it lives in Supabase secrets and nowhere else,
  and the bot is never given Administrator.
* **Boomcat is not synced.** One person holds it, and syncing it would need the
  bot above the owner's own role.
* **Roles are matched by Discord's role id, not by name.** A name only finds
  them once ("Disaster Plants Expert" against `site_pages.name`); after that a
  renamed role keeps working.
* **Sync runs on a wiki change**, adding the new Discord role and removing the
  old one. A role given by hand on Discord is left alone until that person's
  wiki role changes.

### A hole the relay opens, found 2026-10-04

Somebody banned or timed out on the Discord server can still post on the wiki,
and the relay would then post their words **into the Discord forum** through
the webhook, past the ban. For a wiki account linked to Discord, the relay can
look up that person on the server first. Default unless the owner says
otherwise: **such a post stays on the wiki and is not sent to Discord.** An
account not linked to Discord cannot be checked; the wiki's own moderation is
what covers it.

### SPEC 2026-10-04: batch 1, the relay on the character threads

#### What a reader and a member will see

* **On the wiki**, a message from Discord sits in the character's thread like
  any post, tagged DISCORD, with the person's Discord display name and
  @handle. No profile link, since there is no wiki account behind it. Reply,
  report and moderation work on it as on any post.
* **On Discord**, `#character-discussion` holds one post per character, titled
  with its name, opened with a link to the character's wiki page. A wiki
  message shows under its writer's wiki name with Discord's APP tag and the
  wiki's logo as its picture. A wiki reply opens with `> **Kai**: first words…`.
* **Nothing on the wiki links to the server in Part 1.** The invite is Part 2's.

#### The rules the relay keeps

1. **A wiki post is on Discord exactly while it is visible on the wiki.** Sent
   within about 10 seconds. Deleted when its author removes it or a moderator
   hides or removes it. Sent again if a moderator restores it (staff removal is
   reversible: `20260928000000`, section 6).
2. **A Discord message reaches the wiki within about 10 seconds.** Deleted on
   Discord, by anyone: removed on the wiki, as the new status
   `removed_on_discord` ("Removed on Discord."). Edited on Discord: the wiki
   copy follows. Both are found by re-checking the last 24 hours, so a change
   older than that is not followed. The wiki's delete-only rule binds wiki
   authors; Discord lets its members edit, and the copy mirrors the original.
3. **A wiki moderator removing a Discord message deletes it on Discord.**
   Hiding does not: hiding is reversible and a Discord deletion is not.
4. **Never copied back:** the relay's own messages (its webhook's id), Discord
   system messages (pins, "started a post"), and anything older than the
   moment a post was linked (start fresh).
5. **Replies:** a Discord reply to a message with a wiki copy becomes a reply
   under that wiki post. Anything else becomes a new post in the thread.
6. **Images** attached on Discord are copied into Storage, in a new
   `discord-media` bucket: PNG, JPEG, WebP or GIF, up to 8 MB each, at most 4
   per message (the site's own limit). Any other file becomes a line naming
   it. A KLIPY GIF link is turned into the GIF's own address, as a wiki post's
   is: from Discord's embed of it when that is a KLIPY media address, else one
   API lookup.
7. **Discord markup becomes text:** a user mention becomes @name, a channel
   #name, a custom emoji :name:, a timestamp a date.
8. **No pings from the wiki.** Every webhook send sets `allowed_mentions` to
   nothing, so "@everyone" typed on the wiki pings nobody.
9. **Bans.** A wiki account linked to Discord whose owner is banned or timed out
   on the server: its posts stay on the wiki, unsent. A wiki ban (`viewer`) on
   a linked account: that person's Discord messages are not copied.
10. **Length.** A wiki post over 2,000 characters is cut on Discord with a link
    to the full post. A Discord message fits the wiki's 4,000 as it is.
11. **Without its secrets the relay does nothing**, so a preview branch never
    touches the real server.

#### Data

* `page_discussions` gains `source` (`'site'` or `'discord'`, default
  `'site'`), `discord_author_id` and `discord_author_handle`; `status` gains
  `removed_on_discord`. The shape trigger sets `source := 'site'` on **every**
  client insert. Only the relay, as the service role, writes `'discord'` rows,
  and for those the trigger keeps the given author name, leaves `author_id`
  NULL, accepts `discord/...` image paths, and skips the 20-second limit
  (Discord has its own slow mode).
* `discord_threads`: `site_key` (the `page_id` for a character; forum threads
  in batch 2), `channel`, `discord_thread_id` (unique), `linked_at`,
  `last_message_id` (the cursor), `checked_at`.
* `discord_messages`: `post_id` (FK to `page_discussions`, `ON DELETE
  CASCADE`), `discord_message_id` (unique), `direction`, `state` (`pending`,
  `sent`, `deleted`, `skipped`, `failed`), `attempts`, `last_error`,
  `updated_at`.
* Both new tables: RLS on, **no client policy and no client grant**. Only the
  service role touches them.
* `discord-media` bucket: public read, no client write policy.

#### The machinery

* **One Edge Function, `discord-relay`**, declared in `supabase/config.toml` so
  it deploys on merge to `main`. Supabase Cron calls it every 10 seconds through
  `pg_net`, with a secret header the function checks. The anon key is public,
  so it cannot be the guard.
* **Each call:** list the channel's active posts (one request) and fetch new
  messages only where a post's last message moved; send pending wiki posts and
  delete the ones no longer visible. **Once a minute** as well: open any missing
  character post (linking an existing post of the same title rather than making
  a second), and re-check the last 24 hours for edits and deletions.
* **The rules live in one plain JS file**,
  `supabase/functions/_shared/discord-relay-core.js`: no Deno, no browser, so
  the Playwright runner tests it in Node. The Edge Function is a thin layer of
  requests around it.
* **Secrets the owner sets:** `DISCORD_BOT_TOKEN`, `DISCORD_GUILD_ID`,
  `DISCORD_CHARACTER_CHANNEL_ID`, `DISCORD_CHARACTER_WEBHOOK_URL`, and
  `RELAY_SECRET` (also in Vault, for the cron job).
* **Checking a ban** needs `BAN_MEMBERS` **or `VIEW_AUDIT_LOG`** ("Get Guild
  Ban", checked 2026-10-04). View Audit Log only reads, so the bot gets that and
  never Ban Members. A timeout is the member's `communication_disabled_until`,
  from "Get Guild Member", which needs no privileged intent.

contract; 7 thread-page tests in the browser. Two of the rule tests are derived
from other files: the KLIPY patterns, key and order against

migration. **Falsified on the commit**: 19 deliberate breakages, from "pings
allowed" to "migration path drifts", each turned a test red; the tree was

**Verified on the preview branch, 2026-10-04** (PR #216, branch ref
`fnirabnzgcgboxuhkumb`; the full list is the PR's first comment):

* All 13 relay functions and the 3 new tables refuse anon and a signed-in
  member with `42501`. Writes were sent with each table's real columns, so the
  refusal is about permission. A member insert claiming `source = 'discord'`
  lands as an ordinary wiki post under their own name.
* As the service role: the lease, linking (and refusing a second link), the
  cursor (forward only, numeric), taking a message (trimmed name, handle,
  image, never twice, bad image path refused, unlinked post skipped, reply
  nested), the edit and its mark, "removed on Discord", and the outbox's send,
  delete and delete_original.
* Read from the database directly: the cron job runs every 10 seconds (26
  runs, 0 failed, **0 HTTP requests** with no Vault secrets), `pg_cron` in
  `pg_catalog`, `pg_net` in `extensions`.
* **The preview deploys the PR's Edge Function.** `discord-relay` is ACTIVE
  there with `verify_jwt` off, and without the secret it answers its own
  `Not found` (a missing function gets the platform's JSON `NOT_FOUND`). So
  the relay can be tried against a test server before the release.

**Found on the preview:** a preview database grants the service role no table
it is not named on (the "not auto-exposed" default in `supabase/config.toml`).
The relay is unaffected, because every read and write goes through its own
`SECURITY DEFINER` functions; a probe has to read public tables as anon.

**CI's first run failed on a comment.** `block-styling-coverage` read "(v1.0
batch 1)" in `discussions.css` as a rule for the class `.0`, a token it had
taken from `sbox-tab${i === 0 ? ...}` in `js/description.js`. The audit now
strips CSS comments, removes `${...}` before splitting a class attribute, and
keeps only tokens that can be class names. That also put `.sbox-tab` and
`.sbox-panel` under audit for the first time (both styled in `Layout.css`); a
planted `.sbox-tab` rule in `discussions.css` alone, with `Layout.css`'s
renamed, turns it red. `mobile-drawers` flaked once in the same run; it did the
same in a v0.20 run, so it predates this work.

**Still not verified:**

### Decided 2026-10-02

Each was put to the owner with the alternative, and chosen:

* **Discord to wiki: Supabase checks the two forum channels every 10 seconds.**
  An Edge Function on a Supabase Cron schedule reads new messages over Discord's
  HTTP API. Rejected: an always-on bot holding Discord's live connection (the
  gateway). It is instant and sees edits and deletions as they happen, but it
  needs a server running all day outside Supabase, which is a monthly cost and a
  second thing to keep alive. The price of polling: Discord does not tell a
  poller about edits or deletions, so the last day of messages is re-checked to
  catch them. If the delay ever matters, a gateway bot can replace the poller
  without changing the database side.
* **Wiki to Discord: a webhook, under the writer's name.** Shows as
  "Real Deptr [APP]: Hello"; Discord's APP tag already marks it as relayed.
  Rejected: messages under the bot's own name ("Bot: Real Deptr: Hello"). The
  price: Execute Webhook has no `message_reference`, so a site reply cannot be a
  Discord reply. It is sent as a normal message opening with a quote of what it
  answers.
* **Roles: synced for people who signed in with Discord, by hand on Discord for
  everyone else.** Owner's wording: *"Synced for users who signed in with
  Discord, manual discord-side for users who signed in via other methods"*.
  Read as **one way, wiki to Discord**: a role set in the owner tools gives the
  matching Discord role. A Discord role never grants a wiki power, because that
  would let anyone with Manage Roles on Discord make a wiki reviewer. *Told to
  the owner; correct this line if they meant both ways.*
* **Old posts: start fresh.** Each character's Discord post shows only messages
  from the day it is linked. The old posts stay on the wiki.
* **Role scheme, the owner's questions answered:** no member list is needed (the
  bot gives roles itself). *Moderate discussion* gets a Discord role, because
  moderating the connected forum means moderating both halves and that power on
  Discord only comes through a role. *Upload media* does not; it does nothing on
  Discord. *Expert* is optional, as one role rather than one per character:
  **the owner's call, not yet made.**

Stated to the owner as defaults, not objected to:

* Deleting on either side deletes on the other, for an author removing their
  own message and for a moderator removing someone else's.
* A wiki ban (`viewer`) stops that person's Discord messages being copied to the
  wiki, when their Discord account is linked. Discord bans are Discord's.
* Hidden characters get no Discord post until they are shown.
* Discord caps a message at 2,000 characters and the site at 4,000: a long site
  post is cut on Discord, with a link to the full post.
* Pictures in Discord messages are copied into Supabase Storage. Discord's links
  expire (`CLAUDE.md`, the media rule).

### Checked against the documentation, 2026-10-02

**Discord** (`docs.discord.com`, which `discord.com/developers/docs` now
redirects to):

* *Execute Webhook*: in a forum channel, "you must provide either `thread_id`
  in the query string params, or `thread_name` in the JSON/form params", and
  `thread_name` creates a post. With `thread_id`, "the thread will
  automatically be unarchived". There is no `message_reference` parameter.
  `?wait=true` returns the created message, which is where its id comes from.
  Edit and Delete Webhook Message both take `thread_id`.
* *Forum channels*: only threads can be created in them, and they show as
  posts. A post is created with `POST /channels/{id}/threads` carrying a
  message. Creating a post needs `SEND_MESSAGES`; replying needs
  `SEND_MESSAGES_IN_THREADS`. Active posts: `GET /guilds/{id}/threads/active`;
  archived: `GET /channels/{id}/threads/archived/public`.
* *Message Content intent*: without it, `content`, `embeds`, `attachments`,
  `components` and `poll` come back empty, **over the HTTP API too**, not only
  the gateway. "Apps with fewer than 10,000 users can access privileged intents
  by enabling them in the Developer Portal."

**Supabase**:

* Edge Functions are scheduled with `pg_cron` plus `pg_net`, with credentials
  in Vault. Supabase Cron runs "anywhere from every second to once a year";
  no more than 8 jobs at once, each under 10 minutes.
* Branching: on merge, "Edge Functions declared in `config.toml` are deployed"
  to production, alongside migrations.

**Not yet checked**, and needed before building D5: how Edge Function secrets
reach a preview branch; Discord's rules for webhook display names (a writer's
name that Discord refuses must not lose the message); whether a **locked** post
refuses a webhook.

### Design notes, to settle before building

* **Secrets.** The bot token and both webhook URLs live in Supabase secrets,
  put there by the owner, never in this repo, CI or a chat message. Same rule as
  the service-role key; `CLAUDE.md` gains the line when D5 lands.
* **A Discord message has no wiki account behind it.** `page_discussions`
  stamps `author_id := auth.uid()` in `enforce_discussion_shape` and refuses a
  NULL one, so a message the relay writes needs its own path that a browser can
  never take, and its own author fields (Discord id, display name, @handle).
* **One table for messages, a new one for forum threads.** The likely shape:
  forum messages stay in `page_discussions` under a forum key, so reports,
  moderation, images, KLIPY and the rate limit already work on them; a new
  table holds each forum thread's title and tags. To be decided with the data
  in front of it.
* **Link tables.** Site thread to Discord post; site message to Discord message
  (for deletions, and so the poller never copies back what the webhook sent);
  a per-post cursor (last message seen).
* **Discord markup** (`<@id>` mentions, `<:name:id>` emoji) is turned into
  readable text on the way in.
* **Tests cannot reach Discord**, as they cannot reach Storage. The relay's
  translation rules are written so they can be tested without it.

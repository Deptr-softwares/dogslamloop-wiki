## Batch 1 — built 2026-09-10

All three bugs fixed, each falsified against its own commit. Two came out
differently from the spec above, and the spec was wrong in the safer direction
both times — it under-stated them.

**B3 was 26 pages, not 7.** The spec listed the seven found by reading. The test
was written to derive the rule instead — *every page that loads `site_utils.js`
needs the modal stylesheets* — and it immediately found **19 more**: 18 generated
`system` and `others/` stubs, plus `privacy-policy.html`. The generated ones came
from one template: `generate-pages.js` has three, and the **system** one was the
only one missing `Forms.css`. Fixed there and regenerated, not by hand.

Had that test listed the seven pages it was written to fix, it would have passed
forever and caught none of the nineteen. This is the second time in two versions
that deriving rather than listing changed the answer.

**B1's cause was not the label.** The spec guessed at "EDIT PAGE" being a
character longer and said, correctly, that it needed measuring. Measured:
9.6px/4px 8px on a character page against **11.2px/6.4px 12px** on a system
page — and 11.2px/6.4px 12px is exactly what `.btn-sys` declares.

`.btn-sys` and `.tab-editor-btn-sidebar` are **both single-class selectors** that
set font-size and padding, so specificity is equal and **stylesheet order
decides**. The two templates disagree: a character stub loads `Layout.css`
**last**, a system stub loads it **second**, before `Buttons.css`.

That is worth more than the bug. Any `Layout.css` rule meant to override a
`Buttons.css` one silently fails on all 18 system pages, and nothing says so.
Fixed narrowly — qualified the selector with `.btn-sys` so it wins in either
order — rather than by reordering the system template, which would change which
rule wins for every other class those two files share. **The general hazard is
still open and belongs to the owner** (see Known-open).

**B2 was exactly as diagnosed.** Falsifying against the pre-fix commit produced
`Received: Array []` — no button lit at all, the strip fully dark, which is the
owner's report reproduced.

### F8 moved to its own branch, and why

The spec put F8 in this batch. It is out, for a rule rather than a preference:
**Supabase branching decides once, on a branch's FIRST push.** F8 needs a
migration either way (see below), and a migration added to a branch in a *later*
push gets `SKIPPED` and reaches `next-update` verified by nothing — observed on
PR #165. Batch 1's branch was already going to push without SQL, so F8 belongs
on a fresh branch whose first push carries its migration.

**F8 also has one open question the spec did not anticipate.** The Media Library
lists **Supabase Storage**, not a table — `storage.from('wiki-media').list('')`
— and `list()` returns `{name, id, updated_at, created_at, last_accessed_at,
metadata}`. **There is no uploader in what the client can see.** So the join the
spec described has nothing to join *from* yet, and the choice is:

* **Read `storage.objects.owner_id`** — covers media already uploaded, but needs
  a `SECURITY DEFINER` function reaching into the `storage` schema, and it is
  unverified whether that column is populated for the ~198 existing files.
* **Add `uploaded_by` to `media_moderation`** — the shape `reviewed_by` already
  uses in that table, `uuid REFERENCES auth.users(id) ON DELETE SET NULL`, no new
  security surface. But it can only credit media uploaded *after* the migration;
  everything already in the bucket stays uncredited.

Owner's call, asked 2026-09-10. **They chose the second.**

### Batch 1 went red on its own fix, and the reason is worth keeping

`tests/routing.spec.js:66` failed in CI, consistently across three retries.
**B1 caused it.** The same rule sets `display: none`, flipped to `flex` by
`.is-active`, which `initTabEditorButtons` adds at runtime on the pages it
manages — and it does not manage the tier list page, whose Edit link is static,
points at `tier-editor.html`, and deliberately has no HISTORY button beside it.

That link was visible **only because `.btn-sys` was winning the cascade**.
Making the sidebar rule win properly applied the `display: none` and hid a link
whose own markup comment says it must never be hidden for readers. Fixed by
stating `.is-active` in the markup, so the intent is written down rather than
inherited from a file ordering.

**The lesson, and it generalises past CSS:** the pre-flight check was "does every
consumer carry `.btn-sys`?", which every consumer did. **A consumer can also
depend on the rule LOSING**, and no selector sweep can see that. Checking who
uses a thing is not the same as checking who benefits from it failing.

## F8 — Media Library uploader credit *(built 2026-09-10)*

Shipped after being carried through v0.16, v0.17 and v0.18.

### It is a new table, and `media_moderation` could not have held it

The owner chose "record the uploader ourselves at upload time" over reading
`storage.objects.owner_id`. That decision stands. The **table** changed, because
the one the plan named cannot take the column:

`media_moderation` is an **overlay**, and its header says so — *absence of a row
means unchecked*. `js/admin-media-queue.js` reads it literally:

```js
status: record ? record.status : 'unchecked',
```

`status` is `NOT NULL` with `CHECK (status IN ('approved','flagged'))`, so a row
written at upload time has to claim one of the two. **Every upload would arrive
pre-approved and the moderation queue would be permanently empty** — a failure
nobody would notice until something bad got through.

It also costs the three properties that header names as the whole reason for the
overlay shape: contributors would need an INSERT policy on the moderation table
(the "insert your own row" policy it was designed not to have), the upload path
would gain something to remember, and un-approving — which is `DELETE` — would
erase the credit as a side effect.

**Credit is registry data**, true of every file. **Moderation is judgement
data**, true only of files somebody looked at. Two lifetimes, two tables.

### `public.media_uploads`

`path` (PK, the object name, same key as `media_moderation.path` so the two join
with no mapping), `uploaded_by uuid REFERENCES auth.users ON DELETE SET NULL`,
`uploaded_at`.

* **SELECT** to `authenticated` — the bucket's own list policy is already
  authenticated-only, so this exposes nothing to anyone who cannot already see
  the file list. Not granted to `anon`: the credit renders inside the editor.
* **INSERT** to `authenticated` `WITH CHECK (uploaded_by = auth.uid())`. No role
  check — uploading is open to any signed-in contributor, and gating the *record*
  of an upload more tightly than the upload would leave real files uncredited.
* **No UPDATE policy at all**, because `js/editor-media.js` refuses an upload
  that would overwrite an existing filename. A path is written once and cannot
  change hands.
* **DELETE** gated on `can_delete_media()` — the same capability that removes the
  file, so a row cannot outlive what it describes.

**What it cannot do:** only files uploaded after the migration get a row. The
~198 already in the bucket have no uploader this project can read, and absence
renders as **no caption rather than "Unknown"** — the same choice as the
deliberately NULL `reviewed_by` on `20260812000002`'s seed rows. A caption that
says nothing, on almost every card, is worse than no caption.

### Two escaping bugs, found while building rather than reported

* **`file.name` went into the gallery card raw**, while the upload queue *in the
  same file* had always escaped it. Filenames come from the uploader's disk.
* **The URL went into `src="..."` raw** — and `getPublicUrl` builds it *from*
  that filename, so it is equally attacker-influenced, in an attribute where a
  bare double quote ends the attribute and starts markup.

The second is the one worth remembering: it surfaced **only because the test
outlived the first fix**. After escaping the caption, the spec still failed —
the hostile `<img>` had lost its own class, because something had broken out of
an attribute. Real Storage percent-encodes what it returns, so this was defence
in depth rather than a live hole, but *"the layer below happens to sanitise"* is
not the standard here.

## F1 — Search

**Two surfaces, two indexes.** The owner's call, and it is the right one: *"the
searchbar for a short search, full text for a dedicated `search.html` page.
Similar to most modern wiki."* The split resolves the size problem instead of
trading against it — the small index loads everywhere, the large one loads only
on the page whose whole job is searching.

Measured against live content on 2026-09-10, not estimated:

| | Entries | Index |
|---|---|---|
| **Structural** — page names, section headings, move names | 475 headings + 382 move names + every page | **~16 KB** |
| **Full text** — every paragraph | 1,630 paragraphs | **~223 KB** (~60 KB gzipped) |

### F1a — the searchbar

Loads `data/search-index.json` (~16 KB) on first focus, not on page load.
Typeahead over page names, section headings and move names. A wiki for a
fighting game is searched for four things — a character, a move, a system term,
a section — and all four are in this index. Body text is not, deliberately.

**Every result deep-links, and the anchors already exist.**
`window.collectSectionTargets(descData, frameData)`
([character_tabs.js:726](js/character_tabs.js#L726)) already walks both page
families and mints anchor ids that **match `assignSectionAnchors`'s DOM sweep**,
in rendered order, including the `sec-notes` / `sec-notes-2` numbering when two
sections share a title. So a result is
`characters/Sukuna/index.html?tab=combos#sec-punish-combos` for free, against
ids the in-page link picker already depends on.

**Build the index by calling that function, never by writing a second walker.**
A second traversal of `desc_data` would be a third derivation that has to agree
with the renderer and the picker, and the picker's own history says what
happens when one of them misses a family: until v0.18 F5 it offered exactly one
target on a system page, "Discussion", and none of the sections actually on the
page. One walker, three consumers.

It also already reads `frame_data`, which matters more than it looks: a move's
heading is its **name**, and names live in `frame_data`, not `desc_data`. 382 of
the 857 structural entries are move names. An index built from `desc_data` alone
could not find a single skill — the thing this wiki is mostly about.

**Calling it from Node.** `js/character_tabs.js` is an IIFE that assigns to
`window` with no `module.exports`. The established way to read it from a script
is the one `tests/character-tab-vocabulary.spec.js` already uses, for the same
reason ("so this file never holds a second copy of the list it is policing"):

```js
const fakeWindow = {};
new Function('window', fs.readFileSync(VOCAB_FILE, 'utf8'))(fakeWindow);
```

`collectSectionTargets` reaches for `window.sectionAnchorSlug`,
`window.getCharacterTabLabels()`, `window.GENERIC_SECTION_TITLES` and
`window.FRAME_MOVE_CATEGORIES`. Two are defined in that same file and
`sectionAnchorSlug` has an inline fallback; resolve the rest by evaluating their
owning module against the same stand-in window rather than by stubbing them,
because a stub is a fourth copy.

**`data/search-index.json` is a generated file.** New `scripts/fetch-search-index.js`,
wired into `npm run refresh-content` and into `regenerate.yml`'s write set. Two
project rules bite here and both have drawn blood before:

- **"Whatever `npm run validate` checks, `npm run generate` writes."** The
  invariant is stated at
  [regenerate.yml:184](.github/workflows/regenerate.yml#L184), and it broke this
  job for three days once: adding a `--check` to validate without a matching
  `--write` in generate breaks it *silently*, because a passing run and a run
  with nothing to do look identical from the outside.
- **Never assert a count** of pages, headings, moves or index entries in a test.
  A test an owner edit can turn red is a production outage, not a failing test —
  the Roulette page cost three days of stale content this way.

#### F1a as built *(2026-09-10)* — the spec's two numbers were wrong

**1,501 entries and 257 KB unfiltered, against a predicted 857 and ~16 KB.** The
estimate counted only `heading` blocks and move names as bare strings. It missed
the per-entry structure entirely, and it missed that the *keyed* sections —
matchups, counterplay, starter guide — are not heading blocks at all and so were
invisible to the way it counted.

**Matchups were 492 of those, a third of the index.** Every character page
carries a "vs. \<Opponent\>" section for every other character, so typing
"Vessel" would return the Vessel page buried under 21 near-identical rows —
exactly the failure the spec had named as the *full-text* risk, sitting in the
structural index instead. Excluded here with the synthetic "Discussion" target,
and both belong in F1b where results are ranked and paginated.

Filtered, plus array records rather than objects: **982 entries, 83 KB raw,
13.7 KB gzipped.** The wire figure is close to the original claim, by a
different route. The raw one was simply wrong.

**Not added to `npm run validate`**, and this is the deliberate half. Every other
artifact that check compares is built offline from committed files; this one
comes from Supabase, so a `--check` would turn the owner editing a heading into a
red required check. It refreshes nightly in `regenerate.yml`, *after*
`fetch-registry` — the index skips any `page_data` row with no live registry
entry, so building it against a stale `navigation.json` would silently drop a
page published that day.

**The test that matters is the slug-agreement one.** The generator runs in Node,
where `pagebuilder.js` cannot be evaluated, so `collectSectionTargets` uses its
own inline copy of `sectionAnchorSlug`. That copy is currently
character-for-character identical to the real one — an assumption, not a
guarantee. Drift would break every link in the index at once and look like
nothing: valid JSON, right size, plausible ids, all pointing at elements that do
not exist. Falsified by perturbing only the fallback.

#### A rebase deleted the feature, silently, and the suite stayed green

Rebasing this branch onto `next-update` conflicted on **64 stamped HTML files**.
Resolving toward the integration branch is the documented fix and was right for
63 of them — but this branch also **added a `<script src="js/search.js">` tag**
to 17 hand-authored pages, and taking the other side dropped it. The generated
stubs recovered on `npm run generate` because their change lives in the template.
The hand-authored ones had nothing to regenerate from.

**The searchbar would have vanished from every hand-authored page with a
completely green suite.** No error, no console warning, just no search box —
the module that draws it was no longer on the page.

`tests/search-index.spec.js` now derives the rule: every page that builds a
sidebar must load `js/search.js`. **The regeneration rule has a blind spot, and
this is its shape:** "regenerate, never hand-merge" recovers anything a generator
owns, and silently discards anything in the same files that it does not.

Falsified by removing the tag from `blog.html` — and the first attempt at that
falsification was itself wrong, matching an unstamped tag that no longer exists
in the file, so the test "passed" against a change that never happened. **A
passing falsification is a hypothesis too.**

### F1b — `search.html`

A dedicated results page that fetches the full-text index (~223 KB) and searches
paragraphs as well as structure. Full text needs **relevance ranking**, or a
common word returns forty near-identical rows with nothing to tell them apart —
that is the failure mode that makes a full-text search worse than none.

New hand-authored page, so it is not in the generator's write set — but it
**must** load `Forms.css` (see B3, which is exactly this mistake made seven
times).

## F3 — The MoS button

A red `.btn-sys` in the editor's Workspace Header reading **MoS** (Manual of
Style). Opens a modal carrying the Writing Guide's Basics, plus a statement of
the language standard, and two buttons: **Ok** and **Rewatch Tutorial** (→ F2).

Source: Writing Guide → `basics` → *"Universal Rules"* — headings **Basics**,
Character Pages, Other Pages, **Ground for Rejection**. Note that *Basics* and
*Ground for Rejection* are `list` blocks, so the modal has to render list items,
not just paragraphs.

**On the language standard**, which the owner asked for help with: state a
variety plus a baseline, because "written in English" is not a rule anyone can
follow or enforce. Proposed wording, for the owner to accept or change:

> This wiki is written in American English, following Wikipedia's Manual of
> Style for capitalisation, headings and numbers. Game terms use the spelling
> and casing they have in-game.

The last sentence is the one that matters in practice — it is what settles
whether a move is "Domain Expansion" or "domain expansion", and no general style
guide can answer that for a Roblox fighter.

## Bugs

### B1 — the History/Edit pair is larger on system pages

**Not diagnosed.** Both page types build the pair from the same
[page_router.js:150](js/page_router.js#L150) and
[pagebuilder.js:312](js/pagebuilder.js#L312), share `.tab-editor-btn-sidebar`,
and there is no page-type width rule in any stylesheet. The only difference
visible in source is the label — system renders "EDIT PAGE", character "EDIT
TAB".

This one needs **measuring in the browser**, not reading. Assert the structural
consequence, not pixel geometry: font metrics differ between Windows and the
Linux runner, which is why `visual.spec.js` is `testIgnore`d.

### B2 — the Techs tab does not light up

**Diagnosed. One line, and there is a written precedent.**

[editor-tabs.js:16](js/editor-tabs.js#L16) is a module-level `const`, evaluated
at parse time:

```js
const EDITOR_MAJOR_TABS = window.getCharacterTabIds({ includeInjected: true, editableOnly: true });
```

[character_tabs.js:340](js/character_tabs.js#L340) drops an optional tab unless
it is in `enabledOptionalTabs` — which is `[]` until the character's
`tab_settings` has been fetched. So `techs` is never in `EDITOR_MAJOR_TABS`, for
the life of the page. `renderEditorTabNav` then never toggles `edit-nav-techs`
on, but **does** clear `.active` off the button the user came from, so the strip
goes dark while the editor mounts correctly underneath — exactly what was
reported.

[admin-core.js:355](js/admin-core.js#L355) documents this same bug, in the same
words (*"never had `.active` removed"*), and records that `js/page_boot.js` fixed
it on the reader page and admin.html was missed. **The editor is the third
surface and was missed too.** Fix: `includeOptional: true`. Safe —
`EDITOR_MAJOR_TABS` has exactly one consumer, and an `.active` class on a hidden
button costs nothing.

The regression test must drive a real tab switch and read back which button
carries `.active`, not assert the array contents — asserting the array is the
vacuous shape this project has shipped twice.

### B3 — unstyled fields in the profile modal

**Diagnosed, and wider than reported.** The profile modal
([site_utils.js:1332](js/site_utils.js#L1332)) is injected into every page and
styles its inputs with `.editor-input`, which is defined in
[Forms.css:10](style/Forms.css#L10).

Seven pages load `Modals.css` but not `Forms.css`:

`blog.html` · `submissions.html` · `systems/index.html` ·
`systems/tierlist/index.html` · `systems/updatelog/index.html` ·
`systems/color-codes/index.html`

— and **`recent-changes.html` loads neither**, so it is missing `.profile-field`
as well. Character pages load both, which is why it looks correct there.

All seven are hand-authored (`NEVER_TOUCH` or root pages), so this is an edit
per file, not a generator change. **A test should derive the rule** — every page
that injects the modal loads the stylesheets the modal needs — rather than
listing these seven, or the eighth page will repeat it. `search.html` (F1b) is
that eighth page.

### F4 — the matchup chart *(PR #194, open)*

A 24 × 24 grid under Terminology on the systems hub. **Verified against
production, not mocks:** 385 rated cells, 167 unrated, 24 on the diagonal — 576,
which is 24². Deep links resolve to `sec-vs-<opponent>`.

A **grid, not a peek**, unlike `buildTerminologyPeek` beside it: a glossary is a
list and six of it is a fair sample, but a matchup chart's whole value is the
shape of the roster at once.

**Two things it refuses to do, both with tests.** `tier` is free text and one
production entry reads "Aerial Circling tier" — `resolveMatchupTier` keeps that
wording and renders it white rather than rounding it to a neighbouring
difficulty. And opponent names join **exactly**: recovering a near-miss would
attach somebody's written opinion to a character they did not write it about.
The chart is also deliberately **not symmetrical**, which is the property most
likely to be "fixed" later.

**Three content problems, the owner's to fix**, found by reconciling 417 stored
entries against 385 rendered cells — every one accounted for:

* **`"Disaster Plant"` on 12 pages; the roster says `"Disaster Plants"`.** Twelve
  real ratings that join to nothing. Fixing the name lights up twelve cells.
* **`"More pls fill this up"`** in an opponent field on Strongest of History.
* **19 characters rate themselves.** Harmless — the diagonal is blank anyway.

### C6 — the multicolour shortcode *(PR #194)*

`[multicolor=a,b]` sweeps text from the first stop to the last, one span per
visible character. Carried since **v0.12** and deferred four times with no design
ever recorded; the owner chose the gradient reading over a repeating cycle.

**Stops are resolved through a probe element, not parsed as hex.** `safeColor`
accepts five grammars and two of them — `var(--x)` and named colours — have no
numeric value without a stylesheet. Parsing only hex would have accepted fewer
colours here than the sibling `[color=]` accepts, which nobody could guess from
outside.

**The walk is the risk, not the maths.** It runs on a half-built HTML string, so
it steps over tags from nested shortcodes, treats an entity as the one character
a reader sees rather than the five a string index sees, and leaves whitespace
unwrapped so words survive a line break. Both branches falsified individually.

### F2 + F3 — the tour and the Manual of Style *(pushed, no PR yet)*

**Neither holds its own copy of the text.** Both read `page_data` for
`writing_guide`, tab `basics` — the words a contributor is told to read and a
reviewer judges against. The tour's steps are **derived from the guide's own h3
headings**, so a sixth element added to the guide becomes a sixth step with no
code change. The owner's five and the guide's headings happen to match; nothing
in the code names them.

The only thing authored in code is the language standard, because the guide
states no variety. American English, since the guide's own Basics writes
"capitalize". Owner revised the second line on 2026-09-20.

### Gradient presets in the footer *(owner request, 2026-09-20)*

Eight two-stop presets in the colour popup, inserting `[multicolor=a,b]`.
`applyFormat` already produced `[tag=value]text[/tag]`, so the insert needed no
new machinery. **Batch 5 was stacked onto batch 4 for this** — the button writes
a shortcode, and testing only the insert would pass against an engine that had
never heard of `[multicolor]`.

### What went wrong, and is worth keeping

**I shipped "visible but unreachable", twice, in one batch.**

*The tour over the notices.* The tour's text box sits exactly where the v0.18
notices put GOT IT, so a notice raised during the tour could not be clicked. The
first fix **refused the notice** — worse, because a first-time contributor would
then never see the Media Library notice at all. The tour pauses instead. That
still only worked in one direction: the tour is **async**, so it can arrive *on
top of* a notice already up. A probe showed that; no test did. Both orderings are
now pinned.

**The colour popup's top ~48px is clipped by the scrolling workspace**, and
`keepColorPopupOnScreen` only ever clamped sideways. Measured 2026-09-20: the
first row sat at y=358 behind a strip ending at y=377, and `elementFromPoint`
returned the strip. **Nobody had noticed because that band only ever held a
label.** Adding a row of buttons put real controls in it — and moving the row
lower just put a different row in, because the height was the problem. The clamp
now works on both axes, capping the scroll region **from measurement rather than
a fixed number**: the swatch count grows with the roster, and a hardcoded height
would go wrong the day a character is added.

**A test gap found by a failed falsification.** The tour body and the MoS modal
carry identical escaping interpolations, and `String.replace` takes the first
match — so an attempt to break the modal broke the tour instead and **nothing
went red**. The tour body had no escaping test at all. Both are covered now.

**Two smaller ones.** Gradient buttons carried `.color-preset-btn` at first,
making them members of a family whose every other member has `data-color`; the
existing swatch sweep caught it immediately, and separating the classes also
removed a handler-ordering hazard. And a test drove `setSelectionRange` alone,
which fires no event — the toolbar tracks selection on `mouseup`, so the
shortcode landed at the caret with nothing inside it.

## Batch 6 — C2, built 2026-09-20

Ctrl-click a block's header to select it. The selection can then be copied,
pasted, deleted and moved as one piece, from the bar that appears above the
list or from any selected card's own buttons.

### The design was already in the file

The spec carried from v0.18 says *a selection model, not a keybinding*, and
says nothing about shape. The shape came from `expandedBlocks`, twenty lines
above: collapse state is a **WeakSet keyed by the block object**, and the
comment there states the three reasons — index changes under reordering, a flag
on the block would be serialised into `desc_data` and shipped to every reader,
and object identity survives `renderBlockList`.

Every one of those applies harder to a selection, because **every operation a
selection offers changes the indices of the blocks around it**. A selection
held as indices would be wrong the instant it was used.

**No order is stored anywhere either.** Order is derived from the live array
each time it is needed, so "copy these five" and "move these five up" still mean
the same five blocks after the array has been rewritten under them. There is no
second copy of the order to go stale because there is no copy at all.

### Three rules chosen, not fallen into

* **A selection beats the hover.** Hover copy is what this was before C2 and
  still works untouched with nothing selected — but once an author has said
  which blocks they mean, the pointer resting on a sixth must not overrule them.
* **A card that is part of the selection hands its ▲▼✖ to the whole
  selection**; a card outside it still acts on itself. Otherwise the card
  buttons and the bar quietly come to mean different things.
* **v0.18 F9's gallery early return is kept**, not routed around.

### What went wrong

**`stopPropagation` does not stop listeners on the same element.** All three of
this file's click listeners are bound to `#block-list`, so every selection-bar
button *also* reached the general button handler — which resolves buttons
through `closest('.block-card').getAttribute(...)` and throws on anything
outside a card. Four exceptions per pass, one per button.

**Eighteen passing tests had nothing to say about it.** The bar's own work had
already been done in the first listener, so the document was correct and the
selection was correct; the exception surfaced in a second listener where nothing
was watching. The test that found it asserts on `pageerror` rather than on the
document, which is the only place this was ever visible. `stopImmediatePropagation`
is the fix.

**A test that accused the stylesheet.** The hover assertion failed comparing
`rgb(219,168,13)` against `rgb(231,176,8)` — both yellow. Not a specificity
bug: `.block-card` carries `transition: border-color 0.1s`, so it had compared
two frames of the same animation. A failing test is a hypothesis, not a verdict.
## Batch 7 — C3 SectionedBox: the design, recorded before building

Read `devlogs/V0.16-DEVLOG.md` for the owner's own wording; this is the shape
it resolves to against the current code, established 2026-09-20 by reading it
rather than by inventing one.

### The data shape

```js
sectionedbox: {
    type: 'sectionedbox',
    title: 'New Section Box',
    intro: [],                                  // blocks
    sections: [{ title: 'Section 1', content: [] }],   // blocks per tab
    align: 'left',
    author: '',
}
```

`{ title, content: [blocks] }` deliberately: it is **the shape `comboGroups`
already uses**, so the keyed-section machinery, the diff walkers and the nested
renderer all already know how to read it. A new shape here would be a fourth
container convention in one file.

### The two behaviours, derived rather than named

The spec says the box wraps itself in a Combo Card's wrapper **inside a
Combos/Techs group** and drops the wrapper everywhere else, so it does not
produce wrapper-on-wrapper styling.

Those groups render with `contextClass = tabId`, so the obvious test is
`contextClass === 'combos' || contextClass === 'techs'`. **That is the one
thing `renderDocumentTab`'s own header forbids** — *"this function does not
know either tab by name"*, because every difference between Combos and Techs is
a string in `js/character_tabs.js`. A third tab added there would silently get
the wrong behaviour.

Derived instead: `window.getDocumentSections(contextClass)` is truthy for
exactly the document tabs and falsy everywhere else. A tab added later gets the
wrapper without anyone coming back here.

### Two constraints inherited from the accordion bugs — the owner asked for this

Both fixed on this branch, both of which SectionedBox would otherwise have
reproduced on day one:

* **The body that holds nested blocks must not be a flex container.** Media
  alignment is `float`, and float is ignored on a flex item — which is how
  Right silently rendered hard-left inside an accordion.
* **Which tab is open must not live only in the DOM.** The editor repaints the
  preview on every keystroke, so a SectionedBox would reset to its first tab on
  each character typed — the same bug as the accordion closing itself, and
  worse, because a tab row makes it look like the author's click did nothing.
  `populateTextSection` already captures and restores `<details>` open state
  across a repaint; the active tab is restored the same way and by the same
  rule: **by position, not by title**, because the title is what is being typed.

### Seven sites, four files

`tests/theorybox.spec.js` states the cost of a new block type and it is unchanged:
registry shape, picker entry, label map, editor form (`js/editor-blocks.js`),
reader (`js/description.js`), **reviewer preview** (`js/admin-preview.js`) and
**draft sync** (`js/editor-sync.js`). The last two only ever run inside a
reviewer's session or a draft sync, which is what makes them the two that get
forgotten. The two diff walkers are near-identical copies in the two files, kept
that way deliberately, so both need the same clause.

## Batch 7 — the rest, built 2026-09-20

### C4 — Seconds Data

A third way to say how long a phase lasts, beside counted frames and an
estimate. JJS is 60fps server-side, so a second **is** 60 frames — the
conversion is exact rather than a display convenience, which is why the whole
feature lands in `phaseWeight`, the one function that decides a phase's width,
instead of at each call site.

It inherits the estimate's rule about divisions: **no ticks**. Drawing 120 of
them for one typed `2` would invent a per-frame breakdown out of nothing.

**The fill hook was renamed and that was the load-bearing part.** It was
`.phase-estimated`, which said *why* a phase had no divisions rather than
*what* it was. It is `.phase-solid` now, shared, with `.phase-estimated` and
`.phase-seconds` kept as the semantic classes. Without that rename a timed
phase would have rendered at the correct width and completely transparent —
which is verbatim the bug that rule's own comment records having been reported
for estimates.

**The legend was wrong the moment this shipped** and was fixed with it: it told
readers a smooth block "is an estimate", when it now means "not counted" and
the hover says which of the two.

### C7 — Box-in a list

The owner's whole spec, carried since v0.15 without ever being in an ordered
list: *"visual only, a sleek clean border around the list"*.

**Opt-in per list**, not applied to every list on the site — the wiki has
hundreds, and boxing them all is a decision about existing pages rather than an
option on a new one. Assumption stated to the owner; one line to flip.

*"Visual only"* is the load-bearing half, so the test that matters compares a
boxed list against an unboxed one and requires everything except the border to
match. A box that quietly reordered or dropped the credit would still look
right.

### C5 — ALREADY BUILT. Do not start it.

**Established 2026-09-20 by reading the code the roadmap pointed at.** The item
reads *"the Tier List Editor reusing the live Certified render, with
drag-and-drop inside it"*. `js/tier-editor.js` already does exactly that, and
its own header has said so since v0.14:

Its `portrait()` emits `.tier-portrait` / `.tier-portrait-icon` into
`.ctl-chars` — the reader's own classes from `js/certified-tier-lists.js`, so
it **is** the live Certified render, not a copy of it. Drag-and-drop is there
too, on pointer events so mouse and touch share one implementation.

It shipped as v0.14 item 3's second half and the inventory never caught up,
so v0.16, v0.17 and v0.19 each carried it forward as outstanding.

**Two corrections that go with it:**

## Carried warnings

**The suite is close to its limit.** ~1470 tests against a single
`python -m http.server` with 4 workers. The failure shape to recognise is a
burst of flakes across unrelated page-loading specs with the run time up by a
quarter — that is load, not a regression. Re-run the failing specs *alone*
before diagnosing; a failure that passes in isolation is load, and a consistent
failure in isolation is real. Seen again in v0.18 from four sequential runs of a
single spec file. The real fix is a threaded server or parallel-safe fixtures.

**A release conflicts on stubs, and the fix is to regenerate.** Each branch
regenerates from Supabase with its own code, and stubs embed an asset stamp
derived from `js/` — so two branches with different unreleased JS legitimately
produce different stubs. v0.18's release PR went `CONFLICTING` on **62 generated
files whose only difference was the stamp**. Resolve toward the integration
branch, then `npm run generate`; never hand-merge, and check afterwards that
nothing only `main` had was reverted.

**F1 adds a generated file, so it adds to that conflict surface.**
`data/search-index.json` regenerates per branch from Supabase like every other
artifact. Expect it in the next release PR's conflict set, and resolve it the
same way — regenerate, never hand-merge.

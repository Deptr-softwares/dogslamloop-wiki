## F1 — Search

**Two surfaces, two indexes.** The owner's call, and it is the right one: *"the
searchbar for a short search, full text for a dedicated `search.html` page.
Similar to most modern wiki."* The split resolves the size problem instead of
trading against it — the small index loads everywhere, the large one loads only
on the page whose whole job is searching.

Measured against live content on 2026-09-10, not estimated:

| | Entries | Index |
|---|---|---|
| **Structural** — page names, section headings, move names | 475 headings + 382 move names + every page | **~16 KB** |
| **Full text** — every paragraph | 1,630 paragraphs | **~223 KB** (~60 KB gzipped) |

### F1a — the searchbar

Loads `data/search-index.json` (~16 KB) on first focus, not on page load.
Typeahead over page names, section headings and move names. A wiki for a
fighting game is searched for four things — a character, a move, a system term,
a section — and all four are in this index. Body text is not, deliberately.

**Every result deep-links, and the anchors already exist.**
`window.collectSectionTargets(descData, frameData)`
([character_tabs.js:726](js/character_tabs.js#L726)) already walks both page
families and mints anchor ids that **match `assignSectionAnchors`'s DOM sweep**,
in rendered order, including the `sec-notes` / `sec-notes-2` numbering when two
sections share a title. So a result is
`characters/Sukuna/index.html?tab=combos#sec-punish-combos` for free, against
ids the in-page link picker already depends on.

**Build the index by calling that function, never by writing a second walker.**
A second traversal of `desc_data` would be a third derivation that has to agree
with the renderer and the picker, and the picker's own history says what
happens when one of them misses a family: until v0.18 F5 it offered exactly one
target on a system page, "Discussion", and none of the sections actually on the
page. One walker, three consumers.

It also already reads `frame_data`, which matters more than it looks: a move's
heading is its **name**, and names live in `frame_data`, not `desc_data`. 382 of
the 857 structural entries are move names. An index built from `desc_data` alone
could not find a single skill — the thing this wiki is mostly about.

**Calling it from Node.** `js/character_tabs.js` is an IIFE that assigns to
`window` with no `module.exports`. The established way to read it from a script
is the one `tests/character-tab-vocabulary.spec.js` already uses, for the same
reason ("so this file never holds a second copy of the list it is policing"):

```js
const fakeWindow = {};
new Function('window', fs.readFileSync(VOCAB_FILE, 'utf8'))(fakeWindow);
```

`collectSectionTargets` reaches for `window.sectionAnchorSlug`,
`window.getCharacterTabLabels()`, `window.GENERIC_SECTION_TITLES` and
`window.FRAME_MOVE_CATEGORIES`. Two are defined in that same file and
`sectionAnchorSlug` has an inline fallback; resolve the rest by evaluating their
owning module against the same stand-in window rather than by stubbing them,
because a stub is a fourth copy.

**`data/search-index.json` is a generated file.** New `scripts/fetch-search-index.js`,
wired into `npm run refresh-content` and into `regenerate.yml`'s write set. Two
project rules bite here and both have drawn blood before:

- **"Whatever `npm run validate` checks, `npm run generate` writes."** The
  invariant is stated at
  [regenerate.yml:184](.github/workflows/regenerate.yml#L184), and it broke this
  job for three days once: adding a `--check` to validate without a matching
  `--write` in generate breaks it *silently*, because a passing run and a run
  with nothing to do look identical from the outside.
- **Never assert a count** of pages, headings, moves or index entries in a test.
  A test an owner edit can turn red is a production outage, not a failing test —
  the Roulette page cost three days of stale content this way.

### F1b — `search.html`

A dedicated results page that fetches the full-text index (~223 KB) and searches
paragraphs as well as structure. Full text needs **relevance ranking**, or a
common word returns forty near-identical rows with nothing to tell them apart —
that is the failure mode that makes a full-text search worse than none.

New hand-authored page, so it is not in the generator's write set — but it
**must** load `Forms.css` (see B3, which is exactly this mistake made seven
times).

## F2 — The editor tutorial

A JRPG-style guided tour that runs on first entry to the editor, and again after
"Got It" on the v0.18 notice modal. Five elements, then the detail of each in
order.

**The content already exists and is written.** Writing Guide → `basics` → *"How
to use the editor?"*, which names all five exactly as the owner's list does:

1. Workspace Header (and *The QA*, an `h4` beneath it)
2. Workspace Navigation
3. Workspace
4. Workspace Footer
5. Preview Panel

63 blocks / 6,273 characters in that tab — fully authored, not placeholder.
Read it from `page_data` at `page_id = 'writing_guide'` rather than copying the
prose into JS: the owner edits the Writing Guide through the site, and a copy in
the repo would be a second source that silently goes stale.

**Where the tutorial's step order comes from.** The rendered order of that
section, so a step added to the Writing Guide appears in the tour without a code
change. Guard for the empty case — a tab with no blocks yields no tour, and the
tutorial should not open on nothing.

## F3 — The MoS button

A red `.btn-sys` in the editor's Workspace Header reading **MoS** (Manual of
Style). Opens a modal carrying the Writing Guide's Basics, plus a statement of
the language standard, and two buttons: **Ok** and **Rewatch Tutorial** (→ F2).

Source: Writing Guide → `basics` → *"Universal Rules"* — headings **Basics**,
Character Pages, Other Pages, **Ground for Rejection**. Note that *Basics* and
*Ground for Rejection* are `list` blocks, so the modal has to render list items,
not just paragraphs.

**On the language standard**, which the owner asked for help with: state a
variety plus a baseline, because "written in English" is not a rule anyone can
follow or enforce. Proposed wording, for the owner to accept or change:

> This wiki is written in American English, following Wikipedia's Manual of
> Style for capitalisation, headings and numbers. Game terms use the spelling
> and casing they have in-game.

The last sentence is the one that matters in practice — it is what settles
whether a move is "Domain Expansion" or "domain expansion", and no general style
guide can answer that for a Roblox fighter.

## F4 — Matchup table on the Side Dashboard

**"Side Dashboard" is `js/dashboards.js`**, and the surface is the systems hub,
`systems/index.html`. Recorded because it was read three other ways first — the
left sidebar, the right sidebar, and a page called "Side Dashboard" that does
not exist.

Placement: a new section **after `#glossary-section`**, the hub's "Terminology"
block, per the owner's *"preferably under the Terminologies section"*.

**Copy the shape of `buildTerminologyPeek`**
([dashboards.js:320](js/dashboards.js#L320)) exactly. It is the same problem
already solved on the same page: fetch `page_data`, derive rows, `section.hidden
= true` and return when there is nothing, escape at every interpolation, and
swallow the error rather than shouting — *"a failure to load an optional extra
should not shout at a reader."*

### The real data shape, read from production 2026-09-10

```js
{ opponent: "Honored One", tier: "Equal", content: [ ...blocks ], author?: "..." }
```

`desc_data.matchups`, an array. **22 pages carry one, 413 entries in total.**

**`tier` is free text, and the data proves it.** Eleven values are real tiers;
one entry reads `"Aerial Circling tier"`. The table must render an unrecognised
tier without breaking — which costs nothing, because
[site_utils.js:419](js/site_utils.js#L419) already resolves an unknown tier to
`{ id: name, color: '#ffffff' }`, and `MATCHUP_TIER_ALIASES` already folds
`Unwinnable → Hopeless` and `Unloseable → Dominating`. Use
`window.MATCHUP_TIERS` and that resolver; do not restate the ladder.

**262 of 413 entries are `"Equal"`** — 63%. A grid coloured straight from the
data will be mostly one colour, and that is the honest picture rather than a
rendering bug. Worth the owner seeing a draft before the layout is settled.

## Bugs

### B1 — the History/Edit pair is larger on system pages

**Not diagnosed.** Both page types build the pair from the same
[page_router.js:150](js/page_router.js#L150) and
[pagebuilder.js:312](js/pagebuilder.js#L312), share `.tab-editor-btn-sidebar`,
and there is no page-type width rule in any stylesheet. The only difference
visible in source is the label — system renders "EDIT PAGE", character "EDIT
TAB".

This one needs **measuring in the browser**, not reading. Assert the structural
consequence, not pixel geometry: font metrics differ between Windows and the
Linux runner, which is why `visual.spec.js` is `testIgnore`d.

### B2 — the Techs tab does not light up

**Diagnosed. One line, and there is a written precedent.**

[editor-tabs.js:16](js/editor-tabs.js#L16) is a module-level `const`, evaluated
at parse time:

```js
const EDITOR_MAJOR_TABS = window.getCharacterTabIds({ includeInjected: true, editableOnly: true });
```

[character_tabs.js:340](js/character_tabs.js#L340) drops an optional tab unless
it is in `enabledOptionalTabs` — which is `[]` until the character's
`tab_settings` has been fetched. So `techs` is never in `EDITOR_MAJOR_TABS`, for
the life of the page. `renderEditorTabNav` then never toggles `edit-nav-techs`
on, but **does** clear `.active` off the button the user came from, so the strip
goes dark while the editor mounts correctly underneath — exactly what was
reported.

[admin-core.js:355](js/admin-core.js#L355) documents this same bug, in the same
words (*"never had `.active` removed"*), and records that `js/page_boot.js` fixed
it on the reader page and admin.html was missed. **The editor is the third
surface and was missed too.** Fix: `includeOptional: true`. Safe —
`EDITOR_MAJOR_TABS` has exactly one consumer, and an `.active` class on a hidden
button costs nothing.

The regression test must drive a real tab switch and read back which button
carries `.active`, not assert the array contents — asserting the array is the
vacuous shape this project has shipped twice.

### B3 — unstyled fields in the profile modal

**Diagnosed, and wider than reported.** The profile modal
([site_utils.js:1332](js/site_utils.js#L1332)) is injected into every page and
styles its inputs with `.editor-input`, which is defined in
[Forms.css:10](style/Forms.css#L10).

Seven pages load `Modals.css` but not `Forms.css`:

`blog.html` · `submissions.html` · `systems/index.html` ·
`systems/tierlist/index.html` · `systems/updatelog/index.html` ·
`systems/color-codes/index.html`

— and **`recent-changes.html` loads neither**, so it is missing `.profile-field`
as well. Character pages load both, which is why it looks correct there.

All seven are hand-authored (`NEVER_TOUCH` or root pages), so this is an edit
per file, not a generator change. **A test should derive the rule** — every page
that injects the modal loads the stylesheets the modal needs — rather than
listing these seven, or the eighth page will repeat it. `search.html` (F1b) is
that eighth page.

## Carried warnings

**The suite is close to its limit.** ~1470 tests against a single
`python -m http.server` with 4 workers. The failure shape to recognise is a
burst of flakes across unrelated page-loading specs with the run time up by a
quarter — that is load, not a regression. Re-run the failing specs *alone*
before diagnosing; a failure that passes in isolation is load, and a consistent
failure in isolation is real. Seen again in v0.18 from four sequential runs of a
single spec file. The real fix is a threaded server or parallel-safe fixtures.

**A release conflicts on stubs, and the fix is to regenerate.** Each branch
regenerates from Supabase with its own code, and stubs embed an asset stamp
derived from `js/` — so two branches with different unreleased JS legitimately
produce different stubs. v0.18's release PR went `CONFLICTING` on **62 generated
files whose only difference was the stamp**. Resolve toward the integration
branch, then `npm run generate`; never hand-merge, and check afterwards that
nothing only `main` had was reverted.

**F1 adds a generated file, so it adds to that conflict surface.**
`data/search-index.json` regenerates per branch from Supabase like every other
artifact. Expect it in the next release PR's conflict set, and resolve it the
same way — regenerate, never hand-merge.
